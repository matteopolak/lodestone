# Face occlusion data

## What it is

The face-occlusion table answers whether each of the six faces of a canonical 26.2 block state is a complete unit-face occluder. It supplies the directional enclosure predicate used by underwater floor decoration without confusing occlusion with collision, outline, or motion-blocking behavior.

## How it works

`oracle-java/FaceOcclusionOracle.java` walks the built-in block-state registry in ascending global `StateId` order. For each state and face it records whether the runtime's face-occlusion shape is a full block face, then emits six population counts and gap-free 256-state bit-string chunks. The Rust generator in `tests/face_occlusion.rs` independently validates the `C`, `B`, `K`, and `P` rows, packs the six columns into one six-bit mask per state, and writes `src/generated/face_occlusion.rs`.

The public `face_occlusion` module performs one O(1) rodata lookup after `StateId` validation. `Face::Down`, `Up`, `North`, `South`, `West`, and `East` map to bits 0 through 5. Consumers should bind any local worldgen interner ids to canonical state ids once per pass; a state string must not be resolved in the per-candidate loop. The ordinary integration test compares every committed bit and population count with the external dump; its ignored companion is only the byte-exact regeneration gate.

## How to change it

When the canonical game-data version changes, update the oracle class and its dump comments only as needed, run the oracle recipe, then run the regeneration recipe. The ignored drift test compares generated bytes and also checks every state-to-block boundary against the canonical block-state table. Never hand-edit the generated source. A new consumer should use `occlusion_mask` when it needs several faces and `occludes` for one face.

## Configuration

The recipes use `.cache/mc/26.2/versions/26.2/server-26.2.jar` plus its library classpath. `LODESTONE_REGEN=1` permits the focused ignored test to rewrite the generated table. The external dump lives at `crates/lodestone-data/tests/support/face_occlusion_jvm.txt` and is intentionally produced only by the oracle recipe.

## Dependencies

The oracle requires Apple `container`, the cached 26.2 server and Java 25. Runtime Rust code depends on `lodestone-model` and the canonical `block_states::StateId` table. `lodestone-worldgen` binds its local interner ids to this table once per state and uses the result for underwater-magma enclosure checks.
