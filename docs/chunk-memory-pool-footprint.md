# Chunk section memory: pool footprint measurement (issue #362)

## What this is

Issue #362 proposed a size-classed buffer pool with handles for chunk section
data (the `Vec<u64>` behind [`PackedArray`](../crates/lodestone-world/src/packed.rs)
and the `Vec<u32>` palette behind `PalettedContainer::Indirect`), but explicitly
asked for the footprint to be *measured* before anything gets built. This doc
is that measurement, plus the recommendation it implies. **No pool exists in
the tree; this doc does not add one.**

The reproducible measurement lives at
[`crates/lodestone-world/tests/pool_footprint.rs`](../crates/lodestone-world/tests/pool_footprint.rs)
(`#[ignore]`d — it's slow, see below). Re-run it after any future change to
`PaletteKind`, container thresholds, or the generator:

```sh
cargo test -p lodestone-world --release --test pool_footprint -- --ignored --nocapture
```

## The sample

4225 real overworld columns (a 65×65 grid, chunk radius 32 around `(0,0)`),
generated by the actual JVM-verified pipeline
(`lodestone_worldgen::overworld::OverworldGenerator`, seed 42, `y = -64..320`,
24 sections/column) — the same generator `lodestone-server`'s
`overworld_generator` wraps for production use. 101,400 sections total. Not
hand-built uniform sections: the pipeline runs shape (interpolated density),
sea-level fluid fill, and real surface rules (grass/dirt/sand/gravel), so the
sample genuinely contains the three regimes that matter — see below.

**Known limitation of this fixture, stated up front**: the composed generator
(`crates/lodestone-worldgen/src/overworld.rs`) does not yet run carvers
(no caves), the real aquifer, or features (no ores, no vegetation, no
structures), and runs under one fixed biome (no biome variety). A
fully-featured generator would very likely produce *somewhat* more variety per
section (ore veins, cave-cut air pockets) and non-zero block-entity data. The
qualitative conclusion below is unlikely to flip from that — caves mostly add
*more* air (which only grows the already-large "no allocation" bucket) and ore
veins are a small fraction of an otherwise-uniform stone section — but the
exact histogram would shift somewhat. Re-run this test once carvers/features
land if the pool question needs revisiting.

## Re-derived size-class arithmetic

Issue #362 claimed 14 distinct byte classes for a 4096-entry `PackedArray`
across `bits ∈ 1..=32`. Re-derived at runtime from `PackedArray::long_count`
(not trusted from the issue): **confirmed exactly correct**, same 14 classes,
same groupings (512 B at 1 bit up to 16 KiB at 22–32 bits, with the `11–12`,
`13–16`, `17–21`, `22–32` bit ranges each collapsing to one shared class). The
64-entry biome container has its own, smaller 12-class table (8 B–256 B).

**The more important structural finding, independent of any terrain sample**:
this codebase's two live `PaletteKind`s cannot reach most of that table at
all. `PaletteKind::block_states()` clamps indirect storage to `4..=8` bits and
switches to direct at a fixed `15` bits; `PaletteKind::biomes()` clamps to
`1..=3` bits indirect, direct at `6` bits — confirmed against
`crates/protocol/v770/src/packets/chunk.rs`, which builds both kinds with
their un-widened defaults (the only other non-default use in the tree,
`lodestone-shell/src/collision.rs`'s `block_states_with_direct_bits(20)`, is
test-fixture-only, not the live protocol path). So:

- **Blocks**: only 6 of 14 classes are reachable at all — `{4, 5, 6, 7, 8}`
  bits (2.00–4.00 KiB) plus `15` bits (which falls in the shared `13–16` /
  8.00 KiB class).
- **Biomes**: only 4 of 12 classes are reachable — `{1, 2, 3}` bits (8–32 B)
  plus `6` bits (56 B, also in a shared class).

A pool sized to the issue's generic 14-class table would already be carrying
8 dead classes for blocks and 8 for biomes before a single real section is
measured.

## The size-class histogram (measured)

| | count | % of 101,400 sections |
|---|---:|---:|
| No allocation (`Storage::Single`) | 76,019 | 74.97% |
| 4 bits (2.00 KiB) | 25,381 | 25.03% |
| 5–8 bits, 15 bits (all other reachable classes) | **0** | **0.00%** |

Of the 6 classes this codebase's block containers can structurally reach, the
real 32-radius sample populates **exactly one**. Every varied/surface section
had few enough distinct block states (max observed: 6) that `bits_for_size`
never exceeded the 4-bit indirect floor. Biomes were 100.00% `Single` (the
generator's fixed-biome limitation, stated above — not evidence about real
biome variety, just this fixture's honest ceiling).

Regime breakdown, matching the three kinds `CLAUDE.md` asks for explicitly:

| regime | sections | % |
|---|---:|---:|
| Empty sky (air-only) | 64,670 | 63.8% |
| Uniform non-air (e.g. solid stone) | 11,349 | 11.2% |
| Varied surface band | 25,381 | 25.0% |

## The palette-length distribution (measured)

Over the 25,381 `Indirect` block sections: **min 2, median 2, mean 2.7, max
6**. 92.2% have 2–4 distinct states; the remaining 7.8% have 5–8; nothing
reaches double digits, let alone the 256-entry ceiling before a container
switches to `Direct`. Total palette bytes across the whole sample: 265.3 KiB
logical (`len × 4`) vs 427.4 KiB actual capacity — a 1.61× overshoot from
ordinary `Vec` push-doubling (this measurement builds containers via
`PalettedContainer::from_values`, same as `build_storage`'s `Vec::new()` +
repeated `push`; the real network-decode path uses `Vec::with_capacity(count)`
and would show ~1.00×, so 1.61× is a conservative/pessimistic reading, not an
underestimate).

Issue #362's stated hazard — a big palette recycled into a small section,
carrying oversized capacity forward — **does not exist in the current code**:
`Storage::Indirect`'s `palette` is never `clear()`d or `truncate()`d in place.
A width-crossing write goes through `rebuild_with`, which discards the old
`Storage` entirely and rebuilds fresh via `build_storage`. The hazard is
prospective — it would only be *introduced* by a pool that recycled `Vec<u32>`
palette buffers the same way it recycles `Vec<u64>` packed arrays.

## Bytes resident per loaded chunk (measured, mean over 4225 columns)

| component | mean bytes | accessor |
|---|---:|---|
| **Total** (`LoadedChunk::heap_bytes`) | 18,994.0 (18.55 KiB) | — |
| Blocks: packed array | 12,303.0 | `PalettedContainer::packed_heap_bytes` *(new)* |
| Blocks: palette | 103.6 | `PalettedContainer::palette_heap_bytes` *(new)* |
| Biomes (packed + palette) | 0.0 | `PalettedContainer::heap_bytes` (trivial — see biome caveat) |
| Light | 3,562.5 | `ColumnLight::heap_bytes` |
| Heightmaps | 816.0 | `Heightmaps::heap_bytes` |
| Block entities | 0.0 | *(known gap — see below; also none generated)* |
| Column/struct overhead (`Vec<Option<Arc<_>>>` spine + Arc control blocks + `ChunkSection` struct) | 2,208.9 | derived (`total − accounted`) |

At a 32-chunk render distance (4225 columns) that projects to roughly 78 MiB
for this data — comfortably small, consistent with `tests/memory.rs`'s
existing per-column ceilings.

Light was **computed** by this measurement (`compute_column_light` over the
real generated terrain, the genuine singleplayer/worldgen code path — not
hand-authored uniform sections), so it's one step short of server-captured
bytes as evidence, but it is not fabricated: the block occupancy driving it is
real.

## Accounting gaps found

Every structure this pool would touch already has (or, for the two container
splits, now has) a `heap_bytes()`-equivalent:

- `PackedArray::heap_bytes()` — existed already.
- `PalettedContainer::heap_bytes()` — existed; **split into
  `palette_heap_bytes()` / `packed_heap_bytes()`** as part of this work
  (`crates/lodestone-world/src/container.rs`), because the combined number
  couldn't answer issue #362's own question ("how much of this is the
  never-shrinking palette versus the size-classed packed array"). Covered by
  `container.rs`'s `palette_and_packed_heap_bytes_split_sum_to_heap_bytes`
  test.
- `ChunkSection`, `ChunkColumn`, `NibbleArray`, `LightData`, `ColumnLight`,
  `Heightmap`, `Heightmaps`, `LoadedChunk`, `World` — all already have
  `heap_bytes()`.

**One real gap remains, not fixed here** (out of this crate's ownership):
`LoadedChunk::heap_bytes()` approximates block entities as
`block_entities.capacity() * size_of::<BlockEntity>()` — the flat struct size
only. Neither `BlockEntity` (`crates/lodestone-world/src/block_entity.rs`) nor
`lodestone_core::Nbt` (which every `BlockEntity.nbt` field owns) has a
`heap_bytes()` that walks the recursive NBT payload — nested compounds,
lists, and every `String`. A resident chunk carrying real chests, furnaces, or
signs is undercounted by this crate's own accounting today. Worldgen doesn't
generate block entities yet either, so this measurement's own `0.0 bytes`
figure is honestly a "not measured" rather than a "measured zero" — flagging
rather than fixing, since fixing it needs a change in `lodestone-core`
(outside this crate).

## Recommendation

**Do not build the size-classed pool as scoped in issue #362.** Three
independent reasons, each sufficient on its own:

1. **75% of sections need zero allocation.** A pool cannot help what never
   allocates; `Storage::Single` already captures the majority of real terrain
   for free.
2. **Of the sections that do allocate, the real sample populates exactly 1 of
   the 14 (or even the 6 structurally-reachable) classes.** A 14-class pool
   solves a distribution problem that isn't present in real terrain today; a
   6-class pool (sized to what's structurally reachable) still wastes 5 empty
   free lists against this sample. If anything is ever built, size it to what
   is *observed*, not to the generic per-`bits` table — which for this sample
   is one class.
3. **The palette hazard the issue raised doesn't exist yet, and pooling would
   introduce it.** Palettes measured 2–6 entries, nowhere near a footprint
   problem, and nothing today recycles the `Vec<u32>` (every width-crossing
   write reallocates from scratch via `rebuild_with`). Building palette
   recycling now would create the "no length guard, no shrink" bug issue #362
   warned about, in order to save single-digit palette entries.

Combined with the issue's own timing note (`World::load` ~1.0–1.5 µs/insert —
allocation *time* was never the argument for this pool) and the absolute
footprint (~18.6 KiB/chunk, ~78 MiB at render distance 32), there is no
current evidence a pool would move any number that matters. This conclusion
is specific to **today's generator and today's `PaletteKind` configs** — see
the fixture limitation above — and should be re-checked once carvers/features
land, using the same `pool_footprint.rs` test.

If block/biome pooling is revisited later with better evidence, and
separately, if allocator pressure ever becomes a *measured* problem worth
addressing at all: `NibbleArray`'s 2 KiB light buffers (`Arc<[u8; 2048]>`,
already fixed-size, already the single largest non-packed contributor in this
sample at ~3.56 KiB/chunk) are structurally simpler to pool safely than the
variable-width packed arrays — a single size class, no bits-dependent layout.
That's an observation from this data, not a recommendation to build it; it's
outside issue #362's scope.

## How to change this measurement

- The generation sweep, conversion, and every histogram/print live in
  `crates/lodestone-world/tests/pool_footprint.rs`. Radius, seed, and Y range
  are `const`s at the top of the file.
- `derive_size_classes` re-derives the byte-class table at runtime from
  `PackedArray::long_count` — change `PackedArray`'s layout and this test's
  own assertion (`14` classes) will catch a class-count drift automatically.
- The "reachable bits" check hardcodes the current `PaletteKind::block_states`
  / `biomes` thresholds (`4..=8`/`15`, `1..=3`/`6`) as local consts, because
  `PaletteKind` doesn't expose its thresholds as public accessors. If those
  constructors' clamps change, update the consts at the bottom of the test
  file to match, or the "reachable classes" report will silently drift from
  reality.
- Gaps found above (`Nbt`/`BlockEntity` heap accounting) are flagged, not
  fixed — see the "Accounting gaps found" section for what a fix would touch.

## Configuration

- `RADIUS = 32`, `SEED = 42`, `MIN_Y = -64`, `SECTIONS = 24`,
  `WORLD_HEIGHT = 384` — all `const`s in `pool_footprint.rs`.
- The test is `#[ignore]`d (like this repo's live/GPU gates) because a real
  32-radius sweep costs on the order of a minute, dominated by
  `OverworldGenerator::column` (independently measured at ~12–13 ms/column in
  `lodestone-worldgen/benches/generation.rs`). Run explicitly:
  `cargo test -p lodestone-world --release --test pool_footprint -- --ignored --nocapture`.

## Dependencies

- `crates/lodestone-world/Cargo.toml` gained one **dev-dependency**:
  `lodestone-worldgen = { path = "../lodestone-worldgen" }`, test/bench-only.
  `lodestone-worldgen` depends on `serde_json` alone (confirmed before adding
  this) — no dependency on `lodestone-world` in either direction, so this
  edge closes no cycle and never touches `lodestone-world`'s own library
  build or anything that depends on it.
- The test reads `lodestone-worldgen`'s checked-in JVM-parity fixture tree
  (`crates/lodestone-worldgen/tests/support/worldgen_data/`) directly, the
  same fixtures `lodestone-worldgen`'s own tests and benches use.
