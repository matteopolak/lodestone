# World-storage engine decision prototype

## What it is

The native chunk path now uses a complete `NativeDirtyChunkRecord` input and a `NativeChunkRecord` output. Both values carry block, biome, heightmap, resident block-entity, canonical light, and pending block/fluid-tick state together; partial chunk loaders are not part of this API.

`lodestone-storage-prototype` is an isolated, non-production comparison between a purpose-built append/index segment and redb. It supplies a small, reproducible workload for the storage-engine choice without selecting a production engine. `lodestone-storage-schema` is the separate version-1 Protobuf vocabulary for the native backend: it commits generated Rust types, a descriptor, and byte fixtures, but performs no I/O itself. `lodestone-storage` is the native append/index layer that persists validated envelopes as atomically committed replacement batches, plus the compact extension-ID table that those envelopes reference. `lodestone_server::world_storage` is the integrated-server seam: a host explicitly selects `Anvil` or `LodestoneNative`, then an attached server may save and reopen a complete bounded chunk through one `NativeDirtyChunkRecord` input and one `NativeChunkRecord` output. That typed chunk record carries block, biome, heightmap, resident-block-entity, canonical sky/block-light, and pending block/fluid-tick state together, so no partial loader can silently discard a field. It also directly saves and reopens intentionally small typed player and resident-entity locators; neither is a replacement for Anvil's complete player or entity persistence.

## How it works

The current chunk API is the complete-record boundary described above. The older field-by-field examples in this document are historical schema context; a producer must use `WorldStorage::write_dirty_chunk` with `NativeDirtyChunkRecord`, and a reader must consume every field returned by `WorldStorage::load_chunk` as `NativeChunkRecord`. The native adapter validates the backend selection before conversion, so `Anvil` remains untouched and rejects this typed path.

The native comparison harness models independently dirty records rather than serializing a whole column for every save. It first seeds 128 typed chunk envelopes whose deterministic state-index streams are 24 KiB. It then writes one changed chunk and a player envelope carrying a 192-byte extension payload together as one logical save transaction. Both engines receive the same fixed 13-byte keys, validated Protobuf envelopes, replacement order, and transaction boundary. Setup is outside Criterion's timed closure, so the reported logical-byte throughput answers the incremental-write question rather than initial world creation. Before timing, the harness reopens both stores and prints each engine's seeded size, post-save size, and growth; those values are samples to record with the host environment, not a conclusion about the eventual engine.

The custom `AppendIndexStore` appends one self-contained record per replacement and reconstructs an in-memory latest-record index when opened. It calls `sync_data` before publishing a record in that index. Opening truncates an incomplete final header or payload back to the last complete record, which is the only crash-tail recovery promised by this slice. A malformed complete record, unsupported version, reserved-field value, invalid kind, or checksum mismatch refuses to open the segment; silently skipping completed corruption would hide a damaged save.

The segment record has this externally specified, version-1 little-endian layout. No production schema is implied by these test records.

| byte range | field | meaning |
|---|---|---|
| `0..4` | magic | ASCII `LSRP` |
| `4..6` | version | `u16`, currently `1` |
| `6` | kind | explicit record-kind discriminant |
| `7..11` | x | signed `i32` column coordinate |
| `11..15` | z | signed `i32` column coordinate |
| `15..19` | id | `u32` local record identifier |
| `19..27` | generation | reserved `u64`, must be zero in version 1 |
| `27..31` | payload length | `u32` |
| `31..35` | checksum | IEEE CRC-32 of exactly the payload bytes |
| `35..` | payload | opaque benchmark fixture bytes |

`compact` is a size-reclamation control only: it writes the newest value for each key to a sibling file, syncs that file, and renames it over the segment. This prototype deliberately does not define directory-swap recovery, snapshots, compaction scheduling, migration, or Anvil conversion. Those must be specified by the eventual selected engine rather than inferred from this experiment.

The schema's `StorageRecord` envelope carries an explicit format version and selects either a `ChunkRecord` or a typed `GeneralRecord`. A chunk stores signed column coordinates, the target game-data version, per-section numeric state palettes, palette bit widths, packed state-index byte streams, per-section 4×4×4 built-in-biome enum grids, the independent 4×4 surface-biome enum answer, an optional fixed 16×16 motion-blocking heightmap, complete named-NBT roots for resident block entities, and an optional complete canonical light-section stream. Each light layer is a typed `LightData` oneof: absent is `Missing`, a four-bit `uniform` value is compact, and `values` is exactly one 2048-byte packed nibble array. The light stream includes the one section below and one above the block range, preserving the same boundary convention as `lodestone_world::ColumnLight`. Position and type stay inside each NBT root: this lets `BlockEntity::Opaque` preserve an unsupported entity's full tree rather than flattening it into a lossy native shape. Core terrain state never repeats resource-location strings. General state has distinct typed forms for world properties, players, and entities. An engine may save an envelope only after `validate_record_with_extensions` accepts the representation-level invariants that Protobuf cannot state, such as a known format version, a non-empty palette with a width from 1 through 15, no legacy raw light bytes, strictly ordered typed light sections with four-bit uniforms and exact 2048-byte arrays, a biome section that aligns with its block section, complete built-in enum grids, either no motion-blocking map or exactly 256 `u16`-range entries, and an extension payload ID registered in the durable table.

`lodestone_storage::NativeStore` groups one or more `RecordWrite` values into a transaction. Each write carries a fixed 13-byte `RecordKey` — signed column coordinates, a `u32` local ID, and an explicit chunk/general discriminant — plus one validated `StorageRecord` envelope. Thus a hot record does not carry names to identify itself: a future producer allocates compact local IDs for its general records, while a whole-column chunk uses local ID zero. The record-kind discriminator must agree with the envelope's `oneof`, so a byte stream cannot accidentally index a chunk payload as general state.

The on-disk stream is a sequence of version-1 transactions. A transaction has a `LSTB` start header (record count, encoded-body length, and CRC-32), fixed key/length/CRC frames whose payloads are Protobuf envelopes, and a matching `LSTC` commit header. The writer syncs the start and body before appending and syncing the commit marker, then publishes all new index entries together. On open, only a transaction with a complete matching commit marker contributes to the latest-record index. An incomplete final start, body, or commit marker is truncated back to the preceding transaction boundary. A complete transaction with a mismatched marker, checksum failure, invalid Protobuf, invalid schema invariant, duplicate key, or trailing bytes refuses to open instead of silently losing durable state. Reads check the indexed payload checksum again before decoding.

`NativeStore::committed_chunk_coordinates` exposes a copied, deterministic snapshot of just the latest committed chunk keys. Its order is `(column_x, column_z)`, duplicates collapse naturally because the underlying latest-record index has one entry per key, and it filters out every general record. It does not seek to or decode a payload. The snapshot exists only after the normal open/recovery scan, so an incomplete final transaction is absent and completed corruption still prevents an open. Version 1 keys do not include a dimension discriminator; callers receive only the horizontal coordinate pair. `WorldStorage::native_chunk_coordinates` takes that snapshot under its native-backend mutex, which makes the returned vector stable after the call even if a later writer commits more chunks.

`WorldStorage::native_chunk_records` is the corresponding typed terrain-export boundary. Callers supply the selected vertical extent because neither the native key nor version-1 record defines a dimension height; it returns `NativeChunkSnapshot` values in coordinate order, each pairing that recovered coordinate with the complete `NativeChunkRecord`. The backend lock covers index discovery and every read/decode, preventing a concurrent writer from replacing a selected column between those steps. A missing light stream, malformed envelope, or unsupported field rejects the entire selection rather than exposing terrain-only data to an exporter. Anvil rejects this native-only request and does not scan compatibility files.

`NativeStore::committed_general_keys` is the matching copied snapshot for latest general-record keys. It retains each key's producer-owned coordinates and local ID, follows the `RecordKey` canonical order, and excludes chunk records. This is the discovery boundary for a reviewed player, entity, or metadata exporter: a caller must read and decode each returned envelope before deciding its typed destination, because the key intentionally does not duplicate the envelope's typed discriminator or identity. It likewise works only from the recovered index, so replacement history and an incomplete final transaction cannot create duplicate or phantom export candidates.

`WorldStorage::native_general_records` is the typed export boundary built on that recovered snapshot. It holds the native-backend lock from key snapshot through each read, so no writer can replace a selected record between discovery and decoding. It returns canonical-order `NativeGeneralRecord::{WorldProperties, Player, Entity}` values only after the established bounded readers accept their bodies and each body proves it is at its reserved key: world properties use `WORLD_PROPERTIES_KEY`, while player and entity identities recompute their separate UUID-derived keys. An unknown body, extension payload, malformed value, or key/body mismatch fails the whole snapshot instead of leaking an opaque or misrouted export candidate. Anvil rejects this native-only request and is not scanned.

`NativeStore::compact` rewrites the latest value for every indexed key as one fully committed replacement transaction. It writes and syncs `world.ls.compacting`, renames the active `world.ls` to `world.ls.previous`, then publishes the replacement as `world.ls`; each name transition is followed by a directory sync. A reopen removes an unpublished replacement while the old active segment still exists, restores `world.ls.previous` when the active name disappeared before publication, and keeps the new `world.ls` if publication completed before old-file cleanup. A replacement with neither an active nor previous segment, or all three segment names at once, is ambiguous corruption and refuses to open. This gives compaction a deterministic crash outcome without adding rollback snapshots: an interruption during maintenance picks the last committed active segment, while a published replacement remains durable. `WorldStorage::compact_native` exposes this only for the selected native backend and returns the retained-record count plus before/after bytes; it serializes in-process Lodestone handles but cannot establish cross-process exclusivity.

Extensions are registered once in an `ExtensionTable`. A registration has a non-zero local numeric ID, namespace, name, and schema version; a record carries just the local ID and opaque extension bytes. `NativeStore` stores the table as an atomically replaced `extensions.ls` sidecar, restores it before validating the segment's latest records, and refuses a payload whose local ID is absent. `register_extensions` sorts and deduplicates one request batch before assigning the lowest unused IDs, preserves existing assignments across reopen, and refuses a second version for an already registered namespace/name. `WorldStorage::register_native_extensions` and `IntegratedServer::register_native_extensions` expose that lifecycle only for the explicitly selected native backend; Anvil rejects it. This keeps the string-bearing registry outside hot core records while still making a save's extension contract explicit.

`WorldStorage::write_dirty_world_properties` and `load_world_properties` own the world's one generated `WorldProperties` envelope and its reserved native key. Metadata producers therefore cannot create a valid properties body that the typed reader will never find. This native-only write does not modify Anvil files; the existing Anvil metadata importer calls it only after its ordinary loss preflight and authorization.

`WorldStorage::write_dirty_player` and `WorldStorage::load_player`, surfaced by `IntegratedServer::write_dirty_native_player` and `IntegratedServer::load_native_player`, are the direct locator boundary for the typed `PlayerRecord` body. `NativePlayerRecord` carries exactly a complete 16-byte UUID, a built-in dimension, three producer-owned signed fixed-point coordinates, and millidegree yaw/pitch. `NativePlayerData`, written and read through `write_dirty_player_data` and `load_player_data`, adds the independently consumable typed game mode without changing locator-only producers. It deliberately has no conversion from a live player object: the live snapshot uses floating point while the locator's fixed-point unit belongs to its producer, so implicit rounding would fabricate a persistence contract. It does not claim to preserve inventory, health, velocity, or opaque player fields. The regular complete player state remains on the established Anvil path; its game mode wins whenever present. `anvil_player_export::export_all_players` converts a complete native general-record snapshot into staged Anvil player files, preserving every native player field and filling fields absent from the native schema with new-player defaults. Publication renames one complete `players/data` directory and refuses an existing target rather than silently merging or replacing player data. Player and resident-entity general keys reserve one local-ID bit as a typed domain, so equal UUIDs can persist independently. The remaining 95 compact identity bits make a same-type collision explicit because the complete UUID stays in the protobuf body and every write and read compares it. The schema rejects a UUID of any other length and the unspecified or unrecognised dimension value. General-record extensions are also refused by this reader until it has a lossless consumer for them.

The integrated-server lifecycle consumes that data for the selected `LodestoneNative` backend. The persistent constructor attaches the same `WorldStorage` handle to its `RegionChunkSource` before spawning the connection task; login reads a valid overworld locator for the initial join position and rotation, while a missing record uses the existing world-spawn/Anvil fallback. A native game mode fills the join value only when the complete Anvil player data has no mode; otherwise Anvil remains authoritative. A corrupt or extension-bearing locator is logged and blocks native overwrite for that session, leaving the complete Anvil file available for recovery. Non-overworld locators are retained but do not change an overworld join or get overwritten until dimension-aware restore exists. Live position values use an explicit signed-thousandths-of-a-block conversion and rotations use millidegrees; a real disconnect writes synchronously, while singleplayer shutdown publishes a separate in-memory native-data slot, joins the connection task, and then commits the last typed record. This runtime seam intentionally does not replace complete player persistence.

`WorldStorage::write_dirty_entities` and `WorldStorage::load_entity`, surfaced by `IntegratedServer::write_dirty_native_entities` and `IntegratedServer::load_native_entity`, provide the corresponding small resident-entity record. `NativeEntityRecord` retains only a complete UUID, canonical resource-key type, built-in dimension, exact IEEE feet position, and yaw/pitch. Resource keys avoid registry-local numeric type IDs, while retaining floating values avoids inventing a fixed-point unit for a live pose. Each write names the entity's resident chunk and vertical extent; the adapter rejects non-finite or out-of-range coordinates, a pose outside that extent, repeated UUIDs in one batch, compact-key collisions, malformed type keys, extensions, and stored poses outside the requested bounds. The UUID-derived key is independent of the resident chunk, so a later write for a moved entity replaces its one record instead of retaining a stale old-column copy. Its dedicated typed-key domain means it also cannot alias a player locator with the same UUID. This is an explicit record consumer, not a `MobSim` or Anvil entity restore: motion, health, item lifecycle, AI state, and opaque fields have no lossless native representation here and are neither stored nor dropped from Anvil.

The first production chunk adapter is intentionally narrower than the schema's eventual scope. `WorldStorage::write_dirty_chunk` converts a server `ChunkColumn` into one independently replaceable `ChunkRecord`: it emits a per-section local palette of built-in numeric block-state IDs, a one-to-fifteen-bit little-endian packed local-index stream, no light stream, the complete 4×4×4 built-in-biome grid for each section, the separate 4×4 surface-biome grid, a retained 16×16 motion-blocking map when the source has one, and one empty-root named-NBT byte string for each resident block entity. `WorldStorage::write_dirty_chunk_with_light` takes the separate `lodestone_world::ColumnLight`, checks its `section_count + 2` shape, and writes each Missing/Uniform/Values layer without expanding uniform data. `IntegratedServer::write_dirty_native_chunk_with_light` and `IntegratedServer::load_native_chunk_with_light` expose that same selected native-record path to a persistent host without redirecting `WorldSaveHandle` or `RegionChunkSource` away from Anvil. Before writing, the adapter requires every entity's NBT position to match its `ChunkColumn` tuple, lie within this record's horizontal column and vertical extent, and be unique. `WorldStorage::load_chunk` refuses a record that carries a light stream because it has no light return value; `WorldStorage::load_chunk_with_light` validates the requested key, current game-data version, contiguous block and light section sequences, packed lengths, palette indices, enum values, grid extents, heightmap range, and every NBT root's name, trailing bytes, position, extent, and uniqueness before reconstructing both a real `ChunkColumn` and `ColumnLight`. A light-aware reopen of an older terrain-only record returns `MissingStoredLight` rather than treating unknown data as dark. Malformed or custom data that does not fit this lossless NBT/light boundary is an error, never a dropped entity or light layer; opaque NBT that does fit is retained verbatim. The integrated-server restart proof reads blocks, biome answers, a deliberately non-uniform heightmap, block entities, and missing, boundary, uniform, and varied light layers through a fresh server, so this is not merely a segment-level round trip.

For the production lifecycle, `IntegratedServer::save_native_now` and its autosave/shutdown caller snapshot all pending source columns, live block entities, and both scheduler queues before the Anvil writer drains them. The live `ServerProtocol` computes canonical light for each column; missing heightmaps or light are explicit errors rather than silently incomplete native records. `IntegratedServer::reopen_native_chunk` stages both queues into the persistent scheduler while returning the complete `NativeChunkRecord`. Anvil remains the compatibility writer and loader.

`WorldStorage::write_dirty_chunk_with_scheduled_ticks` adds the smallest live-scheduler extension: one chunk record carries separate block and fluid pending-tick lists, each entry's absolute trigger tick, typed priority, and its queue's world-wide insertion order. `load_chunk_with_scheduled_ticks` validates and stages those records into a `ScheduledTickHandle`; its next scheduler access merges them with those stored order keys, so reloading columns in a different order cannot change ties across chunk owners. The record represents only the built-in actions this server can decode. A plugin/custom action, an unrecognised enum value, duplicate insertion key within one queue, or a tick outside the record's column is rejected rather than converted into a dropped or inert callback. The established Anvil tick lists and save/load path are unchanged.

This is **not** a complete native world format yet. The adapter preserves every built-in three-dimensional biome cell, surface-biome answer, retained motion-blocking heightmap, resident block entity that can be represented as a complete NBT root, and separately supplied canonical light column, but before writing it still refuses any column with structures, shaped-only generation, or undrained generation-spawn candidates. It also rejects a biome outside the current built-in enum census rather than coercing an extension biome into a built-in value. The server `ChunkColumn` and its canonical `ColumnLight` remain separate values, so ordinary terrain-only writes still have no light and the light-aware method must be selected explicitly. Legacy raw light byte placeholders are rejected rather than ambiguously interpreted. The caller supplies `min_y` and `height` when loading because version 1 stores section coordinates but no dimension definition; minimum Y must be aligned to 16. The existing Anvil `RegionChunkSource` remains the live terrain/entity/metadata loader and is deliberately not redirected through this partial adapter.

`crates/lodestone-storage-schema/tests/fixtures/` contains externally specified version-1 hexadecimal byte fixtures for a chunk envelope, a world-properties envelope, and an extension table. The tests decode each fixture into generated types, assert every semantic field, then re-encode it byte-for-byte. They are intentionally not generated by the Rust encoder, so a symmetric encoder/decoder mistake cannot approve a wire-layout change.

`RedbStore` uses the exact same fixed `RecordKey` byte representation and replaces the same values through one committed redb write transaction per logical save. The direct `lodestone-storage` benchmark repeats that comparison against `NativeStore`, including the production envelope validation and encoding path, so it does not compare unrelated key shapes, opaque payloads, or atomicity boundaries.

## How to change it

Keep the workload representative and bounded. If a changed fixture is intended to stand for a new world-state category, add a distinct `RecordKind` value and explain its size, update rate, and keying in this document. Do not turn a benchmark payload into a save schema.

To change the native vocabulary, edit `crates/lodestone-storage-schema/proto/lodestone/storage/v1/storage.proto`. Preserve field numbers and use new optional fields or `oneof` members for compatible additions; incompatible semantics require a new envelope version. Regenerate both committed artifacts with:

```bash
LODESTONE_STORAGE_SCHEMA_REGENERATE=1 cargo check -p lodestone-storage-schema
```

The build script always recompiles the schema with a vendored Protobuf compiler and compares the result with `src/generated/lodestone.storage.v1.rs` and `storage.fds.bin`. Normal `cargo check` and `cargo test` therefore fail on an unregenerated schema or generator drift. Update the independent fixture only after explicitly specifying its new bytes and field meanings; never rewrite it from `encode_to_vec`.

`NativeStore::write_transaction` is the boundary a dirty-record producer calls through `WorldStorage::write_dirty`. Keep writes small and group only state that must become visible together; a batch is durable only once its commit marker is synced. Before emitting any extension payload, call `register_native_extensions` and retain the returned `RegisteredExtension::local_id`; do not invent an ID or mutate a registered schema version. `WorldStorageBackend::Anvil` deliberately refuses typed-record writes and native extension registration instead of dropping them: the established `RegionChunkSource`/`WorldSaveHandle` path remains first-class and keeps its dirty-column behaviour. `IntegratedServer::open_persistent_with_mobs_and_storage` now attaches the selected native backend to the production autosave and shutdown lifecycle while retaining that Anvil terrain/entity/metadata path. Use `save_native_now` only as the same complete-record lifecycle seam used by native autosave; it snapshots live entities and both scheduler queues, computes light through the live protocol, and refuses missing heightmaps or light rather than omitting them. `reopen_native_chunk` stages both queues into the persistent scheduler and returns the complete decoded value. Use `write_dirty_native_player` only for a producer that already owns the locator's fixed-point contract; it neither schedules itself nor alters the Anvil player writer. Call `WorldStorage::compact_native` only from a maintenance point that has exclusive access to the store; it rewrites every live record into one transaction and its returned before/after byte counts report the reclaimed append history. The dedicated `lodestone-server native-compact --native-path <native-store>` command is that operator path: stop every server using the world first, and it refuses a missing `world.ls` instead of creating an empty store. `committed_chunk_coordinates`, `native_chunk_records`, and `committed_general_keys` are safe point-in-time selections, but they are not live iterators: take one snapshot and pass its owned values through the export input, rather than attempting a read/write stream over the segment. A general key is not a type assertion; always read and decode its current envelope before routing it to a typed exporter. Do not change the transaction-header constants or key byte representation in place: a format change requires a new storage version and an explicit reader/migration policy. The crate currently serializes snapshot reads and writes through one mutable file handle; it provides coherent snapshots but not parallel-reader throughput. Schema negotiation, migration, Anvil loss preflight, native support for structures and automatic source selection are follow-up work. It intentionally provides no rollback guarantee.

For chunk changes, update `NativeDirtyChunkRecord` and `NativeChunkRecord` together. The former is a borrowed snapshot requiring the complete column, light, and scheduler; the latter owns all decoded payloads and offers `stage_scheduled_ticks` for the live queue handoff. Do not reintroduce a terrain-only or light-only chunk reader: replacing one complete native record with a partial value would erase state that the record already knows how to preserve.

Run the comparison explicitly on an otherwise idle machine; it is not an ordinary CI command and no duration threshold is committed:

```bash
cargo bench -p lodestone-storage --bench incremental -- --sample-size 20
```

Record both logical-byte throughputs, the printed seeded/post-save/growth byte counts, recovery outcome for an interrupted append, and the environment. The existing prototype benchmark remains useful for early append/index experiments, but it is not the engine-selection run. A decision needs repeated same-machine comparisons, compaction cost and reclaimed bytes, and recovery/corruption results, not one timing. Before promoting either store, add tests for concurrent readers/snapshots, interrupted compaction, and the actual integrated-server dirty-record consumer.

## Configuration

There are no runtime flags. A host constructs `WorldStorage::open(WorldStorageBackend::Anvil)` to select the existing compatibility backend, or `WorldStorage::open(WorldStorageBackend::LodestoneNative { directory })` before calling `IntegratedServer::open_persistent_with_mobs_and_storage`. `NativeStore::open(directory)` uses `world.ls` and its durable `extensions.ls` table within that directory. `lodestone-server native-compact --native-path <native-store>` requires that existing `world.ls` and must run only after every process using the store has stopped. Native chunk loading also requires the active dimension's `min_y` and `height`; the current adapter accepts a positive height and a 16-aligned minimum Y only. `NativePlayerRecord` accepts only `BuiltinDimension::Overworld`, `Nether`, or `End`, and its signed fixed coordinates are deliberately forwarded with no unit conversion. The benchmark constants are `COLUMNS = 128`, `CHUNK_BYTES = 24 KiB`, and `PLAYER_EXTENSION_BYTES = 192` in `crates/lodestone-storage/benches/incremental.rs`. They are deliberately visible and fixed so a result reports a known workload.

## Dependencies

- `redb` is a development-only comparison dependency; no product path depends on it.
- `lodestone-storage` depends on `lodestone-storage-schema` and `prost` for the validated envelope boundary. It uses only the standard library for segment I/O and CRC-32.
- `criterion` and `tempfile` are development-only dependencies used by the explicit benchmark and fast isolated tests.
- The standard library provides filesystem synchronization and the local CRC-32 implementation.
- `prost` is the generated-type runtime, while `prost-build` and `protoc-bin-vendored` produce the checked Rust source and descriptor at build time. The vendored compiler avoids making the drift gate depend on a host-installed Protobuf executable.
