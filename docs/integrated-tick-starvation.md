# Integrated tick starvation

## What it is

The integrated server shares a 20 Hz world-tick task with the live chunk cache. A player-anchor update can expose columns still being generated by the join stream; this keeps the tick task from synchronously generating cold columns, and offers an opt-in trace for slow tick phases.

## How it works

**Resident-only reads.** `resident_tick_terrain_snapshot` builds the natural-spawn terrain view only when every selected column is already retained, through the same atomic boundary as `resident_tick_column` (no check-then-load pair). The view is all-or-nothing so the spawner sees one stable terrain; a stale area retries later. Fluid seeding and random ticks use the boundary too: a cold coordinate is skipped and retried after the join or seed worker installs it. A random-tick draw that reads a cold neighbour discards its events but still advances the position stream (staying put would redraw the same cold read and starve later chunks). Scheduled block/fluid work and event handoffs use resident snapshots; a cold due record is requeued and a cold event stays pending. Cross-column probes admit their whole bounded footprint before entering fire, redstone, fluid, explosion or physics code: `resident_tick_footprint` checks without cloning payloads or refreshing cache recency, and a busy gate defers the whole operation. `snapshot_terrain` remains for callers needing a complete loading snapshot.

The coordinate-gate table uses a non-cryptographic hash; no iteration order affects mutations, packet bytes or generation order (ordered multi-coordinate admission sorts independently). Single-column and single-block reads hold one gate until the snapshot completes and release and prune it under one table lock.

**Holds.** Integrated worlds pause simulation until the client reports `PlayerLoaded` and the initial mob terrain is installed. The marker can arrive before the streamed view is complete, so it alone neither releases the seed task nor proves terrain is presented. A protocol with no player-loaded packet (every pre-1.21 family) returns `false` from `ServerProtocol::sends_player_loaded`, so its connection counts as loaded on entering Play, including after respawn or dimension change; a test client on the manual policy must send the marker itself. A client that never sends it is treated as loaded after 60 vitals ticks (three seconds). While held, native-plugin adjudications still answer: when a proposal is waiting the held tick runs one `GameTick` pass and discards its resolutions (the clock does not advance, but `GameTick` systems observe it). The chunk stream and generation workers stay active while paused. The dedicated host has no local player, so it calls `WorldStateHandle::release_initial_tick_holds` right after opening; its tests wait on wall-clock time.

**Stepping.** A headless harness steps the world with `WorldStateHandle::hold_ticks` (stops world ticks, not the loop's cadence), `step_ticks(n)` (grants exactly `n`, grants accumulate) and `run_ticks_freely`. Gate reads on `tick_stats().tick_count`, recorded at the very end of a tick; the ECS tick witness advances partway through one. Resuming does not replay loading time as a burst. The differential fuzz oracles in `crates/lodestone-fuzz/tests/` are the reference users.

**Lifetimes.** Native world-tick task handles detach when dropped; a closed control channel is not an abort. Explicit abort and the sticky shared shutdown signal stop the loop; sibling dimension loops use the same detached lifetime.

**Block-change delivery.** The connection drains tick-produced block changes into an ordered local queue, keeping only changes for columns already delivered, and sends at most 64 updates per select-loop pass (native and browser), so socket input, keep-alives and chunk publication interleave; relighting stays on its own queue.

**Tracing.** `run_tick_loop_with_weather_impl` (shared by native and `wasm32`) records three phase durations per tick and, when tracing is on, emits an event only for a phase lasting at least one 50 ms period (tick number, phase, follow-area size, resident-column count). Slow waits are traced independently: each wait event records the upcoming tick, requested deadline, request time and resume time relative to the driver's monotonic origin, so one slow wait pairs with its actual tick. Paused initial-world waits are excluded. In the browser, tracing also records `callback_lateness_max_micros` (lateness against the integer-millisecond timeout) and `callback_resume_gap_max_micros` (delay before Rust resumes), maxima over early-wake iterations and not additive; the factory/FFI arm interval adds a small offset. Native leaves these empty; untraced and paused browser waits keep the direct Promise-resolver path.

**Mob seeding.** Seeding waits for the first join. When its area lies inside the initial view it reuses full columns as they become resident; if the stream drains short, the bounded dispatcher generates the missing ones; an area outside the view uses the dispatcher directly. The task installs terrain and persisted entities before releasing its hold. LAN startup warms its fallback tick area through the same dispatcher, after the first join's initial batch (or the playerless random-tick deferral).

**Liveness witness.** `worldgen_tick_liveness` acknowledges the completed initial view, holds one newly visible column behind a bounded gate while moving a player across its boundary, and requires both the server tick counter and the tick-clock counter to advance and a play packet to be processed while generation is still held. A button action before the move creates an ordered scheduled-block workload; natural spawning and random ticks are disabled so progress isolates the generation handoff.

## How to change it

- New periodic tick work must use a resident-only accessor on a bounded `ChunkSource`: never a cold `ChunkSource::column` or blocking `set_block` in the tick task (gates would let the join stream and world clock block each other). Use `try_resident_column_presence` for admission and `try_resident_column` only when the payload is needed; keep the retry behaviour; keep changes in the shared tick-loop body so native and browser agree.
- Wait attribution lives in `TickDriver::wait_for_tick` and `TickTrace`, not the scheduler. Keep worker-local timer controls in `lodestone-time`'s JS tests (stalling the page does not prove a worker timer was delayed), and preserve the direct untraced path and shared cancellation.
- If the update batch size changes, preserve feed order and the delivery-time snapshot boundary (a queued update for a not-yet-visible column must not arrive after its newer initial snapshot), and keep each pass bounded under a fluid cascade.
- Keep mob-seed residency reads nonblocking with the fallback on the bounded dispatcher; do not use `PlayerLoaded` as the fallback boundary. If the seed area changes, update its view-coverage check and drain signal together.

## Configuration

Tracing is off by default. Native: `LODESTONE_TICK_TRACE=1` and enable the `lodestone_tick_trace` target at `info`+ in the `tracing` subscriber. Browser: enable that target through the SDK log level. Only phases, wake delays or yields of at least 50 ms are emitted. `lodestone_block_trace=debug` shows the break action, target, pending dig and adjudication; the `lodestone_server::stall` target warns when an authoritative break keeps the connection loop busy for 50 ms or more.

## Dependencies

`ChunkSource` residency methods, `ChunkStore`'s cache lookup, `FollowArea`'s terrain view, the shared `TickClock` phase boundaries, `rustc-hash` (gate table), `tracing`, and for browser wait attribution `lodestone_time::browser_sleep_observed` with `BrowserSleep` cancellation.
