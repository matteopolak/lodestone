# 26.3 feature decoration

## What it is

`lodestone-worldgen-feature-26-3` runs the 26.3 `feature` and `placed_feature` registries over a chunk: it orders every biome's feature lists into the global per-step sequence, derives the per-chunk decoration seed and the per-feature seed, runs each placed feature's placement modifiers and places the feature, all bit-identical to the real 26.3 server. Ores (`ore`, `scattered_ore`), lakes, fluid springs, disks and the top-layer freeze are ported and oracle-verified; every Overworld feature type is ported and oracle-verified; the Nether and End types (`Feature::Unported`) still place nothing.

## How it works

- `blocks::BlockTable` is the real server's block-state table (`assets/block_facts.txt` in the data bundle, dumped by `BlockFactsOracle263`): property domains plus a fact word per state (air, replaceable, solid, occlusion, fluid, sturdy faces, light). A `State` is the global state id; `with(state, prop, value)` edits a property by the sorted mixed-radix layout. `tags::BlockTags` resolves the bundled block tags (nested `#tag` entries included) into per-block bitsets.
- `env::Env` bundles both plus the six per-state heightmap flags. `level::Level` is the 3x3 chunk window features run in. `set` is the region write (keeps the live heightmaps current, drops writes outside the build height); `set_raw` is the section write ore blobs use (no heightmap upkeep). The two world-generation heightmaps `WORLD_SURFACE_WG` and `OCEAN_FLOOR_WG` are frozen at terrain time; `WORLD_SURFACE`, `OCEAN_FLOOR`, `MOTION_BLOCKING` and `MOTION_BLOCKING_NO_LEAVES` follow writes. `Level::biome` zooms with the obfuscated seed and clamps the quart Y to the stored range (queries above the world, such as an ore range reaching y=384, read the top stored cell).
- `registry::Features::load` parses every placed feature; `registry::sort_features` is the feature sorter: each biome contributes edges between consecutive features, a depth-first search over `(step, first-seen index)` order gives a reverse topological order, and each step's list index is the feature's global index (the seed input). `Decorator::decorate` then mirrors the reference loop: decoration seed from the chunk origin, then per step the sorted union of the present biomes' feature indices, `set_feature_seed(decoration_seed, index, step)`, `PlacedFeature::place`.
- `placement::Placement::modify` appends each modifier's output; `PlacedFeature::place` recurses depth-first, which is the reference's stack discipline (a modifier's whole output is drawn before the first output is processed further). The `biome` modifier asks whether the zoomed biome at the position lists the top-level placed feature in any step.
- `stateprovider::StateProvider` is the block-state provider (`simple`, `rule_based`, `weighted`, a bare state, or a name from the bundled `block_state_provider` registry). A rule-based provider with no answer yields `None` (the disk skips the cell); `get` falls back to the block already there. A new provider type is a variant plus its `parse` and `get_optional` arms.
- `feature::lake` holds `lake` (a blob grid carved from random ellipsoids, checked against the surroundings before any write, then a barrier shell and, for water, ice at the surface) and `spring_feature` (counts rock and hole neighbours). The configured spring fluid is the source fluid, so the placed block is the source block regardless of the `falling` flag. Both read the block table's own liquid flag (water, lava, bubble column) and solid flag. `feature::disk` visits columns x-fastest then z, which fixes the order of provider draws. `feature::freeze` is the top-layer ice and snow pass.
- `climate` answers should-freeze and should-snow from the biome's temperature (frozen modifier and snow-line lapse live in `lodestone_worldgen_core::engine::release26_3::biome`) and `has_precipitation`. Block light is taken as zero everywhere, because the real region reads a light engine that has not run for a chunk still being generated. `Level::biomes` is installed by `Decorator::decorate`. A snow layer survives on a block whose collision up face is full (`BlockTable::collision_up_full`), unless the block is tagged against snow, or tagged to support it regardless.
- Vegetation: `feature::plant` holds `simple_block` (double plants place both halves, waterlogging is copied from the fluid already there) and `block_column`; `feature::select` holds the random, weighted, boolean, sequence and overlay selectors that nest a placed feature (`PlacedFeature::place_nested`). Block providers also include `noise`, `dual_noise`, `noise_threshold`, `randomized_int` and `rotated`; the noise ones build a normal-noise field from the provider's seed. `survive::Kind` classifies each block by its survival rule (vegetation, double vegetation, mushroom, cactus, sugar cane, lily pad, seagrass, kelp, sturdy-below, ...); a block that is not classified is a gap, never a guess.
- Light assumption for mushrooms: a column still being generated reads raw brightness 15 (sky 15, block 0), so a mushroom survives only on blocks tagged to override the light requirement. `climate::RAW_BRIGHTNESS` holds the constant.
- Huge mushrooms: `feature::mushroom` covers both shapes (cap first, then stem; the cap provider is drawn once per cap block, with the face flags set from the position in the cap; blocks only replace air, leaves and the mushroom-replaceable tag).
- `feature::misc` holds `vines`, `bamboo`, `underwater_magma` and `block_blob`. The magma rule treats a neighbour as covering when it can occlude (the table has one occlusion bit, not per-face shapes); vine attachment (`misc::can_attach`) needs a sturdy full face or a full-cube collision and is shared with the tree edge pass. Bamboo survival is `survive::Kind::Bamboo`.
- Cave, ocean and ice features. `feature::multiface` (`multiface_growth`: glow lichen with the plain spreader, sculk vein with its stricter one; the search loop re-reads the same cell each step, as the reference does), `feature::ice` (`spike`, `iceberg`, `blue_ice`; the iceberg mixes `f32` and `f64` exactly as the reference and runs at sea level whatever the origin), `feature::dripstone` (`speleothem`, `speleothem_cluster`, `large_dripstone` over a dripstone or sulfur base; `Column::scan` is the shared floor/ceiling scan, large dripstone uses the table-based trig and a wind offset), `feature::coral` (`coral_tree` and `coral_claw`: the nested placed feature drops one coral block per call and the shape stops growing the moment it declines; the nested feature's own water filter decides, and both shuffles use the shared list shuffle), `feature::room` (`monster_room`: the chest's loot seed and the spawner's mob each draw because the real region attaches block entities to both; the chest turns toward its single solid neighbour), `feature::geode` (`geode`: shells chosen by a sum of inverse distances over a 33-cube, perturbed by a `f32` noise built per placement from the world seed with `engine::release26_3::noise::parity_params(-4, [1.0])`; sums are `f64`, the cuboid is walked x fastest), `feature::patch` (`vegetation_patch` and the waterlogged variant; the surface cells are a `JavaSet` because planting iterates a hash set), `feature::root_system`. Pointed blocks use the `vertical_direction` and `thickness` properties.
- Region random: `Level::region_rng` is the region's own random source, used by pale moss carpet placement (the topper's sides flip coins from it). The real server seeds it from the clock, so the carpet toppers are not reproducible there; the oracle seeds it with the world seed per chunk and the engine does the same.
- Survival rules added for these features: moss and pale moss carpet, sea pickle, small dripleaf (a double plant), spore blossom, mangrove propagule, hanging roots, coral plants, fans and wall fans; coral blocks, sculk catalyst and potent sulfur have no rule.
- Oracle registries: `DecorationOracle263` loads every worldgen registry from the jar's JSON, not from the code-built defaults, because the two differ where a codec does not round-trip (the cherry foliage corner-hole chance is 0.5 in code and 0.25 in the data). `+dump:name` also prints a `t bits value` line for every random draw of that feature, for diffing a divergent draw sequence against ours.
- Gaps: `Decorator::gaps` lists, per placed feature, every feature type or block rule not yet ported. `tests/vegetation.rs` excludes exactly those features on both sides (oracle argument `*,!name,...`, produced by the ignored `print_oracle_args` test), so the fixture grows as gaps close. `print_gaps` summarises what remains.
- Trees: `feature::tree` is one [`Run`] per placement: a trunk placer (`tree::trunk`: straight, forking, giant, mega jungle, dark oak, fancy, bending, upwards branching, cherry, poplar), a foliage placer (`tree::foliage`), then decorators (`tree::decorator`: beehive, trunk and leaf vines, cocoa, place-on-ground, alter-ground, attached-to-logs, attached-to-leaves, shelf mushroom, creaking heart, pale moss), then a leaf-distance pass and an edge pass. `tree::fallen` places the stump and the horizontal log; its decorators run on the same `Run` with the log set holding only the stump, then only the log. Trunk, foliage, root and decoration positions are `javaset::JavaSet`, which reproduces the reference hash-set iteration order (bucket by spread position hash, 16 buckets doubling at 75 percent load, insertion order inside a bucket); decorators read it stably sorted by Y and the distance pass drains its seven work lists in that order, so the order shows in placed blocks. The edge pass (`Run::update_edges`) walks the outer faces of the placed region in the reference face order and turns unsupported plants to air (a large fern whose upper half became a leaf loses its lower half); a vine re-derives its faces from what it can still attach to (a full-cube neighbour or the vine above) and becomes air with none; other block kinds are left alone, so a new neighbour-sensitive block near trees would be a mismatch to look for. The beehive decorator draws bee entries (2 plus a bounded draw each) because the real region attaches a block entity to the hive; the oracle's region reproduces that with a placeholder tag.
- Structure templates: `nbt` reads the gzip NBT documents (`STRUCTURE` in the data bundle), `template::Template` holds a template's blocks ordered as the reference stores them (full-collision blocks, then other blocks, then block entities, each sorted by y, x, z) and `template::place_in_world` replays the reference placement: one palette draw from the feature random (even for a single palette), the processors over every block first (`block_rot` draws one float per rottable block), then the writes, waterlogging, edge-face shape updates (`shape::edge_faces`) and per-block neighbour updates. `feature::structure` holds `template` (weighted entry, rotation draw, rotated-size offsets; the desert well and the sulfur springs) and `fossil` (rotation, template index, chunk-bounded placement at a floor-relative depth, empty-corner check, then skeleton and overlay with their processor lists, from the `PROCESSOR_LIST` bundle). Only rule, block-rot and protected-block processors are supported; anything else lists as a gap.
- Sculk: `feature::sculk` is the world-generation sculk spreader. Cursors (`charge_count` of `amount_per_charge` at the origin per round) take `spread_attempts` update passes; a cursor on sculk, on a vein or on anything else spends charge differently, may place sensors and shriekers, converts supported neighbours to sculk, and moves to a random reachable sculk or vein cell within 12 blocks horizontally. It shares `multiface::Ctx` with `multiface_growth` (spread types are a parameter there). The region's writes run no neighbour updates, so placements are plain writes.
- Probe mode: features too rare for a sweep (desert wells at 1 in 1000, fossils, springs in cave biomes) are tested with `+force:<placed name>:<tries>` on the oracle and `Decorator::decorate_forced` on ours (in tests, `only = ["+force:name:tries"]`). Each try uses feature seed `(decoration_seed, try, step)` and only tries that drew more than the single rarity roll print a line. `+dump:<name>` with a force traces the last try. The oracle's fake level also carries a template manager served from the jar's data, which template features read.
- Controls: `common::reproduces` runs a fixture under another seed and returns whether every feature line still matches; it never panics, and it ignores the chunk header (which names the seed), so a wrong-seed control cannot pass on the header alone.
- Value providers (`provider`), block predicates and rule tests (`predicate`) are parsed once into enums; no JSON is read while placing.

## How to change it

- New feature type: add a variant to `feature::Feature`, parse it in `Feature::parse`, place it in `Feature::place`, and add the type name to the oracle's `types` list in the test. Draw order is the contract: read the real placement once and keep every `nextX` call in order. Reads that the real region answers with void air (outside the build height) go through `Level::get`.
- New placement modifier or block predicate: `placement::Placement`, `predicate::BlockPred`.
- `survive::classify` maps block names to a `Kind`; add the rule to `Kinds::supported` and `can_survive`. An unclassified block makes its placed features a reported gap.
- Debugging a mismatch: the oracle accepts `+dump:<placed name>` (prints that feature's changed cells) and `+probe:x:y:z` (block facts around a position); the ignored `dump_feature` test prints ours (`LODESTONE_DUMP=name,cx,cz`).
- After a version bump: `scripts/regen-worldgen-data-26-3.sh` (documents and tags) and `scripts/regen-block-facts-26-3.sh` (state table), then re-run the oracle commands in the test headers.

## Configuration

None at runtime. Probe layouts: `desert-only.txt` (well, fossils), `sulfur-only.txt` (rooted sulfur spring) and `deep-dark-only.txt` (sculk patch), each with a `+force` fixture in `tests/fixtures`. `tests/trees.rs` replays a fixture of chunks picked from a 144-chunk sweep (greedy cover: the biggest chunk of every feature that changes blocks, two for tree features; the oracle's per-chunk sections are independent, so a subset of a sweep is a valid fixture), over `scripts/worldgen-oracle-26-3/tree-biomes.txt` (a layout of every tree biome plus mushroom fields), with a wrong-seed control and a non-vacuity check on thirteen placed features; regenerate it with the `print_oracle_args` output and the oracle layout argument `tree-biomes.txt` (a bare file name, resolved under the oracle directory). `tests/specials.rs` replays the other layouts: `special-biomes.txt` (oceans, ice, caves, pale garden, with cave biomes repeated so they dominate) and `lush-only.txt` (one biome, so the rare azalea root systems and ceiling plants place); both fixtures are greedy covers of oracle sweeps, and a non-vacuity list pins the features each must change. Dungeons and geodes are rare in noise-only terrain (there are no carvers in the oracle), so `tests/fixtures/rooms-overworld-42.txt` and `geodes-overworld-42.txt` are chunks found by sweeping `plains-only.txt` with only that feature type enabled (`monster_room`, `geode`); both tests carry a wrong-seed control. `ice-only.txt`, `warm-ocean-only.txt` (swept over negative and positive chunks, since most warm-ocean columns are land) and `windswept-savanna-only.txt` give single-biome layouts for the rare icebergs and windswept savanna trees. Root placers (`tree::roots`, mangrove only) run before the trunk: the trunk base is the origin raised by a sampled offset, the column below must accept roots, each side walks a random descending path and nothing is written unless all four sides fit. The pale moss decorator places the pale moss patch configured feature itself; the oracle region answers the registry and generator questions that call asks through a fake level (`fakeLevel` in the oracle), since the real region has no server level. Tests: `tests/ore.rs`, `tests/fluids_surface.rs` and `tests/vegetation.rs` (12 chunks, every ungapped placed feature, with wrong-seed and non-vacuity controls) replay oracle fixtures; the fluids fixture holds 14 chunks picked from a 256-chunk sweep so that the three underground-lake chunks, both springs, every disk and the freeze all change blocks (the test fails if any stage places nothing). `cargo test -p lodestone-worldgen-feature-26-3 --release` (add `-- --ignored --nocapture` for the decoration timing, about 2 ms per chunk for the ore families over the mixed-biome terrain).

## Dependencies

`lodestone-worldgen-data-26-3` (documents, tags, state table), `lodestone-worldgen-core` (random sources, the biome zoom, simplex noise; the tests also use its terrain generator). Verification: `DecorationOracle263` builds the nine chunks the features step receives (fill and surface over a synthetic quart-resolution biome layout, final heightmaps primed, no carvers), allocates the real region without a server level and runs the real sorter, placer and features chunk by chunk. It prints, per executed feature, the random-draw count and a hash of the changed blocks, and a hash of each final chunk, so a mismatch names the first diverging feature. `BlockFactsOracle263` dumps the state table (bit layout in its header, including the liquid flag and the collision up-face fact). The oracle's region answers block light as zero and drops scheduled ticks, which never change a block. A wrong-seed control must fail. The oracle binds both block and fluid tags from the jar's data; without the fluid tags, water-checking blocks silently never survive.
