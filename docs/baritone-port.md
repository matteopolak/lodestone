# Autonomous navigation: a Baritone-equivalent for Lodestone

## What this is

A plan for building a **Baritone-class navigation and autonomy system** for this client: tell it
a coordinate or a block type and it walks, jumps, digs, bridges and climbs its way there, across
terrain it has not seen yet, without desyncing. Delivered as a **bevy plugin**, so it has the same
power as built-in code — the requirement driving
[`docs/bevy-migration.md`](./bevy-migration.md).

It is a **plan, not a port.** The architecture below is designed from first principles for this
codebase. Every movement constant is taken from Minecraft's own source
(`/.cache/mc/26.2/src`, de-obfuscated) or from the censuses this repo already generated by booting
the real 26.2 jar. Baritone was read once, by one agent, to establish *what the problem is* and
*which failure modes are real in practice* — §1.2 explains why that distinction matters and §2
is the whole of what was taken.

**Nothing here is buildable until `docs/bevy-migration.md` Stages 2 and 4 land.** §8 maps the
dependency precisely, and §9's first milestone is deliberately something that ships *before* them
and is visible on its own.

## 1. Provenance and licence

### 1.1 The facts

Baritone is **LGPL-3.0**: its `LICENSE` is the LGPLv3 text verbatim, and every source file carries
the standard "either version 3 of the License, or (at your option) any later version" header. (The
README's "LGPL-3.0 with anime exception" badge points at a JPEG, not at operative licence text.) A
transliteration derived from reading that source would be a derivative work, and Rust's static
linking means "linked into" is "the whole binary" — which is why the copyleft boundary is worth
being deliberate about even when the owner is content with the licence.

### 1.2 The decision, recorded

The repo owner has decided:

1. **This is a clean-room design.** The plan is written from the problem statement plus Minecraft's
   own data, not from Baritone's expression. That is not only the legally clean path, it is the
   *more accurate* one: costs derived from `lodestone-physics` are the costs our own executor can
   actually satisfy, and no third party's tuning constants can say that.
2. **The licence is the owner's choice, not a constraint on the design.** A genuine clean-room
   design need not be LGPLv3; the owner is content for it to be. Either way it lives in **its own
   crate with its own `LICENSE` file**.
3. **Implementers will not read Baritone.** This document plus this repo plus `.cache/mc/26.2/src`
   must be sufficient. If you find yourself needing a number from somewhere else, that is a defect
   in this document — file it.

### 1.3 The crate boundary, and the one linking concern that drives an API decision

Two crates, for reasons good independent of licence (§4.0):

| crate | what | deps |
|---|---|---|
| `lodestone-nav` | the version-free search core: world view, movement graph, cost model, goals, the resumable search. A plain library — no bevy, no ECS, no async, no threads. | `lodestone-physics`, `lodestone-model`, `lodestone-world` |
| `lodestone-autopilot` | the bevy plugin: worker orchestration, the per-tick executor, behaviour arbitration, chat commands, debug overlay. | `lodestone-nav`, `lodestone-ecs` |

**Do not name either crate after Baritone.** In a clean-room design the name is the one thing that
would suggest derivation where there is none, and it invites a trademark question nobody needs.

**The linking concern, because it drives §7.5:** the collision-shape, path-type and block-property
censuses this design needs are today reachable *only* by depending on `lodestone-v770` directly
(§3.3). Version crates are permissively licensed like the rest of the tree, so nothing breaks —
but a plugin that depends on one is **version-locked**, which defeats the entire `VersionAdapter`
seam, and it drags a licence boundary through a generated data crate for no reason. The fix is one
new `VersionAdapter` method (§7.5), and it is a prerequisite rather than a nicety.

## 2. The problem, stated independently of any implementation

### 2.1 What a system of this class must be able to do

- **Path over the voxel movement graph**, where an edge is not "step to an adjacent cell" but
  "execute a *movement*" — walk, walk diagonally, step up, step down, drop a survivable height,
  jump a gap, climb a ladder, swim — each with its own duration and its own preconditions.
- **Modify the world as part of the path**: break a block to get through, place a block to get
  across or up. This is what separates a player bot from a mob navigator, and it is where most of
  the cost model's interest lives.
- **Path further than it can see.** Render distance is finite; the goal usually is not. The search
  must be able to end three ways — reached the goal, ran out of budget, ran out of *world* — and
  the last two must still produce forward progress.
- **Keep moving while it thinks.** A bot that stands still for 400 ms every 30 blocks looks broken.
- **Execute the path against a server that validates it.** The client predicts, the server
  re-simulates, and the gap between them is where paths fail (§3.2 quantifies the gap the server
  actually tolerates).
- **React to a world that changes under a committed plan** — a block someone else mined, a chunk
  unloading, gravel collapsing, lava spreading.
- **Arbitrate between concurrent intentions**: the user's explicit "go here" versus a mining task's
  "go to the next ore" versus a safety reflex's "get out of the lava" versus exploration's "wander
  toward unseen chunks".
- **Do all of that under a tunable policy**, because "may it break blocks?" and "how much fall
  damage is acceptable?" are user decisions.

### 2.2 What makes it hard

Five problems, in rough order of how much of the design they dictate:

1. **The cost model and the executor must agree.** A path is a promise about time. If the search
   believes an edge takes 6 ticks and the executor needs 14, every estimate downstream is wrong,
   segment hand-off mistimes, and the chosen route is not the one that would have been fastest.
   Worse: if the search believes a movement is *possible* and the executor cannot perform it, the
   bot loops — plan, fail, replan the identical plan. This coupling is the reason §4.4 derives
   costs by *simulating the executor's own inputs* rather than by writing formulas.
2. **A long search cannot run on the frame thread.** Tens of thousands of expansions against a
   16 ms frame and a 50 ms tick. And this client has a hard rule that simulation must never be
   gated on anything ([`docs/frame-pacing.md`](./frame-pacing.md): a client the server considers
   stalled is sent **no chunks at all**, silently). §5 is the answer and it is the crux.
3. **The world the search reads is not the world the executor walks.** The search needs a frozen,
   coherent world or it produces paths through blocks that were never simultaneously there. The
   executor runs later against the live one. Bridging that without re-validating an entire plan
   every tick needs a mechanism (§4.5).
4. **Movement is momentum-dependent, but a graph node is a position.** Whether a gap is crossable
   at all depends on entry velocity. A purely positional graph must either assume the worst (and
   refuse jumps it could make) or the best (and plan jumps it cannot) — and the second failure is
   §2.2(1)'s loop. §4.3 pays for an extra node dimension to fix it.
5. **Partial success must be first-class.** Almost every real search ends without reaching the
   goal. "No path" is the wrong answer; "here is the best 40 blocks I found, ask again when you get
   there" is the right one (§4.6).

### 2.3 Failure modes that are real in practice

This is the genuinely valuable thing taken from reading the reference implementation: a catalogue
of what actually goes wrong. These are observations about Minecraft and about executing computed
paths. They are expensive to rediscover, and most of them are invisible until you have a bot that
moves.

**Losing track of where you are on the plan**

- **Backwards rubber-band.** The server rejects movement and teleports you back a block or two. The
  executor's idea of "which edge am I on" is now *ahead of the body*. Recovery needs a backwards
  scan over already-completed edges for one whose valid-position set contains you — and it must
  **reset the internal state of every edge in between**, or a half-finished edge resumes mid-way
  and immediately mis-fires.
- **Forward overshoot and multi-edge skipping.** At sprint speed, on ice, or in a descent chain, the
  body can end up several edges further along than tracked. So a forward scan is needed too — but
  deliberately **not** over the immediately next one or two edges, because an edge is legitimately
  allowed to be "past its own destination" while still unfinished (a sneak-place is), and the edge
  must remain the authority on when it is done.
- **The position→edge mapping is many-to-one and must stay a function.** Each edge declares a *set*
  of positions that count as "on it". Both recovery scans depend on that, and on the plan **never
  revisiting a position** — a plan that does makes the mapping ambiguous and recovery
  non-deterministic. Validate plan well-formedness at construction.
- **"Where am I, for planning purposes" is not `floor(position)`.** Several Minecraft facts conspire:
  soul sand's collision top is 0.875 and a slab's is 0.5, so the block whose cell your feet occupy
  is not always the block you are standing on; if the block below you is not walkable you may be
  sneaking out over an edge, and the plan must be seeded from the supporting column you are
  actually standing off of; if you are mid-jump the seed is the block below. Get this wrong and the
  plan's first node is somewhere you are not standing.
- **Very high speed breaks the arrival test.** Above ~20 blocks/s (reachable with Speed effects or
  ice) a walk edge can finish one or two blocks past its destination. Accept those positions as
  success rather than classifying them as off-course.

**Stalling, drifting, and the counters that catch them**

- **A plan can be legal, executable, and still stall forever.** The commonest shape is being a few
  hundredths of a block short of a cell boundary with forward held and something preventing
  progress. **Every edge needs a tick budget and a hard failure.**
- **The stall budget must come from the *planning-time* cost, captured once when the edge begins —
  never from a live recomputation.** This is the most non-obvious rule in this section: a
  break-then-move edge's *remaining* cost falls as you break the blocks, so a live budget always
  outruns the elapsed time and the counter never trips. The bot then digs forever.
- **Two drift thresholds, not one.** A lenient one that starts a patience counter (order of
  seconds, not ticks) and a hard one that aborts immediately. Two details matter: distance is
  measured to the *nearest valid position anywhere in the plan*, not to the current node, so a
  legitimate shortcut does not look like drift; and a falling edge must be measured
  **horizontally only**, because mid-fall you are genuinely far from both the block you left and
  the one you will land on without being off-course at all.
- **Recalculation churn is its own failure mode.** A replan trigger that can fire every tick makes
  the bot oscillate and execute nothing. Every trigger needs hysteresis or a rate limit.

**The world changing between planning and execution**

- **Per-edge cost re-verification, with three outcomes**: now impossible → abort; inflated beyond a
  tolerance → abort; otherwise continue. Crucially the *inflation* check must be **suppressed when
  the edge was planned against real loaded chunks**, because then an increase is almost always the
  plan interfering with itself (an earlier edge broke or placed something), not stale data.
- **Do not walk up to the hazard before replanning.** If an edge several ahead has become
  impossible, stopping at the last moment is unsafe — lava that has spread across the route may
  still be spreading, so approaching and *then* replanning puts you in it. Verify a small window of
  upcoming edges whenever you start a new one, and abort early.
- **Chunk boundary at the frontier.** If the next edge's destination is in an unloaded column, pause
  in place. This is routine when travelling faster than chunks arrive, not an error.
- **Truncate the tail of even a successful long plan.** The far end of a search under a relaxed
  heuristic is the least trustworthy part *and* the least-known world. Discard a fraction of the
  tail above some minimum length — but never when the plan actually reaches the goal.
- **Gravity blocks make breaking non-local.** Breaking a block adjacent to unsupported sand or
  gravel triggers a cascading collapse; refuse such breaks outright. And when an edge requires
  breaking, let falling-block entities in the column settle before continuing, or you break into a
  column that is still arriving.

**Movement-specific physical hazards**

- **Sprinting through a descent overshoots the landing** by up to a block. If the block one further
  along — at *any* of the three heights the body occupies — is something you must not enter (lava,
  water when you did not plan to swim, fire, cactus, sweet berry bush, cobweb, magma, bubble column,
  end portal), you must both refuse to sprint and aim *back* toward the descent's origin so you
  brake instead of gliding. A "must not walk into" block family has to be a first-class concept.
- **One specific clipping geometry**: if the block one past a descent's landing is solid but the two
  above it are passable, the overshoot can glitch you upward into it. Force braking on exactly that
  combination. Viewed forward, the same geometry is a descent immediately followed by an ascent in
  the same direction — which is physically flat ground, so recognising and collapsing that pair is
  worth doing, or the bot brakes for nothing.
- **Ascending.** Do not press jump if already airborne. Do not jump with significant lateral
  velocity — you clip the corner. Falling below the origin height means the edge is unrecoverable
  and must fail *immediately*, including during a block-breaking preparation phase, not only during
  motion. Do not jump when stepping onto a bottom slab: step height covers it and jumping
  overshoots.
- **Sprint-ascending needs lateral centring** (order of a tenth of a block) and a head-clearance
  check *behind* you — the block two above the space you came from must be passable, or you must
  travel forward far enough for your head to clear it first.
- **Pillaring upward.** Sneak first and click on the *following* tick: the crouch state is not
  observable until the next tick. Stay near the column centre — sneaking arrests you roughly a
  third of a block from an edge (§3.1: a Minecraft fact, and one we do not currently model), so the
  acceptable drift must be comfortably under that. If flat velocity is near zero and you are below
  the target, keep jumping. Below the origin height, fail.
- **Jumping gaps.** Falling below origin height means immediate failure. Jumping *too late* is a
  genuine failure mode at the longest spans — the jump must be delayed until you have travelled a
  certain fraction across the origin block. If you end up behind the origin, release sprint, walk
  back to a run-up position, and re-approach. Mid-air placement under the landing spot must prefer
  *downward* placement over sideways, because turning to the side while airborne perturbs the
  trajectory.
- **Bridging out over a gap (sneak-back-place)** is the most delicate movement in the set. Sneak is
  mandatory or you fall. Two learned corrections: if you get *too close* to the face you are placing
  against you can no longer see it and must walk backwards slightly first; and if you are standing
  on soul sand or a slab — whose tops are 0.875 and 0.5 rather than 1.0 — your approach to the edge
  differs and you must back off further.
- **A block can be visible-for-breaking while sneaking but not while standing.** So a break that
  worked a moment ago stops working when the sneak is released; the sneak must be held deliberately
  through the break in that situation.
- **Ladders and vines poison forward motion.** Pressing forward while airborne beside a climbable
  block makes you grab and climb it instead of moving forward — so wait until grounded. And a
  climbable stops catching a fall from beyond about eleven blocks, so it cannot be relied on as
  fall arrest above that.
- **Diagonals.** Only sprint a diagonal if all four corner columns are clear; the classic bug is
  cutting a corner, wedging against it, and never failing cleanly because you are still nominally
  progressing. If ascending diagonally while pressed against the lower wall, a jump is required.
- **Falls.** Landing on a bottom slab is glitchy and produces *more* damage than the height
  predicts — exclude slabs from landing candidates. Staying centred over the landing column must
  use position **plus velocity**, not position alone.
- **Liquids.** You auto-jump at water surfaces, currents push continuously, and flowing water cannot
  be scooped. Consequently every "am I at the expected node" test must tolerate being one block
  above the expected node while in liquid.
- **Getting stuck inside terrain.** A bot *will* end up with its collision volume intersecting
  blocks. It needs an unconditional escape hatch — break whatever you are looking at.
- **An obstruction with no reachable face.** Fall back to aiming at the block's centre and swinging;
  if even that does not apply, declare the edge unreachable. Without this the bot hangs
  indefinitely, aiming at nothing.
- **Doors and gates.** Openability is orientation- *and* facing-dependent, so the answer changes as
  the player turns.
- **The world border.** The search will happily propose positions outside it, which are unreachable.
  Any edge that changes horizontal position must be border-checked.

**Search/reality mismatch**

- **Orphan results.** Because the search runs while the body moves, a finished plan can begin
  somewhere you no longer are. Validate every result at the moment of adoption, against your current
  position *or* a position snapshotted at the top of the tick, and discard it with a warning
  otherwise.
- **Pause when the emerging plan doubles back.** While a replacement is being computed, its best
  partial may pass back through where you stand; walking forward is motion you will have to undo.
  Only pause under a conjunction: grounded, on walkable floor, not suffocating, the current edge
  reports itself interruptible, and the partial is long enough to be credible.
- **Abandonment must not be reported as failure.** Behaviours treat "planning failed" as a serious
  signal — blacklist a target, give up, tell the user. Conflating ordinary replanning with genuine
  failure makes them abort constantly.
- **Plan instability looks like indecision.** A fresh search from a slightly different position
  naturally yields a visibly different route, so the bot appears to change its mind every few
  seconds. Discounting the cost of re-using the previous plan's edges is the mitigation, and it
  needs an explicit "off".
- **Node identity is a real bug surface.** Nodes keyed by a packed integer coordinate: a hash
  collision or a wrong equality silently corrupts the plan.

**Interaction with the rest of the client**

- **Clear and re-assert held inputs every tick.** Leaving a key held across a state change causes
  drift. Sprint is a special case: releasing the sprint *input* does not stop you sprinting.
- **Explicitly stop an in-progress break on cancellation**, or the client swings forever.
- **Rotation is quantised on the wire, so an exact comparison never succeeds.** Gate every break and
  place on either the ray-cast actually hitting the intended block *or* the rotation being within a
  tolerance.
- **The rotation the server believes you have is a distinct value from the one the client shows** if
  you ever decouple them, and the server only accepts sprinting in the direction you are facing.
  Every reachability, aim and "am I looking at it" test must use the server-side value.
- **Sneak-right-click is how you place *against* a block.** Without the sneak you open the chest or
  crafting table you meant to place against, and in this client sneak reaches the server **only**
  via `SetPlayerInput` (§3.6) — it is never inferred from the movement packet.
- **Inventory rearrangement is not instantaneous** and needs the body genuinely stationary for more
  than one tick; execution must pause while it happens.
- **Vanilla imposes a cooldown between finishing one break and starting the next**, and a right-click
  shortly after a left-click can be swallowed. Both need explicit waits.

**Long journeys**

- **Plan the continuation before the current segment ends** — with one non-obvious detail: the
  "time remaining" estimate that triggers the look-ahead must **exclude the currently executing
  edge**. Include it and a single long edge (a big descent) keeps the estimate above the trigger
  until it completes, so the look-ahead never fires and you stall at the boundary anyway.
- **Concatenating two segments is only valid when the first ends exactly where the second begins
  *and* they share no other position.** An overlap creates a doubling-back plan, violating
  well-formedness and breaking index recovery.
- **Trim the travelled prefix periodically.** On a long journey the plan grows without bound and the
  per-tick scans over it dominate. Trimming means shifting every index and per-edge counter
  consistently — an easy source of off-by-one bugs.
- **Two different time budgets.** The *first* segment must appear fast so the bot sets off promptly:
  a short deadline once something acceptable exists, and a longer grace that applies only while
  nothing usable has been found at all. A pre-planned continuation can afford much longer, because
  you are already walking.
- **Make the replanning decisions *after* the tick's movement has been applied**, so the gap between
  ticks is available as compute budget. Front-loading them halves the effective movement rate. This
  changes the schedule in §5.2 and is the kind of thing that is obvious only in hindsight.

**Arbitration**

- **A behaviour that wanted control and did not get it must be told**, or it later resumes from a
  stale half-finished plan.
- **Brief interruption and losing control are different events.** A pause to eat or move items must
  be able to seize the body for a tick or two *without* destroying the interrupted behaviour's
  state. Conflating them resets every long-running task at every interruption.
- **A behaviour must be able to say "I am active but have nothing to say this tick."** That is what
  makes a permanently-registered, cheap, top-priority interrupter possible.
- **Any status or HUD surface will be queried one tick later than you expect**, after the fields it
  depends on have been cleared. Guard it.
- **Stopping has more than one meaning**: abandon the current plan; abandon the plan *and* all
  behaviours and goals; and abandon the plan and the in-flight search but deliberately *keep* the
  held inputs, for an immediate replan with no visible stutter. All of them must wait until the body
  is interruptible — you cannot abort mid-jump or mid-sneak over a drop.
- **Goal invalidation has a precise useful predicate**: "this plan used to end inside the goal and
  no longer does." Mere goal inequality is the wrong test, because a behaviour that recomputes its
  goal from a live scan every tick produces a nominally-new goal object constantly and would replan
  forever.

## 3. What this client already has, and what is missing

Grounded in the tree at the time of writing. This section is why the plan is tractable —
substantially more exists than one would guess, and one crucial thing does not.

### 3.1 `lodestone-physics` is strong, and it is the right foundation

[`crates/lodestone-physics`](../crates/lodestone-physics) has **zero runtime dependencies** and
exposes exactly what a navigator needs:

- `tick(&mut PlayerState, MovementInput, &dyn CollisionView, &PhysicsProfile)` and its
  `tick_air` / `tick_water` / `tick_lava` / `tick_elytra` arms
  ([`player.rs`](../crates/lodestone-physics/src/player.rs)).
- `MovementInput { forward: f32, strafe: f32, jump: bool, sneak: bool, sprint: bool }`
  ([`player.rs:39`](../crates/lodestone-physics/src/player.rs)) — **the same input a human
  produces.** This is what the executor should target, and it is what makes the cost model
  meaningful.
- `PlayerState { position, velocity, yaw, pitch, on_ground, horizontal_collision, no_jump_delay,
  sprinting, fall_flying, effects }`.
- `PhysicsProfile::mc_1_21()`
  ([`profile.rs:140`](../crates/lodestone-physics/src/profile.rs)) — the constants, each cited to
  vanilla by name and each confirmed against `.cache/mc/26.2/src`:
  `base_movement_speed 0.1` (`Player.createAttributes`), `sprint_speed_modifier 0.3`
  (`LivingEntity.SPEED_MODIFIER_SPRINTING`, `ADD_MULTIPLIED_TOTAL`), `sneaking_speed 0.3`,
  `gravity 0.08`, `air_drag 0.91`, `vertical_air_drag 0.98`, `ground_accel 0.216_000_02`,
  `flying_speed 0.02`, `jump_power 0.42` (`Attributes.JUMP_STRENGTH`), `sprint_jump_boost 0.2` —
  an `f64` deliberately, because storing vanilla's `double` literal as `f32` drifts Z by ~3e-9 per
  jump. **This is where movement constants come from. Do not re-derive them and do not hardcode a
  blocks-per-second figure anywhere.**
- `EntityDimensions::PLAYER = { width 0.6, height 1.8, step_height 0.6 }`
  ([`entity.rs:79`](../crates/lodestone-physics/src/entity.rs)). Confirmed: 26.2's player does not
  override `maxUpStep()`; step height is the `STEP_HEIGHT` attribute, default 0.6.
- `CollisionView` ([`collision.rs:25`](../crates/lodestone-physics/src/collision.rs)) — the world
  seam, per block cell: `collision_boxes`, `collision_top` (**deliberately uncapped** — fences
  return 1.5, and its doc comment explains why in terms of a pathfinder's step-up check),
  `friction`, `speed_factor`, `jump_factor`, `is_water`, `is_lava`, `is_climbable`,
  `stuck_multiplier`, `fluid_at`, `blocks_motion`, `bounce_restitution`.

Modelled and verified: swept AABB collision in vanilla's axis-step order; real
`collectCandidateStepUpHeights` enumeration rather than a naive 0.6 lift (and it picks the
*lowest* workable step, as vanilla does); ice friction; block speed factor; jump factor; the
sprint-jump boost; slime and bed bounce with the sneak-cancels-bounce rule; ladders and vines
including the sneak-hold; cobweb, powder snow and sweet berry via `stuck_multiplier` with vanilla's
one-tick lag; water and lava travel; the swimming-pose state machine; fluid flow push with per-cell
levels; elytra; and the movement status effects.

**Verified how**, which matters for §6: `tests/support/golden_traces.rs` is 585 KB of raw `f64` bit
patterns generated by an *independent* Python re-implementation, replayed **bit-for-bit with no
tolerance** across 26 scenarios including `SPRINT_JUMP`, `ICE_SLIDE`, `BLUE_ICE_SLIDE`, `SLAB_STEP`,
`LADDER_CLIMB`, `LADDER_SNEAK_HOLD`, `SOUL_SAND_WALK`, `HONEY_JUMP`, `SLIME_BOUNCE`,
`WATER_CURRENT_PUSH`; and `oracle-java/MoveOracle.java` diffs a real JVM against the same traces,
so JVM ≡ golden ≡ Rust.

**Not modelled, and two of these matter a great deal:**

| ~~**`maybeBackOffFromEdge`** — zero occurrences in the tree~~ **CLOSED** — fully modelled with golden traces, see [`edge-back-off.md`](./edge-back-off.md) | was **a likely desync source, not just a feel issue.** The box below explains why, and the reasoning still stands |
| **`isHorizontalCollisionMinor`** — zero occurrences | vanilla's *client* keeps sprinting through a collision within ~8° of the desired direction (`client-src/.../LocalPlayer.java`). Low priority; note it so nobody "fixes" it into a desync |

| 1.8 input pipeline and fluids | `unimplemented!()` behind `InputModel::LegacyMoveFlying` / `FluidModel::Legacy1_8`, so they fail loudly. Navigation is **v770-only**, matching the repo's active scope |
| a bulk "colliders overlapping this AABB" query | `gather_colliders` is private; per-cell calls are the only public route, and §4.4 calls physics thousands of times |

> **The `maybeBackOffFromEdge` finding, stated separately because it is the sharpest one in this
> section.** In 26.2, `Player.maybeBackOffFromEdge` (`.cache/mc/26.2/src/.../player/Player.java`)
> prevents you walking off a ledge while sneaking: gated on shift-held, not-flying,
> `delta.y <= 0`, mover type `SELF` **or `PLAYER`**, and above-ground, it walks the horizontal
> delta toward zero in 0.05 steps while a probe box (shrunk by 1e-7, lowered by the 0.6 step
> height) would still fall. The server's movement handler replays our reported delta through
> `player.move(MoverType.PLAYER, …)` — the very mover type that gate admits — and then compares
> the result against the position we claimed, rubber-banding on a squared error above 0.0625
> (§3.2). **So if we do not model the back-off and the bot sneaks near an edge, our claimed
> position is past where the server's replay puts us, and we get corrected.** Sneaking near an
> edge is exactly what a bridging or sneak-placing bot does constantly.
>
> Confidence: **high that this is a real desync source, moderate on the exact mechanism** — it
> rests on the server's replay reaching the back-off through mover type `PLAYER`. Verify two ways
> before M5: read the call site of `maybeBackOffFromEdge` in `Entity.move` and confirm the server
> path reaches it; and empirically, sneak off a ledge on the oracle and watch the correction
> counter. If confirmed, implementing it in `lodestone-physics` (with a golden trace) is a
> prerequisite for M5, not a nicety.

### 3.2 The honest parity verdict, and the number the server actually enforces

**The library is faithful. The world adapter feeding it is not.** This inverts the obvious
expectation and it is the most important finding here.

`crates/lodestone-shell/src/collision.rs` is what actually runs. `LiveCollision` — the live
multiplayer view — implements **three** of `CollisionView`'s twelve methods: `collision_boxes`,
`is_water`, `is_lava`. And `collision_boxes` emits a unit cube **if and only if the renderer's
atlas says the state is a full opaque cube** (`atlas.classify(id,0,0).occludes`). Its own module
doc admits it: *"a known v1 limitation — partial blocks like slabs and stairs — does not
[collide]"*.

So in the running client today:

- **slabs, stairs, fences, walls, panes, carpets, farmland, snow layers, chests, soul sand's 0.875
  top — no collision at all.** You walk through a fence and fall through a slab.
- `friction` is 0.6 everywhere: **no ice** (real values: ice and packed ice 0.98, blue ice 0.989,
  slime 0.8 — `.cache/mc/26.2/src/.../block/Blocks.java`).
- `speed_factor` is 1.0 everywhere: **no soul sand or honey slowdown** (both 0.4).
- `jump_factor` is 1.0: **honey does not shorten jumps** (0.5).
- `is_climbable` is false: **ladders and vines do not work.**
- `stuck_multiplier` is `None`: **no cobweb** (0.25, 0.05, 0.25), **no powder snow** (0.9, 1.5, 0.9),
  no berry bush (0.8, 0.75, 0.8).
- `fluid_at` is `None`: a fluid cell is full height rather than `amount/9` (already on
  [`docs/backlog.md`](./backlog.md)).
- `bounce_restitution` is 0.0: **no slime blocks** (1.0) or beds (0.75).

**How much disagreement does the server actually tolerate?** From
`.cache/mc/26.2/src/net/minecraft/server/network/ServerGamePacketListenerImpl.java`'s movement
handler, two independent checks:

1. **A speed cap** — squared distance moved minus expected squared delta above `100.0` per packet
   per tick (300 while elytra-flying) logs "moved too quickly" and teleports. That is 10 blocks per
   tick. **Not the binding constraint** for anything a walking bot does.
2. **A physics-agreement check, and this is the one that matters.** The server replays our reported
   delta through `player.move(MoverType.PLAYER, …)`, then compares its own result against the
   position we claimed. Squared error above **`0.0625` — i.e. 0.25 blocks — is "moved wrongly"**
   and rubber-bands us (subject to the old box actually having been free). It is **per packet, with
   no multi-tick accumulator**, and — a quirk worth knowing — the vertical component is discarded by
   an always-true condition, so in 26.2 only horizontal disagreement is checked.

**That 0.25 blocks is the parity bar.** It is not a path-following tolerance, it is a *physics
agreement* tolerance: every tick, our integrator must land within a quarter block of where the
server's own `move()` lands given the same delta. That is a demanding but very achievable bar for a
bit-exact integrator — and an impossible one for an integrator fed a world where slabs do not
exist.

Two more server behaviours a navigator must respect:

- **The server synthesises your jump.** If it sees you on ground, your packet says not-on-ground,
  and `y` increased, it calls `jumpFromGround()` itself. So the `on_ground` flag in our `Move`
  action is load-bearing, not decorative.
- **The floating kick.** ~80 ticks (4 s at normal gravity) of not standing on anything, without
  flight or levitation and with no blocks nearby, is a disconnect. Relevant to long falls and to any
  bot that manages to hover.
- **The teleport handshake.** A corrective teleport is re-sent every 20 ticks until the client
  confirms, and until then **all movement packets are ignored** (rotation only). So after a
  correction we must confirm promptly or we are frozen while appearing to move.

**Verdict.** Confidence, stated so it can be held against reality later:

- **High** that parity is achievable: the hard part (the integrator) is done and independently
  pinned, and the bar (0.25 blocks per tick, horizontal) is well within a bit-exact integrator's
  reach.
- **High** that it is *not currently achieved*: the live adapter demonstrably answers three
  questions out of twelve, and it is wrong in the dangerous direction (routes through fences, falls
  through slabs).
- **Moderate** that wiring the shapes is sufficient. The two residual risks are
  `maybeBackOffFromEdge` (§3.1, and it *is* a desync source if the box above is right) and per-cell
  fluid height. Neither is on the critical path for M1–M3; the first is on the critical path for M5.

**And one trap that is exactly the repo's "world species" of vacuous test.** Both shell collision
adapters — `WorldCollision` (demo) and `LiveCollision` (live) — are coarse *in the same way*. A
cost or legality rule that depends on slab, stair, fence, ice or ladder geometry can be verified
against every scene currently in the tree and pass while meaning nothing. **There is no scene in
this repo today that structurally exercises partial-block collision.** Building one is a
prerequisite (§6).

### 3.3 The version-data tables already exist. Most of them are unreachable.

All generated by booting the real 26.2 server headlessly and interrogating it — this repo's
preferred data source, and the right one:

| table | where | shape | reachable via `VersionAdapter`? |
|---|---|---|---|
| **collision shapes** | [`crates/protocol/v770/src/collision_shapes.rs`](../crates/protocol/v770/src/collision_shapes.rs) | `STATE_SHAPE: [u16; 32_366]` → `SHAPES: [&[Aabb]; 326]` → 716 dedup'd boxes; ~90 KiB rodata, zero heap, O(1) by **state** id | ❌ no method |

those variants are in *mob-node* units, not ticks (negative means impassable; water is 8, fire 16,

### 3.4 There is already an A\* pathfinder in this tree, and this plan does **not** extend it

[`crates/lodestone-entity/src/pathfinding/`](../crates/lodestone-entity/src/pathfinding) is 1,862
lines implementing vanilla's *mob* navigation: A\* over an arena plus a decrease-key binary heap,
vanilla's `PathType` malus table, the `WalkNodeEvaluator` neighbour rules (per-mob width and
height, step-up, drop-down, water), and a path plus navigator that can stall and fail. Its world
seam is `PathWorld`, deliberately a trait so nothing there names a version crate. It is
**consumed** — by `lodestone-server`'s mob AI — and gated against a live oracle
(`crates/lodestone-entity/tests/live_navigation.rs`, `live_oracle.rs`).

**Do not extend it.** Two reasons, both from this repo's own rules:

1. It is pinned by an external oracle for a *different* purpose. Vanilla mob navigation has its own
   semantics — integer costs in malus units, a 1.125-block jump height, no block modification, no
   momentum, mob bounding boxes. Bending it toward player movement destroys the oracle relationship
   that makes it trustworthy, exactly as [`docs/bevy-migration.md`](./bevy-migration.md) §8 argues
   for `lodestone-physics`.
2. The requirements barely overlap. A player navigator needs tick-valued costs, momentum, breaking,
   placing, segmentation and an anytime search. A mob navigator needs none of those.

**Do** take three things from it: the arena-plus-index-heap shape (proven and testable here), the
`PathWorld`-as-trait discipline, and the `PathType` vocabulary. And read its warning that
`collision_top` is uncapped — the same trap, documented independently twice.

### 3.5 The off-thread-snapshot pattern already exists and is the right one

The section mesher states the rule absolutely
([`crates/lodestone-shell/src/mesher.rs:1-20`](../crates/lodestone-shell/src/mesher.rs)): *"the
world is never locked while meshing."* Two phases — on the owning thread, clone the neighbourhood
into an owned `Send` snapshot; on a worker, mesh it with no world access at all.

The primitives:

- `lodestone_world::World` has **no** interior mutability; the lock is one level up
  (`Arc<std::sync::RwLock<World>>`, [`state.rs:230`](../crates/lodestone-client/src/state.rs)).
- Sections are `Arc<ChunkSection>` with **copy-on-write at section granularity** —
  `ChunkColumn::set_block` uses `Arc::make_mut`, forking only the touched section. A held `Arc`
  therefore **cannot** change under a reader.
- `ClientHandle::sections_at(&[(ChunkPos, usize)]) -> Vec<Option<Arc<ChunkSection>>>` is a
  **batched, single-lock-acquisition** snapshot read.
- `Sim::live_collision()` ([`sim.rs`](../crates/lodestone-shell/src/sim.rs)) is the working example:
  3×3 columns × every section, one lock, per tick, handed to `LiveCollision`.

> **Cite `sim.rs` by symbol, never by line.** It is 3,950 lines, under concurrent edit, and Stage 5
> of the bevy migration deletes it. Line numbers in this document were deliberately removed after
> two of them went stale *within this session* — `docs/bevy-migration.md`'s `sim.rs` references are
> already off by ~50 lines for the same reason. Grep for the symbol.
- A single block-state read is a `HashMap` lookup, a `Vec` index and a paletted-container read (one
  div, mod, shift, mask) — single-digit nanoseconds, no allocation. Hoist the section in hot loops;
  the hash dominates.

**This is exactly the shape the search needs.** §5's design is not new infrastructure; it is the
mesher's pattern with a bigger region and a different worker.

### 3.6 The egress is complete

`lodestone_model::ClientAction` ([`action.rs`](../crates/lodestone-model/src/action.rs)) already
carries everything:

- `Move { pos, rotation, on_ground, horizontal_collision }` — position *and* look in one action,
  built by `lodestone_controller::action::move_action(&PlayerState)`, sent every tick. **The client
  decides its own position**; the bot's authority is entirely "run physics with chosen inputs, then
  report".
- `SetPlayerInput(PlayerInput { forward, backward, left, right, jump, shift, sprint })` — the
  digital key state. `Sim::send_player_input`'s doc comment records that this is **the only way the
  server learns you are sneaking** — it never infers shift from the movement packet.
- `PlayerCommand { StartSprinting | StopSprinting | … }`.
- `BlockAction { action: StartDestroy|AbortDestroy|StopDestroy, pos, face, sequence }` — the
  `sequence` is the block-prediction number and must be threaded, never synthesised.
- `UseItemOn { hand, pos, face, cursor, inside_block, sequence }`, `UseItem`, `SwingArm`.
- `SetCarriedItem { slot }` for hotbar selection.

The ingress side has what a navigator must observe: `TeleportPlayer`, `HealthChanged`,
`MobEffectApplied`/`Removed` (Haste, Speed, Jump Boost), `AbilitiesChanged`,
`ChunkLoaded`/`ChunkUnloaded`/`SectionBlocksChanged`/`BlockChangedAck`, `EntityAttributesUpdated`
(`MOVEMENT_SPEED`, `STEP_HEIGHT`), `SimulationDistanceChanged`.

### 3.7 What is genuinely missing

1. A live `CollisionView` that answers more than three questions (§3.2) — **the blocker**.
2. A `VersionAdapter` route to collision shapes, path types and block properties (§7.5).
3. A bulk "colliders overlapping this AABB" query.
4. `maybeBackOffFromEdge` (§3.1 — likely a desync source, prerequisite for M5).
5. An **analog** movement-intent injection point. `Sim::physics_tick` is private and `Sim.input` is
   `lodestone_controller::InputState`, which collapses to ±1.0 axes and carries its own 7-tick
   double-tap sprint latch. Good enough to demo, not to steer.
6. A world-space debug-geometry channel. There is a single-box block-outline pipeline in `gpu.rs`
   and nothing general.
7. `tool_mining` wired into break-time math (an existing island).

## 4. The design

### 4.0 Two crates, and why the split is where it is

`lodestone-nav` is a plain library because **it is the part that can have an external oracle.** The
repo's rule is "anything with an external oracle stays a library the ECS calls"
([`docs/bevy-migration.md`](./bevy-migration.md) §8), and the search core can be gated headlessly
against captured real chunk regions and against a live server. Putting it in a plugin would put a
schedule between the oracle and the code it validates.

`lodestone-autopilot` is the bevy plugin because scheduling, arbitration and the per-tick executor
are what an ECS is for — and because the requirement is that this be a plugin.

The boundary is hard: **`lodestone-nav` knows nothing about bevy, about `Entity`, about
`ClientAction`, or about threads.** It is `(snapshot, start, goal, policy, budget) → plan`, plus
"given a plan edge and a `PlayerState`, what keys do I press this tick". Everything else is the
plugin's problem. That is what makes the search testable and the plugin thin.

### 4.1 Units and determinism: fixed-point ticks

**Cost unit: ticks, in 1/256ths, as a `u32`.**

```
pub struct Ticks(u32);   // 1 tick == 256; COST_MAX is the "impossible" sentinel
```

Ticks because the executor spends ticks and the physics library is per-tick, so every cost is
directly measurable and directly falsifiable. Fixed-point because **a search whose priority queue
orders floats is not reproducible**: equal-cost ties resolve by accumulation order, which changes
with expansion order, which changes with hash iteration. This repo tests things — make the search
deterministic by construction. 1/256 tick is ~0.2 ms of game time, finer than any real cost
difference, and `u32` spans ~9.7 days with saturating addition so an impossible edge cannot
overflow into a cheap one.

Total order in the open set: `(f, then u32::MAX - g, then insertion_sequence)`. Ties break toward
**larger g** — deeper into the graph, closer to something — then by insertion order. Fully
deterministic, and the g-tie-break is what stops flat terrain degenerating into breadth-first.

One related quality choice, worth stating because floating-point noise otherwise decides it: a
diagonal step's cost should be set a hair **below** √2 times a straight step, so a diagonal wins
ties against two axis moves. Otherwise routes over flat ground zigzag arbitrarily and look erratic
even though the cost is identical.

### 4.2 The world view: `NavView`

```
pub trait NavView {
    fn state_at(&self, x: i32, y: i32, z: i32) -> Option<u32>; // None == outside the snapshot
    fn min_y(&self) -> i32;
    fn max_y(&self) -> i32;
}
```

`state_at` returning `Option` is load-bearing: **"outside the snapshot" is a distinct answer from
"air"**, and conflating them is how a search invents terrain — producing a beautiful path into
unloaded chunks. Every legality rule treats `None` as *illegal*, which is precisely the mechanism
that terminates a search at the edge of known world (§4.6).

On top of `NavView`, resolve each state id once per session into a flat table indexed by state id —
32,366 entries of a few bytes, which removes the version call from the inner loop entirely:

```
struct BlockFacts {                  // one per block state, precomputed
    path_type: PathType,             // lodestone_model::PathType
    top: f32,                        // collision_top, UNCAPPED — fences are 1.5
    full_cube: bool,
    passable: bool,                  // no collision boxes at all
    friction: f32, speed_factor: f32, jump_factor: f32,
    climbable: bool, water: bool, lava: bool,
    hardness: Option<f32>, requires_correct_tool: bool,
    gravity_affected: bool,          // sand/gravel family — break cost is non-local
    danger: Danger,                  // must-not-enter and cost-to-be-near
}
```

The concrete implementation, `SnapshotView`, owns `HashMap<(i32,i32,usize), Arc<ChunkSection>>`
exactly as `LiveCollision` does (§3.5) — owned, no lock, `Send`. And because cost derivation needs
to feed `lodestone_physics::tick` (§4.4), **`SnapshotView` also implements `CollisionView` — all
twelve methods, properly, backed by `BlockFacts`.** That single type is therefore both the search's
world and a correct physics world, which is what makes it impossible for the cost model and the
executor to see different terrain.

Add the bulk query while you are here: `fn colliders_in(&self, region: Aabb, out: &mut Vec<Aabb>)`.
The per-cell path costs ~27 virtual calls per physics substep and cost derivation calls physics
thousands of times.

**Snapshot geometry.** A square of columns centred on the player, radius `snapshot_radius` (default
**12** ⇒ 25×25), clipped to loaded columns, all sections. ~15,000 `Arc` clones — pointer bumps
under one lock, comparable to what the mesher already does per frame. It bounds a search to ~200
blocks of reach, far more than one segment needs.

### 4.3 The movement graph: nodes carry arrival state

```
struct NavNode { x: i32, y: i32, z: i32, arrival: Arrival }
enum Arrival { Still, Walking(Dir4), Sprinting(Dir4) }   // 1 + 4 + 4 = 9
```

The node is the block cell the player's **feet** occupy, plus how they got there. §2.2(4) is why:
whether a gap is crossable, and how long a straight run takes, are both functions of entry
velocity. The numbers make it concrete. Derived from our own `PhysicsProfile` constants:

| motion | blocks/tick | blocks/s | ticks per block |
|---|---|---|---|
| walk | 0.21586 | 4.317 | 4.633 |
| sprint | 0.28062 | 5.612 | 3.564 |
| sneak | 0.06476 | 1.295 | 15.4 |
| sprint on blue ice (friction 0.989) | 0.28444 | 5.689 | 3.515 |
| climb a ladder up | 0.2 | 4.0 | 5.0 |
| descend a ladder (capped) | 0.15 | 3.0 | 6.67 |
| swim | 0.098 | 1.96 | 20.4 |
| sprint-swim | 0.196 | 3.92 | 10.2 |

And the jump, integrated from `gravity 0.08` with `vertical_air_drag 0.98` applied after the move:

- vertical velocity 0.42 on tick 1, first above y = 1.0 during tick 3, **apex 1.2522 blocks at tick
  6**, landing during tick 12 — so a flat-ground jump is ~12 airborne ticks.
- 1.2522 is why a 1-block step-up clears and a 1.5-block one (fence, two slabs) does not, and it
  is the number that decides `StepUp` legality rather than a rule of thumb.
- A sprint jump (steady 0.28062 b/t plus the one-shot 0.2 facing boost, with 0.026 air control and
  0.91 horizontal drag per tick) covers ~1.46 blocks by tick 3, ~2.77 by tick 6, and **~4.7–5.1
  blocks by landing** — which is what makes gaps of up to 4 cells the right range for `Gap` and a
  5-cell gap the right thing to refuse.

**The cost of the arrival dimension, stated honestly:** 9× the state space. At the default budget
(§4.6) that is 9 × 20,000 potential slots × ~40 bytes ≈ 7 MB worst case, from a preallocated arena
reused across searches, so it is a one-time allocation rather than churn. The heap stays small
because most arrival variants at a given cell are never reached. If profiling disagrees, the
collapse is local: drop `Sprinting` and treat sprint as a post-pass, losing momentum-gated jumps.

**Movement kinds (edges).** Direction is a parameter, not a separate type:

| kind | describes | milestone |
|---|---|---|
| `Walk(Dir4)` | step to an orthogonal neighbour whose **surface** is within `step_height` (0.6), up or down — this is what makes slabs, soul sand (0.875 top) and farmland work. Note the bound is on the surface, **not** on the cell index: because the feet cell is `floor(feet y)`, a 0.125 step between a stone floor (surface = cell floor) and a soul-sand floor (surface = cell floor + 0.875) changes `y` by one. Reading "same cell height" as a constraint on `y` is what made `graph::walk_step` refuse every soul-sand column in both directions | M1 |
| `WalkDiagonal(Dir4, Dir4)` | 1,1 step; requires **both** intermediate cells clear at both body heights (§2.3) | M2 |
| `StepUp(Dir4)` | +1 Y; requires a jump, since 1.0 > 0.6 | M2 |
| `Descend(Dir4)` | −1 Y onto solid ground; brake-vs-sprint decision per §2.3 | M2 |
| `Drop(Dir4, n)` | fall n > 1 blocks onto solid ground; legality from damage vs health | M2 |
| `Climb(Up\|Down)` | ladder/vine column, plus mounting and dismounting | M2 |
| `Gap(Dir4, n)` | jump a horizontal gap of n ∈ 1..=4; legal only from a compatible `Arrival` | M3 |
| `Break(target, then)` | mine one block, then perform `then` | M4 |
| `Place(target, then)` | place one block, then perform `then` | M5 |
| `Swim(Dir6)` | movement inside water, including surfacing | M7 |

`Break` and `Place` composing over another kind — rather than every kind growing a
break-if-needed variant — keeps the kind set small and makes cost additive and obviously correct.
It costs a little optimality (the search expands the break node separately) and buys a great deal
of clarity. Take the clarity.

### 4.4 Costs and input scripts derived by simulation, not by formula

**This is the design's central idea.** Every movement kind is defined by an **input script** — a
short program producing `MovementInput` per tick from a phase and the current `PlayerState`. The
cost of that movement is obtained by **running `lodestone_physics::tick` with that script** over a
synthetic stencil world and counting ticks.

```
trait MoveKind {
    /// Cells this movement's legality predicate reads. Static, so it can be
    /// translated and unioned after the fact (§4.5).
    fn stencil(&self) -> &[IVec3];
    fn legal(&self, v: &dyn NavView, facts: &FactsTable, from: NavNode) -> Legality;
    fn script(&self) -> &'static InputScript;
    fn exit_arrival(&self) -> Arrival;
}
```

**Why this rather than cost formulas.** Four concrete wins:

1. **The cost is achievable by construction.** The number the search believes is the number the
   executor produced under the same inputs against the same physics. §2.2(1)'s coupling problem is
   solved by definition rather than by discipline.
2. **No transcribed constants.** `PhysicsProfile` is the only source of movement numbers, and it is
   already pinned by two independent oracles.
3. **It self-heals.** When §3.2's missing collision data lands, costs update automatically — in
   directions nobody anticipated (ice runs cheaper, honey jumps dearer) with no cost-table edit.
4. **One definition serves cost and execution.** The script *is* the executor's reference (§4.8).
   There is no second place for them to disagree.

**Making it fast enough.** Simulating per edge inside A\* is far too slow — a movement is 5–20
physics ticks, each with dozens of collider queries. So **memoise by equivalence class**:

```
struct TemplateKey {
    kind: MoveKindId,
    entry: Arrival,
    surface: SurfaceClass,   // friction bucket: 0.6 normal | 0.8 slime | 0.98 ice | 0.989 blue ice
    speed: SpeedClass,       // speed_factor bucket: 1.0 | 0.4 (soul sand, honey)
    fluid: FluidClass,       // none | water | lava
    effects: EffectClass,    // none | speed_n | jump_boost_n | slowness_n, coarse buckets
}
```

Built lazily into a `HashMap<TemplateKey, Template>` where
`Template = { ticks: Ticks, script: &'static InputScript, ok: bool }`. A few hundred reachable
keys, each one ≤20-tick simulation — sub-millisecond total, amortised across the session. **In the
A\* inner loop an edge cost is therefore: one array index for the surface's `BlockFacts`, build the
key, one hash lookup, add penalties.** Comparable to evaluating a formula, without having written
one.

Invalidate the table when status effects change class or the profile changes. Nothing else touches
it.

**Additive penalties are design choices, not measurements.** State what each trades:

| penalty | default | what it trades |
|---|---|---|
| `turn_penalty` | 0.5 tick per 45° of heading change | the executor really loses speed turning, and modelling it is what stops the search emitting zigzags that cost identically on paper. Raise for smoother paths, lower if the bot refuses reasonable detours |
| `jump_penalty` | 2 ticks | jumps are the least reliable class (§2.3). Raise to prefer walking around; set to 0 only after measuring your jump success rate |
| `gap_penalty` | 4 ticks per gap cell beyond the first | a failed 4-cell jump costs a fall and a replan; scale risk with span |
| `damage_cost` | 10 ticks per half-heart of expected damage | makes fall damage trade against time instead of being boolean. Legality is separate — see below |
| `break_overhead` | 10 ticks | aiming, approach, the stop/ack round-trip and vanilla's post-break cooldown, on top of the real break time. **Measure this in M4 and replace the guess** |
| `place_cost` | 20 ticks | discourages bridging when walking exists |
| `danger_cost` | lava-adjacent 200, fire 400, cactus 60, magma 80, powder snow 40, berry bush 20 | deterrents, not durations. Vanilla's own mob malus ordering (water 8, breach 4, fire 16, negative = impassable) is a useful sanity cross-check on the *relative* ordering |
| `unknown` | **illegal, not costly** | entering a cell outside the snapshot terminates a branch. The mechanism, not a penalty |

Penalties are added to the *edge*, so `h` must be computed with none of them (§4.6).

**Fall legality and damage, from the real rule.** In 26.2, damage is
`floor(fallDistance + 1e-6 − SAFE_FALL_DISTANCE)` with `SAFE_FALL_DISTANCE = 3.0` — so ≤3 blocks is
free and it is one half-heart per block beyond
(`.cache/mc/26.2/src/.../entity/LivingEntity.java`). Two corrections to plausible assumptions:

- **Jump Boost raises the safe distance** by `1.0 × (amplifier + 1)`, as an attribute modifier. So a
  bot with Jump Boost II may legally drop 6 blocks for free.
- **Feather Falling does *not*.** It is a damage-protection enchantment, not a distance modifier —
  it reduces the damage taken, never the height at which damage begins. A policy that extends
  `max_fall_blocks` for feather falling is wrong; extend `damage_cost` tolerance instead.

`Drop` is **forbidden** when expected damage ≥ current health − `health_margin` (default 6
half-hearts), and slabs are excluded from landing candidates entirely (§2.3).

**Break cost comes from real data, not a constant.** The vanilla rule is
`progress_per_tick = effective_tool_speed / hardness / (correct_tool ? 30 : 100)`, accumulated
until it reaches 1.0, where the effective speed folds in Efficiency (`level² + 1`, only when base
tool speed > 1.0), Haste/Conduit (`× (1 + 0.2·(amp+1))`), Mining Fatigue, the
`BLOCK_BREAK_SPEED` attribute, ÷5 for eye-in-water without Aqua Affinity, and ÷5 when not on
ground. This client already implements it:
`VersionAdapter::block_hardness` + `VersionAdapter::tool_mining` →
`lodestone_game::mining::BreakInputs` → `Mining::ticks_to_break()`, which replays the
accumulate-then-compare loop rather than dividing — bare-hand stone is **151** ticks, not the
textbook 150, and [`docs/block-break-timing.md`](./block-break-timing.md) says not to "correct" it.

Two traps that doc exists to record, restated because they are easy to reintroduce:
`BlockHardness::requires_correct_tool` is the *block's* flag and feeding it into
`BreakInputs::correct_tool` makes stone break 3.4× too fast — use `ToolMining::correct_tool`, which
is pre-folded. And `tool_mining` is an island today, so wiring it is M4's prerequisite.

Gravity-affected columns make break cost non-local: refuse them in M4 (§2.3), and add whole-column
cost in M5 only if it turns out to matter.

### 4.5 Legality reads are recorded: witness sets instead of revalidation

A committed plan depends on specific cells being what they were when the search ran. Re-validating
the whole remaining plan every tick is O(plan) per tick, forever, for an event that almost never
happens.

**Instead: record what was read, and check incoming block updates against it.**

Each `MoveKind::stencil()` statically declares the cells its legality predicate touches (≤ ~20,
plus the modified cell and its neighbours for `Break`/`Place`). When a plan is **committed**, walk
its edges once, translate each stencil, union into a `HashSet<u64>` of packed positions —
typically 1–2 k cells for a 100-edge plan. Then:

- on `SectionBlocksChanged` / `BlockChangedAck`, test each changed position for membership; a hit
  marks the plan stale;
- on `ChunkUnloaded`, test the column against the plan's remaining footprint; a hit **truncates**
  the plan at the last edge inside loaded world.

Cost: O(block updates), not O(plan) per tick.

**Do not record witnesses during the search** — only for the chosen plan. Recording in the inner
loop would add a hash insert per cell read per expanded node, which is exactly the wrong place to
spend. That asymmetry is why the stencil is *static*: a static stencil is free to translate and
union after the fact.

Two things the witness set does **not** replace, both from §2.3:

- **Per-edge cost re-verification** as each edge begins, with the three outcomes and the
  suppress-inflation-when-planned-against-real-chunks rule. A cell can be unchanged and the edge
  still more expensive (a mob in the way, a fluid level shift).
- **A look-ahead window** of the next few edges, so a hazard is detected before you are standing
  next to it.

And one thing to do exactly once: **re-validate the committed plan against the live world at commit
time.** The snapshot froze when the search started; updates during the search are not in it. One
pass over the edges costs microseconds and closes the hole honestly. If it fails, replan
immediately — never execute a plan you already know is stale.

### 4.6 The search: resumable, budgeted, weighted A\*, with an anytime partial

**Structure — resumable from day one.** A state machine, not a loop:

```
pub struct Search { /* arena, heap, view, goal, policy, stats */ }
impl Search {
    pub fn new(view: Arc<SnapshotView>, start: NavNode, goal: Box<dyn Goal>, policy: NavPolicy) -> Self;
    pub fn step(&mut self, budget: Budget) -> Progress;   // Working | Done(Outcome)
    pub fn frontier(&self) -> NavNode;                    // cheap, for the overlay
    pub fn best_partial(&self) -> Option<Plan>;           // immutable snapshot, never live structures
    pub fn stats(&self) -> SearchStats;
}
pub struct Budget { pub nodes: u32, pub deadline: Option<Instant> }
```

This is the most important structural decision after §4.4, because it makes §5's two drivers *one*
implementation. It also makes the search deterministically testable (run exactly N steps, assert
state) and makes cancellation free — stop calling `step`. Note `best_partial` must build an
immutable copy; handing out live internals to a reader on another thread is the obvious way to make
this unsound.

Two smaller contracts worth enforcing: a `Search` is **single-use** (calling `step` after `Done` is
a programmer error, not a silent no-op), and **exactly one search may be in flight** per navigator.
Both are cheap asserts that prevent confusing states.

**Open set.** An arena of nodes plus a binary min-heap of arena indices, with `heap_idx` stored on
the node so a cost improvement is a decrease-key rather than a re-insert or a linear scan — the
shape already proven in `crates/lodestone-entity/src/pathfinding/heap.rs`. Node lookup by position:
a `HashMap<u64, u32>` from packed `(x, y, z, arrival)` to arena index, with a fast hasher (the
default SipHash is measurable here). **Get the packing and the equality right** — §2.3 notes a
collision silently corrupts the plan, so unit-test the packing bijection directly.

**Minimum improvement threshold.** Over flat ground, mixtures of straight and diagonal edges
produce cost improvements on the order of 1e-16 in floating point — and even in fixed point, of a
single 1/256 tick. Propagating those repropagates half the graph for nothing. Require an
improvement of at least `min_improvement` (default **2/256 tick**) before re-opening a node.

**Heuristic.** In ticks, admissible, derived from our own data:

```
h(n) = octile_horizontal_distance(n, goal) * cheapest_ticks_per_block
     + ticks_per_block_up * max(0, goal.y - n.y)      // descent contributes 0
```

`cheapest_ticks_per_block` comes from the template table, not a literal. **And it must be deflated
by ~1.5%**, because the genuinely cheapest ground motion in the game is sprinting on blue ice at
0.28444 b/t (3.515 ticks/block) versus normal sprint at 0.28062 (3.564) — a 1.4% gap. Deflating the
normal-sprint rate by 1.5% restores strict admissibility everywhere, including ice, at a heuristic
cost too small to matter. This is a much better answer than the alternatives (using the ice rate
everywhere, which weakens `h` by the same amount but for a rare case; or accepting inadmissibility,
which was this document's first instinct and is unnecessary once you have the actual numbers).

**Weighted A\*.** `f = g + w·h`, `heuristic_weight` default **1.25**. One knob trading search time
against path quality, with a published bound: the returned path costs at most `w ×` optimal. At 1.0
it is exact and explores terrain that cannot help; at 1.25 it drives hard toward the goal, which is
also what makes the *partial* good.

**Termination — three outcomes (§2.1):**

- `Reached` — a popped node satisfies the goal.
- `BudgetExhausted` — nodes or deadline. Defaults: `search_budget_nodes` **20,000**;
  `first_segment_ms` **200** once something acceptable exists, with `first_segment_grace_ms`
  **1,500** that applies only while nothing usable has been found at all; `continuation_ms`
  **3,000** for a pre-planned continuation, which can afford to be slow because you are already
  walking. The two-tier deadline is from §2.3 and it is the difference between a bot that sets off
  promptly and one that appears to hang.
- `WorldExhausted` — the heap empties, or the frontier has been at the snapshot edge for
  `edge_of_world_strikes` consecutive expansions (default **50**). Normal, not an error.

**Deadline and cancellation are polled coarsely** — every 64 expansions — because reading the clock
is otherwise a measurable fraction of the search cost, and because there is no preemptive abort:
cancellation is a one-way flag the worker notices at the next check.

**Choosing the partial.** For the two non-`Reached` outcomes, return the expanded node with
**minimum `h`**, subject to being at least `min_progress` blocks of straight-line distance from the
start (default **5**). If nothing clears `min_progress`, **report failure honestly** — committing a
two-block plan produces visible dithering and no progress, and returning *something* makes the user
believe a route exists while the bot visibly does nothing.

Then **truncate the tail** (§2.3): drop the last `tail_discard` fraction (default **0.15**) of the
plan when it is longer than `tail_min_len` (default **20** edges) and does **not** reach the goal.
The far end is both the least-trustworthy part of a weighted search and the least-known world.

Why min-`h` and not a family of relaxation coefficients: with `w = 1.25` the search is already
goal-biased, so the min-`h` frontier node is by construction both close to the goal and reached by
a route the search liked. One knob with a known bound, one rule. **This is the weakest claim in the
document** and §10 says how to falsify it.

### 4.7 Goals

```
pub trait Goal: Send + Sync {
    fn heuristic(&self, x: i32, y: i32, z: i32) -> Ticks;  // MUST be admissible
    fn satisfied(&self, x: i32, y: i32, z: i32) -> bool;   // MUST imply heuristic == 0
}
```

Both contract lines are load-bearing: an inadmissible `heuristic` silently produces bad paths, and
a `satisfied` that does not imply `heuristic == 0` makes the search step past its own goal.
`debug_assert!` the implication inside the search — it is nearly free and it catches every
user-written goal bug at the point of use.

| goal | satisfied when | heuristic |
|---|---|---|
| `AtBlock(pos)` | feet cell == `pos` | full 3-D octile distance in ticks |
| `AtColumn(x, z)` | feet cell's x,z match, any Y | horizontal only, **zero vertical term** — which is what makes long-distance travel not care about terrain height it cannot know yet |
| `AtLevel(y)` | feet Y == y | vertical only |
| `Within(pos, r)` | 3-D distance ≤ r | `max(0, dist − r)` scaled |
| `NextTo(pos)` | feet cell is one of the six neighbours, or on top | `max(0, dist − 1)` scaled |
| `AnyOf(Vec<Goal>)` | any child satisfied | **min** over children — admissible iff every child is |
| `AwayFrom(pos, r)` | distance ≥ r | `max(0, r − dist)` scaled. Admissible *for the capped goal*; an uncapped "flee forever" goal has no admissible heuristic, which is why the cap is in the type rather than optional |

`AnyOf` is what makes "go to the nearest iron ore" one search rather than N — the mining behaviour
builds it from every candidate it knows and the search picks the cheapest automatically. It is the
highest-leverage goal in the set, and §10 flags its scaling risk.

**Goal simplification at range** (§2.3): for a positional goal in an unloaded region the Y
component is unknowable, so effort spent optimising it is wasted. Rewrite `AtBlock` as `AtColumn`
while the target column is outside the snapshot, and restore the Y term once it is loaded. This is
a behaviour-level transform, not a search-level one.

### 4.8 The executor: closed-loop, with a reference trajectory

The executor runs in `GameTick` and produces one `MovementInput` plus a look direction per tick. It
is **closed-loop**: it does not replay a fixed input sequence, it steers.

Per edge, on entry:

1. Simulate the edge's input script from the player's **actual** current `PlayerState` against the
   **live** `CollisionView`, producing a reference trajectory — ≤ ~25 `PlayerState`s. Cheap, and it
   is the same code that produced the cost.
2. Derive `reference_ticks` and a **corridor** — the union of the reference's player AABBs,
   expanded by `corridor_slack`.
3. **Capture the stall budget now**, from `reference_ticks`, and never recompute it (§2.3 — this is
   the rule that keeps a break-then-move edge from digging forever).

Per tick:

4. Emit the script's `MovementInput` for the current phase, **but compute yaw from the current
   position**, not from the reference: aim at the phase's steering target — the far edge of the
   source cell while accelerating, the destination cell's centre once committed, and *back toward
   the origin* when the descent-overshoot rule (§2.3) says brake. This split — **the script owns
   which keys, the controller owns where you look** — is the closed loop, and it absorbs the small
   errors that otherwise compound into overshoot.
5. **Clear and re-assert every held input each tick**, and remember that releasing the sprint input
   does not stop sprinting — sprint state must be cleared explicitly (§2.3).
6. Sprint from the plan's **lookahead**, not from the script alone: sprint only if the next
   `sprint_lookahead` edges (default **2**) are collinear `Walk`s or a compatible `Gap`, and never
   when the descent-overshoot rule applies.
7. Maintain the **edge index** by the recovery scans of §2.3 — backwards over completed edges, and
   forwards but skipping the immediately-next one or two — against each edge's declared *set* of
   valid positions, resetting the internal state of every edge skipped over.

Abort conditions, each with a distinct reason so diagnostics are useful:

| condition | reason | response |
|---|---|---|
| the player AABB leaves the corridor by more than `drift_hard` | `OffCourse` | replan now |
| drift beyond `drift_soft` for `drift_patience` consecutive ticks | `Drifting` | replan. Measured to the nearest valid position **anywhere in the plan**, and **horizontally only** while falling (§2.3) |
| ticks > the captured stall budget × `stall_multiplier` + `stall_grace` | `Stalled` | replan; count consecutive stalls |
| the correction counter increased (§3.2, §7.9) | `ServerDisagreed` | replan from the **server's** position, and confirm the teleport promptly or movement packets are ignored |
| plan marked stale by §4.5 | `WorldChanged` | replan |
| this edge's re-verified cost is impossible, or inflated past `inflation_tolerance` | `EdgeInvalid` | replan (inflation check suppressed if planned against loaded chunks) |
| health below `panic_health` | `Danger` | yield to the safety behaviour (§4.10) |
| the body's collision volume intersects blocks | `Encased` | escape hatch: break what you are looking at (§2.3) |

Defaults, chosen to sit inside the ambiguity §2.3 describes rather than to pretend it away, and
corroborated in *scale* by the reference implementation's own tolerances: `corridor_slack` **0.35**;
`drift_soft` **2.0** blocks with `drift_patience` **200** ticks (10 s); `drift_hard` **3.0** blocks;
`stall_multiplier` **3.0**; `stall_grace` **10** ticks. Note the shape: the corridor is *wide* and
it is the **patience counter, not the distance, that catches most real failures.** Arrival
tolerances are tighter: ~0.25 blocks horizontal and ~0.1 vertical (the vertical figure exists
because lily pads sit slightly above the block floor), and centring checks for a jump or sprint
decision want ~0.1 blocks.

Completion: the player's feet AABB is inside the destination cell **and** `on_ground`, with per-kind
overrides (`Climb` tests the climbable column, `Swim` tests submersion, and every in-liquid test
tolerates being one cell above the expected node). **An AABB test, not a coordinate-equality
test** — the coordinate test is what produces the few-hundredths-short stall. And accept positions
one or two cells past the destination as success when speed exceeds ~20 blocks/s (§2.3).

`Break` and `Place` edges are two-phase — acquire, then move:

- select the hotbar slot; wait for the ray-cast to hit the intended block **or** the rotation to be
  within tolerance, never an exact rotation comparison (§2.3: rotation is quantised on the wire);
- for a place: send sneak via `SetPlayerInput` and issue the click on the **following** tick, since
  crouch is not observable until then;
- hold sneak through a break when the target is only visible while sneaking (§2.3);
- honour vanilla's post-break cooldown and the swallow-a-click-after-a-left-click window;
- on cancellation, explicitly stop the break;
- if no face is reachable, aim at the block centre and swing; if that does not apply either,
  declare the edge unreachable rather than looping.

`lodestone_game::mining`'s `Mining` state machine already owns break progress (`start`,
`continue_`, `stop`, `destroy_stage`); the executor drives it and threads the block-prediction
`sequence`.

### 4.9 Segmentation, splicing and replanning

**Splicing is designed away rather than solved.** When the remaining plan's estimated time —
**excluding the currently executing edge** (§2.3; including it lets one long descent suppress the
trigger until it finishes) — drops below `replan_lead_ticks` (default **30**, 1.5 s), dispatch the
next search **from the current plan's terminal node**: same position, same `Arrival`, same goal. The
new plan therefore begins exactly where the old one ends and concatenation is trivially valid. No
overlap to check, no splice predicate to get wrong.

Concatenate only when the first plan ends exactly where the second begins **and they share no other
position** (§2.3). Otherwise keep them separate and switch at the boundary — an overlap creates a
doubling-back plan, which breaks the position→edge function and with it the recovery scans.

If the continuation has not arrived when the current plan is exhausted, **stand still at the
terminal node.** A visible pause is strictly better than mis-splicing or executing a guess, and it
is *evidence*, which a silently-wrong splice is not. Frequent pauses mean raising
`replan_lead_ticks` or lowering the search deadline.

Two refinements from §2.3, worth having but not first:

- **Early adoption.** If an edge has just cleanly completed and your position appears anywhere in
  the pending continuation, hop straight onto it. Two exclusions, both learned: not while airborne
  outside liquid, and not while sinking in liquid — in both cases "I am at this node" is unreliable.
- **Prefix trimming.** Trim the travelled prefix periodically or the per-tick scans over a
  long journey's plan dominate. Shift every index and per-edge counter consistently; this is the
  off-by-one bug factory of the whole design, so make the plan own its trimming and unit-test it.

**Discard the continuation** whenever the current segment fails partway, checked against both the
live position and the tick-start snapshot — it starts from a place you will never reach.

Replan triggers, all rate-limited by `min_replan_interval_ticks` (default **10**) except where
noted:

- goal or owner changed (immediate, exempt);
- any executor abort reason;
- plan exhausted without satisfying the goal (the normal segmented case);
- the doubling-back pause condition (§2.3) — pause, do not replan;
- `consecutive_stalls` ≥ `stall_patience` (default **3**) → **give up on this goal**, report failure
  to the owning behaviour, and do **not** immediately retry the identical search. This is the
  loop-breaker for §2.2(1), and it must exist even when you believe the cost model is perfect.

**Goal invalidation** uses the precise predicate from §2.3: discard the in-flight plan when it *used
to* end inside the goal and no longer does. Not mere goal inequality — a behaviour that recomputes
its goal from a live scan every tick produces a new goal object constantly and would replan forever.

**Abandonment is not failure.** Report "superseded" distinctly from "no path", because behaviours
treat the latter as a serious signal (blacklist a target, give up, tell the user).

### 4.10 Behaviour arbitration: bids, verbs, and interrupters

Concurrent behaviours need arbitration (§2.1, §2.3). The design is ECS-native and deliberately not
a hardcoded priority ladder. Each behaviour is an ordinary system — in this plugin or in someone
else's — writing at most one `Bid` per tick:

```
struct Bid { owner: OwnerId, priority: i32, kind: BidKind, verb: Verb }
enum BidKind { Controller, Interrupter }   // an Interrupter passing through does not evict
enum Verb {
    Goal(Box<dyn Goal>),   // adopt this goal and move toward it
    GoalHold(Box<dyn Goal>), // adopt and plan, but hold position rather than execute
    Revalidate,            // same goal; drop the plan only if it no longer reaches the goal
    Replan,                // same goal; drop the plan unconditionally
    Hold,                  // stop moving; leave goal and plan alone
    Defer,                 // I am active but have nothing to say this tick
    Release,               // I am finished
}
```

One arbiter system, last in `NavSet::Arbitrate`, picks a winner and writes the authoritative
`NavRequest`. Rules, each earning its place:

1. **Highest priority wins**, and exactly one behaviour drives the body.
2. **Ties go to the most recently *activated* behaviour.** This is deliberately not
   "ties go to the incumbent": incumbency starves a newly-activated equal-priority behaviour
   forever, which is wrong when the new one is a user command. And it does not thrash, because
   activation is an *event*, not a per-tick condition — the winner stays the winner until something
   changes.
3. **`Defer` means "active, no opinion this tick"**, which is what makes a permanently-registered,
   cheap, top-priority interrupter possible: it sits above everything and passes through except on
   the ticks that matter.
4. **`Interrupter` bids do not evict.** A pause to eat or to move items takes the body for a tick or
   two without destroying the interrupted behaviour's state. Losing control and being briefly
   pre-empted are different events and must be distinguishable, or every interruption resets every
   long-running task.
5. **A behaviour that loses control receives `LostControl { owner, reason }`.** Non-optional: a
   mining behaviour that does not know it was interrupted resumes digging into a wall it has since
   walked away from.
6. **Handover drops the outgoing plan — but only when the incoming bid is a `Controller` that
   intends to act**, never when an interrupter is passing through.
7. **Absence of a bid is release.**
8. **Two facts flow back to every behaviour each tick**, because nearly every behaviour's state
   machine branches on them: `last_plan_failed` (→ blacklist this target, try the next, or report),
   and `safe_to_interrupt` (→ gates every physical action *and* every request to stop; a behaviour
   that ignores it will try to right-click mid-jump).
9. **A `Controller` told to stop must subsequently report itself inactive, and an active behaviour
   must never answer with no verb at all.** Both are cheap `debug_assert`s and both are the kind of
   invariant that recurs if unenforced.
10. **Guard every status surface for the inactive case** (§2.3): the HUD will query a behaviour's
    name one tick after its fields were cleared.

Priority bands, convention rather than enforcement, so a plugin can slot in:

| band | who |
|---|---|
| 300+ | safety and self-preservation — in lava, drowning, falling into the void, health below threshold |
| 200–299 | an explicit user command |
| 100–199 | task behaviours — mine, build, farm, get-to-block |
| 1–99 | ambient behaviours — explore, wander, backfill |
| 0 | idle |

**Why bids rather than a registered list with a fixed order:** a plugin can add a behaviour the
arbiter has never heard of, priority is data rather than registration order, and the whole
arbitration is observable as a message stream — which is what you want at 2 a.m. when the bot
mysteriously stops. The cost is that a badly-behaved plugin can starve everything by bidding 9999;
that is inherent to trusted plugins ([`docs/bevy-migration.md`](./bevy-migration.md) §6.1) and not
worth defending against.

### 4.11 Configuration: the knobs that matter, and the tail that does not

A single `NavPolicy` resource, mutable by a plugin or a chat command. **Resist growing a
hundreds-of-settings surface.** The ones that genuinely change behaviour:

**Capability gates** — what the search may consider. These are what users actually reach for,
because each changes the *shape* of paths: `allow_break`, `allow_place`, `allow_jump`,
`allow_gaps`, `allow_climb`, `allow_swim`, `allow_sprint`, `allow_doors`, `max_fall_blocks`,
`health_margin`, `throwaway_blocks`.

**Cost weights** — §4.4's table: `turn_penalty`, `jump_penalty`, `gap_penalty`, `damage_cost`,
`break_overhead`, `place_cost`, the `danger_cost` map, and `reuse_discount` (the previous plan's
edges are discounted to keep routes stable — §2.3 — with an explicit off).

**Search tuning**: `heuristic_weight`, `search_budget_nodes`, `first_segment_ms`,
`first_segment_grace_ms`, `continuation_ms`, `edge_of_world_strikes`, `min_progress`,
`min_improvement`, `tail_discard`, `tail_min_len`, `snapshot_radius`.

**Execution tuning**: `replan_lead_ticks`, `min_replan_interval_ticks`, `corridor_slack`,
`drift_soft`, `drift_hard`, `drift_patience`, `stall_multiplier`, `stall_grace`, `stall_patience`,
`sprint_lookahead`, `lookahead_edges`, `inflation_tolerance`, `panic_health`.

That is ~40 knobs and every one changes observable behaviour. Everything that tempts you beyond
it — overlay colours, chat prefixes, log verbosity, rendering toggles — belongs to the plugin's UI
and must not be able to affect a computed path.

**And the rule that makes the line matter:** anything feeding the cost model is captured **once**
into the search request, not read per-edge. A mid-search policy change otherwise produces a path
optimal for neither the old policy nor the new one, which is worse than a suboptimal but coherent
path. `NavPolicy` is copied by value into `Search::new` and immutable there.

## 5. The crux: a long-running search against a frame-driven ECS

The part a plan must not hand-wave. Here is the constraint set, the decision, what crosses the
boundary, what it costs, and what was rejected.

### 5.1 The constraints, all real in this repo

1. **Simulation must never be gated on anything.** [`docs/frame-pacing.md`](./frame-pacing.md) is
   emphatic: `redraw` clamps `dt`, calls `sim.step(dt)` **unconditionally**, and only then returns
   early if it should not present. "Keep-alives and the per-tick movement packet ride the
   simulation, and a client the server considers stalled is sent no chunks at all — a silent, total
   chunk blackout while join and entity movement continue perfectly." A search that blocks a tick
   does not merely stutter; it can blind the client.
2. **All bevy schedules run on one thread, in fixed order.** `lodestone-ecs` uses `bevy_ecs`
   *without* `multi_threaded` deliberately ([`docs/bevy-migration.md`](./bevy-migration.md) §3.1,
   §4.1(b)) so native and wasm run the same executor and the same order, because
   `lodestone-physics` is bit-exact and thread scheduling must never be observable. There is no
   parallel system executor to lean on, and there should not be.
3. **The world lock must not be held while computing** — the mesher's rule (§3.5). A search holding
   `RwLock<World>` for 150 ms would stall the ingest path that writes chunks.
4. **wasm has no threads**, and the browser client is a stated goal.
5. **A frame is ~16 ms and a tick is 50 ms**; a search is 20,000 expansions.
6. **The result must be deterministic enough to test** (§4.1).
7. **The replanning decisions belong *after* the tick's movement is applied** (§2.3), so the
   inter-tick gap is available as compute budget. Front-loading them halves the effective movement
   rate. This is the constraint that shapes the schedule below, and it is invisible until you have
   measured it.

### 5.2 The decision

> **The search is a resumable, budgeted state machine (§4.6) over an owned `Arc<ChunkSection>`
> snapshot. It is driven by a dedicated OS thread on native and by a per-frame budget on wasm. One
> implementation, two drivers. The ECS side never blocks and never touches the search's memory.
> Plans are *collected* before physics and *dispatched* after send.**

```
                 GameTick (one thread, fixed order)
 ┌──────────────────────────────────────────────────────────────────┐
 │ TickSet::Input     human input → MovementIntent                  │
 │ NavSet::Bid        behaviours write Bid messages                  │
 │ NavSet::Arbitrate  pick owner → NavRequest; emit LostControl       │
 │ NavSet::Collect    try_recv a finished PlanResponse; validate      │
 │                    against the live world; commit or discard       │
 │ NavSet::Execute    executor → MovementIntent, LookIntent, actions  │
 │ TickSet::Physics   lodestone_physics::tick                         │
 │ TickSet::Send      Move / SetPlayerInput / BlockAction             │
 │ NavSet::Dispatch   snapshot (one lock) + send PlanRequest  ← §5.1(7)│
 └──────────────────────────────────────────────────────────────────┘
        │ PlanRequest (owned, Send)          ▲ PlanResponse (owned, Send)
        ▼                                    │
 ┌──────────────────────────────────────────────────────────────────┐
 │ nav worker thread: loop { recv(); while step(big_budget) { … } }  │
 │ • owns Arc<SnapshotView> — copy-on-write, cannot change under it  │
 │ • touches no ECS, no locks, no globals; exactly one search live   │
 │ • cancellation is a polled one-way flag, checked every 64 nodes    │
 │ • publishes an immutable partial + counters for the overlay        │
 └──────────────────────────────────────────────────────────────────┘
```

`NavSet::Dispatch` sitting **after** `TickSet::Send` is §5.1(7) made concrete: the search gets the
whole gap between this tick's packets and the next tick's work, rather than competing with the
tick it was launched from. `NavSet::Collect` sitting **before** `TickSet::Physics` means a plan that
arrived during the gap is adopted in time to steer this tick.

**What crosses the boundary, exactly:**

```
struct PlanRequest {
    id: u64,                      // so a superseded response can be dropped
    view: Arc<SnapshotView>,      // owned snapshot; Send + Sync; no lock
    start: NavNode,
    goal: Box<dyn Goal>,          // Send + Sync
    policy: NavPolicy,            // by value: immutable for this search (§4.11)
    budget: Budget,
}
struct PlanResponse {
    id: u64,
    outcome: Outcome,             // Reached | BudgetExhausted | WorldExhausted | Failed | Superseded
    plan: Vec<Edge>,
    terminal: NavNode,
    witnesses: HashSet<u64>,      // §4.5, computed on the worker
    stats: SearchStats,
}
```

All owned, all `Send`, no borrows, no `Entity`, no bevy types. That is what keeps `lodestone-nav`
bevy-free and makes the boundary auditable: if a field is not `Send + 'static`, the design has been
violated. Note `Superseded` is a distinct outcome from `Failed` — §4.9's abandonment rule.

The snapshot must be built on the tick thread (it is the only place allowed to take the world lock);
assert that, because constructing it anywhere else is the bug this design exists to prevent.

**The wasm arm** is the same `Search`, stepped from an `Update` system with
`Budget { nodes: 2_000, deadline: None }` — no `Instant` on that target — holding the `Search` in a
resource across frames. It is slower to a first plan (a 20,000-node search takes ~10 frames), and
that is acceptable: the bot pauses a beat longer before setting off. **Because it is the same
`Search::step`, this arm cannot rot into an untested branch** — every headless unit test of the
search exercises exactly the code the wasm driver runs, with a different budget.

### 5.3 What each part costs

- **Snapshot construction** is the only cost on the tick thread: one lock acquisition, ~15,000 `Arc`
  refcount bumps and a map build, per *search dispatch* — not per tick. Comparable to work the
  mesher already does. If it shows up in a profile, reuse the previous snapshot when the player has
  not crossed a chunk boundary and no relevant column changed.
- **Memory**: the snapshot's `Arc`s pin sections the client would otherwise free, but the sections
  are shared with the live world, so the marginal cost is the map plus whatever the client has since
  replaced. Bounded, released when the search ends. **Never hold two snapshots at once** — the
  worker owns exactly one, which is the same invariant as "one search in flight".
- **Latency**: a plan arrives 1–10 ticks after dispatch; §4.9's `replan_lead_ticks` hides it, and the
  visible symptom when it fails to is an honest pause.
- **A thread in a plugin** is fine — plugins are compiled-in, fully-trusted code
  ([`docs/bevy-migration.md`](./bevy-migration.md) §6.1) — but the policy should be written down
  (§7.7).
- **Events from the worker are queued and drained on the tick thread**, never dispatched as
  callbacks from the worker. Otherwise plugin code runs on a thread with no ECS access and the
  failure is baffling.

### 5.4 Rejected alternatives, and why

- **Budget the search on the tick thread on native too.** Tempting for uniformity, and it *is* the
  wasm arm. Rejected as the native default because a 4 ms slice inside a 50 ms tick that also runs
  physics, ingest and extract is real jitter on the one thread that must not jitter (§5.1(1)), and
  because it makes time-to-first-plan depend on frame rate — the exact coupling
  [`docs/frame-pacing.md`](./frame-pacing.md) exists to forbid. It stays available as a fallback,
  and it is the same code, so switching is a one-line decision.
- **`bevy_tasks` / an async task pool.** Would work; it is what azalea does. Rejected because
  `lodestone-ecs` deliberately has no multi-threaded executor and no `bevy_tasks` dependency, and
  adding a task pool to obtain one background thread is a large dependency for a small need. A named
  `std::thread` matches the mesher and the net thread and keeps lifetime and priority explicit.
  Revisit if several plugins independently want background work.
- **Search directly against the live `RwLock<World>` with short locks.** Rejected outright: thousands
  of lock acquisitions per search, and — worse — the world changes *between* them, so the search
  reasons about a state that never simultaneously existed. Snapshot coherence is a correctness
  requirement, not an optimisation.
- **Chunks as ECS entities so the search can `Query` them.** Rejected for the reason
  [`docs/bevy-migration.md`](./bevy-migration.md) §2.3/§8 rejects it generally, plus: a `Query`
  cannot leave the schedule, so it cannot feed a worker at all.
- **Incremental/repairing search (D\*Lite, LPA\*) instead of replanning.** Genuinely attractive: the
  world changes locally and a repair is cheaper than a replan. Rejected for v1 because it requires
  search state to survive across world versions, which fights the frozen-snapshot design that makes
  the threading tractable, and because segmentation already re-searches every ~30 ticks so the
  saving is smaller than it looks. Revisit only if profiling shows replanning dominates.

## 6. Verification

The repo's evidence standards apply, and two of them bite hard.

**Expected values must originate outside the code under test.** The cost model is derived from
`lodestone-physics`, so "the executor took as long as the cost model predicted" is a **closed loop**
and proves nothing about vanilla. The external oracles are:

1. **The physics golden traces**, which already pin the integrator against a JVM and an independent
   Python implementation. The navigator inherits that and must not disturb it — hence
   `lodestone-physics` gains no navigation code.
2. **A live server, with the server's own validator as the oracle.** §3.2 gives the exact bar: the
   server replays our delta and rubber-bands on more than 0.25 blocks of horizontal disagreement,
   per packet. Gate: on the creative/flat oracle (`scripts/live-oracles/creative.sh`), issue a goal,
   execute, and assert **the correction counter is flat across the whole traversal**. Use
   `unique_username` from `lodestone-testsupport` — a shared name means a shared player file, and a
   dead player is held on the death screen, which sends no chunks.
3. **Its negative control, observed failing.** Run the same gate with
   `Sim.collide_against_live_world = false` (a diagnostic switch in
   [`sim.rs`](../crates/lodestone-shell/src/sim.rs), whose own doc comment says it exists to
   reproduce the rubber-band behaviour as a negative control) and confirm the correction burst
   appears. Assertions of an absence need a control proving the detector works.

**Coverage inside the subject's screen rect.** The dominant defect class here is the island: a green
search suite is entirely compatible with a navigator that moves nothing. Every milestone in §9
asserts *the player's position changed on a live server*, not that a plan was produced.

**The world-species trap, restated because it is the live one:** both shell collision adapters are
coarse in the same way (§3.2), so any legality or cost rule about slabs, stairs, fences, ice or
ladders can be "verified" against every existing scene and mean nothing. **Build a fixture world
that structurally contains them** — a hand-authored chunk with a slab staircase, a fence line, an
ice run, a soul-sand patch, a ladder column and gaps of 1–5 blocks — and make it the primary
fixture for the graph tests. Without it, M0 cannot be shown to have worked.

Additional gates worth having:

- **The cost-calibration histogram.** The executor logs `(predicted_ticks, actual_ticks)` per edge;
  assert p95 absolute error ≤ 2 ticks over a long traversal. This is the direct test of §4.3's
  arrival-class approximation and §4.4's central claim, and it is the number to watch whenever
  anything about physics changes.
- **Determinism.** The same snapshot, start, goal and policy produce a byte-identical plan across
  runs and across debug/release. Cheap, and it catches accidental float or hash-order dependence.
- **Node-packing bijection.** Round-trip every `(x, y, z, arrival)` in a realistic range. §2.3 says a
  collision silently corrupts the plan; this is the test that makes that impossible.
- **Plan well-formedness.** Every constructed plan: endpoints agree with the position list, edge
  count is one less than position count, each edge's declared source and destination match the
  adjacent positions, and **no position repeats** (§2.3).
- **Search-budget honesty.** `step(Budget { nodes: N })` expands exactly N. Trivially true until
  someone adds an early return; then it is the test that notices.
- **Stall-budget provenance.** A break-then-move edge must trip its stall counter. This is the direct
  test of the §2.3 rule that the budget comes from planning time, and it fails silently if someone
  "simplifies" it to a live recomputation.
- **`ScheduleBuildSettings { ambiguity_detection: LogLevel::Error }`** in the plugin's tests, per
  [`docs/bevy-migration.md`](./bevy-migration.md) Stage 3 — the executor writing `MovementIntent` is
  exactly the second writer this catches, and §7.1 exists because of it.

## 7. What the plugin API must expose for this to be a plugin at all

The deliverable that matters most for `docs/bevy-migration.md`, because several items are things the
current plan does not yet provide.

### 7.1 An ordering anchor for automation-supplied movement intent

`TickSet` today is `Input → Physics → Predict → Animate → Send`
([`sets.rs`](../crates/lodestone-ecs/src/sets.rs)). A navigator must write intent *after* human
input and *before* physics. Two systems writing `MovementIntent` in `TickSet::Input` is an
ambiguity, and the migration plan intends the ambiguity detector to be `Error` in tests — so this is
not stylistic, it will fail the build.

**Requirement:** add `TickSet::Intent` between `Input` and `Physics`, documented as "where non-human
sources of movement intent write; last writer wins", with human input confined to `Input`.

### 7.2 `MovementIntent` and `LookIntent` as components, with analog fidelity

**Requirement:** `MovementIntent` must carry `lodestone_physics::MovementInput`'s full shape —
`forward: f32`, `strafe: f32` — not booleans. Steering needs analog values, exactly where §2.3 says
overshoot happens.

**Gap:** `Sim::physics_tick` is private and `Sim.input` is `lodestone_controller::InputState`, which
collapses to ±1.0 and applies its own 7-tick double-tap sprint latch. A bot driving that seam
inherits behaviour it did not ask for.

**Requirement:** `LookIntent { yaw, pitch }` separate from the camera, with the camera following it
for the local player. §2.3 notes that if look is ever decoupled from the camera, the *server-side*
rotation is the authoritative value for every aim and reachability test — so make which is which
explicit in the component's name and docs.

### 7.3 The chunk world as a resource, with a batched snapshot method

**Requirement:** `sections_at`-equivalent batched snapshot reads, plus `world_dimensions()` and
`is_chunk_loaded()`, from inside a system, without naming `lodestone-client` or `Sim`.

**Gap:** this is Stage 4. Before it, the plugin cannot see terrain at all. **This makes Stage 4 a
hard blocker** and it is the most important scheduling fact in §8.

### 7.4 The local player's physics state as components

**Requirement:** `Position`, `Velocity`, `OnGround`, `HorizontalCollision`, `Health`, `Hunger`,
`ActiveEffects`, `SelectedSlot`, `Inventory`, `FluidState`. Stage 2. Also a hard blocker.

### 7.5 Version data: collision shapes, path types and block properties through the seam

**The most consequential gap.** `VersionAdapter` exposes `entity_dimensions`, `block_hardness` and
`tool_mining` and nothing else. Collision shapes, path types and block properties exist as
oracle-verified censuses in the version crate with **no** route through the seam (§3.3).

Without this, `lodestone-nav` must depend on `lodestone-v770` directly. Legal (a plugin is a leaf
crate, per [`docs/bevy-migration.md`](./bevy-migration.md) §5) but it version-locks the navigator,
mints a second version-data seam beside `VersionAdapter`, and drags a licence boundary through a
generated data crate for nothing.

**Requirement — one new method, not five:**

```rust
/// Per-block-state physical facts a consumer needs to simulate or navigate.
/// Version-owned because state ids are renumbered every version.
fn block_facts(&self, state_id: u32) -> Option<BlockFacts>;
```

with `BlockFacts` in `lodestone-model` carrying the collision boxes (`&'static [Aabb]`),
`collision_top` **uncapped**, `PathType`, friction, speed factor, jump factor, `climbable`,
`stuck_multiplier`, `bounce_restitution` and the fluid cell. One call, cached into a flat table per
session (§4.2), defaulting to `None` — "unknown, never a guessed number" — exactly as the existing
three do.

**This also fixes §3.2**, which is a strictly larger win than the navigator: `LiveCollision` would
implement all twelve `CollisionView` methods from the same table, which is what makes slabs, ice,
ladders and fences work *for the player*.

### 7.6 World-space debug geometry in `Extract`

**Requirement:** an `Extract`-time channel where a plugin appends world-space line segments and
boxes, so a plan can be drawn. `ExtractSet` has `Terrain`, `Entities`, `Hud` and nothing for this. A
plugin correctly cannot get a `wgpu::Device`
([`docs/bevy-migration.md`](./bevy-migration.md) §6), so the shell must own the pipeline.

**Gap:** `gpu.rs` has a single-box block-outline pipeline. Generalising it to an instanced line/box
buffer is small, and it is what makes §9's later milestones observable in the way rule 1 demands.

### 7.7 A written policy on plugin-owned threads

**Requirement:** state in the plugin docs that a plugin **may** own OS threads and **must not** block
a schedule, that cross-thread communication is by channel with `try_recv` in a system, and that
worker-originated events are queued and drained on the schedule thread (§5.3). Nothing needs adding
to make this true; it needs *deciding*, because the alternative is everyone discovering `bevy_tasks`
is absent and reinventing this differently.

### 7.8 Actions, and the sneak channel

Already sufficient (§3.6). One thing to write down: **`SetPlayerInput` must be in the plugin prelude
with its edge-triggered semantics documented.** A bot that reports a sneak-derived position without
ever sending it will place blocks into containers and fall off ledges, and the failure looks like a
physics bug. Document alongside it that the server **synthesises your jump** from the `on_ground`
flag plus a rising `y` (§3.2), so that flag is load-bearing.

### 7.9 The correction counter as a component

**Requirement:** the count of adopted server `TeleportPlayer` corrections must be readable by a
plugin — it is the executor's `ServerDisagreed` trigger (§4.8) and the primary gate discriminator
(§6). Today it is `Sim.teleport_count`, a field on a struct Stage 5 deletes. Make it a component on
the local player during Stage 2 or 3.

### 7.10 Verdict on the current plan's sufficiency

`docs/bevy-migration.md`'s plugin API is **nearly** sufficient. §6's "may read and mutate every
component and resource in the prelude" plus `MessageWriter<SendAction>` covers most of it. The
genuine gaps are: **an intent-ordering anchor (7.1), analog intent and a separate look intent (7.2),
version-data breadth (7.5), and a debug-geometry channel (7.6).** Of those, **7.5 is the one that
would otherwise force a version-locked plugin**, and it is worth landing early because it pays for
itself in the player's own collision long before the navigator exists.

## 8. Dependence on the bevy migration

Stage 0 is done: `lodestone-ecs` exists with `bevy_app`/`bevy_ecs` 0.19, the four schedules, the
public sets, `EcsHandle`, `Runner` — and is already depended on by both `lodestone-shell` and
`lodestone-client`. Stages 1–6 are not.

| this plan needs | stage | why | blocker? |
|---|---|---|---|
| local player position/velocity/on-ground and movement intent as components | **Stage 2** | the executor cannot write intent and the search cannot learn where the player is | **hard** |
| chunk world as a resource with batched snapshot reads | **Stage 4** | the search has no world | **hard** |
| health, hunger, effects, chat ingest | Stage 3 | safety behaviours, sprint gating (food > 6), Haste/Jump Boost in the cost templates, chat commands | soft — M1 can hardcode |
| other entities as ECS entities | Stage 1 | follow-entity, mob avoidance | soft — only M6 |
| `Sim` deleted | Stage 5 | until then a plugin must reach into `Sim`, which is not a plugin-shaped thing | soft, but it is what makes this genuinely *a plugin* rather than shell code wearing a plugin's clothes |
| async bot tier | Stage 6 | a headless navigating bot with no window | not needed |

**The de-risking move: `lodestone-nav` needs none of it.** The search core is
`(snapshot, start, goal, policy) → plan` over `Arc<ChunkSection>` and `VersionAdapter`. It can be
built, tested and gated headlessly *today*, in parallel with Stages 1–4, using
`ClientHandle::sections_at` directly. That converts a serial dependency into a parallel one, and it
is the main reason for the two-crate split.

**But — rule 1.** A finished `lodestone-nav` that nothing calls would be the largest island this repo
has produced. So it must not ship alone: §9 pairs it with a shell-side consumer from the first
milestone, and M0 deliberately produces visible player-facing change with no navigator at all.

## 9. Milestones, each ending in something observable

Ordered so every stage puts something on screen, per `CLAUDE.md`'s rule 1. "Observable" means a
human watching the client sees a difference; "gate" means an automated assertion.

### M0 — wire the collision census into the live world (**prerequisite, and visible on its own**)

Add `VersionAdapter::block_facts` (§7.5), build the per-state table at session start, and make
`LiveCollision` implement all twelve `CollisionView` methods from it. No navigator code at all.

- **Observable:** the player stands on a slab and walks up a stair instead of falling through;
  cannot walk through a fence; slides on ice; is slowed by soul sand; climbs a ladder; bounces on
  slime. **None of these work today.**
- **Gate:** the new partial-block fixture world (§6); the live jump gate still clean; the correction
  counter flat.
- **Why first:** it is the physics-parity precondition (§3.2), it is the largest player-visible win
  in this document, and it unblocks everything below. Doing it first also means the cost model is
  never calibrated against a world that lies.

### M1 — walk to a coordinate over flat ground

`lodestone-nav` with `Walk` only (including sub-`step_height` ups and downs), `Arrival::{Still,
Walking}`, simulated cost templates, the resumable search, `AtColumn` and `AtBlock`, the closed-loop
executor with corridor, drift and stall budgets, one search dispatch (no segmentation), and a
`#goto x z` chat command.

- **Observable:** type `#goto`, the player walks there and stops.
- **Gate:** on the flat creative oracle the player reaches the goal cell within a tick budget **and
  the correction counter is flat throughout**. Negative control: the same run with
  `collide_against_live_world = false` must show the correction burst.
- **Needs:** Stage 2, Stage 4, and M0.

### M2 — real terrain

Diagonals with the both-cells-clear rule; `StepUp`; `Descend` with the sprint-overshoot brake rule
and the must-not-enter block family; `Drop` with damage-vs-health legality and slabs excluded as
landings; `Climb`. Segmentation with terminal-node hand-off, prefix trimming and tail truncation.
Witness-set invalidation plus per-edge re-verification and the look-ahead window. The debug overlay
(§7.6) drawing the committed plan and the search frontier.

- **Observable:** navigates across hills, down cliffs, up ladders, across chunk borders without
  stopping — and you can *see* the plan.
- **Gate:** a ≥300-block traversal on the terrain oracle with the correction counter flat, zero
  `Stalled` aborts, plan well-formedness asserted, and the cost histogram inside tolerance (§6).

### M3 — jumps and gaps

`Gap(dir, 1..=4)` with the late-jump timing rule, `Arrival::Sprinting`, sprint lookahead,
`jump_penalty` and `gap_penalty`.

- **Observable:** crosses a ravine it previously walked around.
- **Gate:** the fixture's 1–4 block gaps are crossed and **the 5-block gap is refused.** Refusal is
  the assertion that matters — a bot that attempts everything is not demonstrating a legality rule.

### M4 — breaking

Wire `tool_mining` into `BreakInputs` (an existing island, §3.3). `Break` edges with costs from
`Mining::ticks_to_break`, hotbar selection, the dig state machine with `sequence` threading, the
rotation-tolerance gate, the sneak-to-see-the-target rule, the post-break cooldown, refusal of
gravity-affected columns and liquid-adjacent breaks, and the encased escape hatch.

- **Observable:** tunnels through a wall instead of going around; picks the pickaxe.
- **Gate:** on the survival oracle, mine through a 3-block wall and assert the blocks **actually
  became air server-side** via RCON readback, not that we sent packets. Plus the stall-budget
  provenance test (§6).

### M5 — placing

`Place` edges: bridge across a gap, pillar up. Sneak via `SetPlayerInput` with the click on the
following tick; the too-close-to-see-the-face back-off; the soul-sand/slab approach correction;
downward-preferred mid-air placement. Throwaway-block inventory tracking. **And `maybeBackOffFromEdge`
in `lodestone-physics` if §3.1's box is confirmed** — this milestone is where sneaking near ledges
becomes constant.

- **Observable:** bridges a 6-block gap over a drop.
- **Gate:** blocks appear server-side in the expected cells; no container was opened; correction
  counter flat while sneak-placing (which is the direct test of the back-off finding).

### M6 — behaviours and arbitration

The bid/verb arbiter with interrupters, `LostControl`, and the feedback channel. Four behaviours:
`Goto` (user), `GetToBlock` (nearest matching state, via `AnyOf`), `Follow` (a moving `Within` goal),
`Explore` (nearest never-seen column). Chat commands for each.

- **Observable:** `#follow player X` and it keeps up; `#mine iron_ore` and it goes and digs;
  interrupt with `#goto` and it obeys immediately, then does **not** resume mining into a wall.
- **Gate:** pre-emption is visible in the message log; the interrupted behaviour receives
  `LostControl`; an interrupter passing through does **not** destroy the controller's state.

### M7 — fluids and danger

`Swim`, water/lava legality, the `danger_cost` table, safety behaviours in the 300+ band, the
one-cell-above tolerance for in-liquid arrival tests.

- **Observable:** swims a river instead of drowning; refuses to path along a lava lake edge; climbs
  out when it falls in.

**Out of scope, deliberately:** elytra, boats, horses, minecarts, schematic building, farming. Each
is a large independent system and none is required for the capability this document is about.

## 10. Traps, open questions, and beliefs I hold weakly

Flagged rather than smoothed over, because this repo's most valuable artifact is the record of
confident beliefs that turned out false.

### Traps — things I am confident will bite

1. **`collision_top` must not be clamped to 1.0.** Fences and walls return **1.5** and the 0.6 step
   height cannot mount them; clamping makes fences look step-able and routes navigation through
   pens. Both `lodestone-physics` and the mob pathfinder document this *independently*, which means
   it has already been nearly-gotten-wrong twice.
2. **`requires_correct_tool` is not `hasCorrectToolForDrops`.** Feeding the block's flag into
   `BreakInputs::correct_tool` makes stone break 45 ticks instead of 151 — 3.4× too fast — and it
   reads like correct data wiring. Use `ToolMining::correct_tool`.
3. **`None` from `NavView::state_at` is not air.** Conflating them makes the search invent terrain,
   and it fails in the most confident-looking way available: a beautiful path into unloaded chunks.
4. **The stall budget must come from planning time, not a live recomputation** (§2.3). The failure
   mode is a bot that digs forever and never trips its own counter.
5. **Sneak reaches the server only via `SetPlayerInput`.** Every sneak-place must send it or it opens
   the container.
6. **The block-prediction `sequence` must be threaded, never synthesised.**
7. **A plan must never revisit a position** (§2.3), or the position→edge mapping stops being a
   function and both index-recovery scans become non-deterministic.
8. **Feather Falling does not raise the safe fall distance** — only Jump Boost does. A policy that
   extends `max_fall_blocks` for feather falling will kill the bot, visibly.
9. **The verification world is coarse (§3.2, §6).** A partial-block rule verified against the current
   tree passes *vacuously*. This is the *world* species of vacuous test and it is the live one here;
   the negative control must be a **new** fixture, not an existing scene.
10. **Exact rotation comparisons never succeed** — rotation is quantised on the wire. Gate on
    ray-cast hit or a tolerance.
11. **Releasing the sprint input does not stop sprinting.** Clear it explicitly.

### Open questions — where I am uncertain, and what would settle it

1. **Is `maybeBackOffFromEdge` really a desync source?** §3.1's box argues yes, and the mechanism is
   plausible and specific, but I have not confirmed that the server's replay path reaches the
   back-off. *Evidence:* read the `maybeBackOffFromEdge` call site in `Entity.move` in
   `.cache/mc/26.2/src`; and empirically, sneak off a ledge on the oracle and watch the correction
   counter. **This is the highest-value open question in the document**, because if it is confirmed it
   promotes a physics change to a prerequisite for M5.
2. **Is the 9-way `Arrival` dimension worth 9× the state space?** *Evidence:* the cost-calibration
   histogram (§6) run twice — with `Arrival`, and collapsed to `Still`. If collapsing costs less than
   ~2 ticks of p95 error, drop it and take the memory back. I lean toward keeping it because
   momentum-gated jumps are the failure I most expect, but I would not defend the 9 against a
   measurement.
3. **Is min-`h` with `w = 1.25` as good a partial-path rule as a family of relaxation coefficients?**
   *Evidence:* on the terrain oracle, total wall-clock time to traverse a fixed 1,000-block route
   under both rules. **This is the claim in the document I would bet least on**, because the
   reference implementation's authors arrived at the more complex rule after real use, and "one
   principled knob beats several tuned ones" is an aesthetic preference until measured.
4. **Is simulated-template cost accurate enough, or does entry velocity vary too much within an
   `Arrival` class?** *Evidence:* the same histogram broken down per movement kind. If `Gap` errors
   are much worse than `Walk` errors, the fix is speed sub-buckets on `Arrival`, not a redesign.
5. **Is a dedicated thread definitely right versus a per-frame budget on native?** §5.4 argues yes.
   What would change my mind: if snapshot construction turns out to dominate the search itself, the
   threading buys little and the simpler arm wins. **Measure snapshot build time at M1.**
6. **Does `AnyOf` over hundreds of candidate ore positions behave?** `min` over 500 children per node
   expansion is not free. Likely fix: spatially prune to the nearest ~16 before building the goal.
   Unverified.
7. **Long-distance travel beyond render distance.** This plan relies on segmentation and caches no
   compact world representation. Right for v1, probably wrong for ten-thousand-block journeys — and
   note §2.3's warning that a *lossy* long-term cache is worse than useless for slab orientation and
   snow depth, so the combination that works is "plan optimistically through cache, verify
   pessimistically at execution". *Evidence needed first:* does the bot actually stall at
   render-distance edges in practice, or does re-searching every 30 ticks keep it moving? Measure
   before building a cache.
8. **How long is vanilla's post-break cooldown, exactly?** §4.4's `break_overhead` folds it into a
   guess. Confirm from `client-src/.../MultiPlayerGameMode.java` and split it out, because a guessed
   overhead inside a measured break time is the kind of thing that makes the histogram in §6 look
   worse than the design deserves.

### One belief that is load-bearing and could be wrong

That deriving costs by simulation (§4.4) is both accurate enough and fast enough. The accuracy claim
is testable by §6's histogram. The speed claim rests on the template table having a few hundred
reachable keys — if the key space turns out to be thousands, because surfaces and effects combine
more freely than I expect, the lazy table becomes a latency spike on the first search after every
effect change. The mitigation is coarser buckets; the signal is a first-search latency outlier. Watch
for it at M2, when ice and soul sand first enter the picture.

## 11. Configuration

- **New crates:** `lodestone-nav` (library: `lodestone-physics`, `lodestone-model`,
  `lodestone-world`) and `lodestone-autopilot` (bevy plugin: `lodestone-nav`, `lodestone-ecs`). Each
  with its own `LICENSE` file per §1.2. **Neither may depend on a version crate** — the whole point
  of §7.5.
- **Runtime policy:** one `NavPolicy` resource (§4.11), ~40 knobs, copied by value into each search.
  Chat commands mutate the resource; nothing mutates a running search.
- **`scripts/wasm-check.sh`:** add both crates to `CRATES`. `lodestone-nav` must be wasm-clean — no
  threads, and no `Instant` in the core (`Budget::deadline` is `Option`, and the wasm driver passes
  `None`, bounding by node count only). `lodestone-autopilot`'s worker thread is
  `#[cfg(not(target_arch = "wasm32"))]`, with the budgeted-`Update` driver as the wasm arm.
- **`cargo xtask check-connected`:** no allowlist entry for either crate. Their going red is the
  island detector working, and §8's warning about `lodestone-nav` shipping alone is exactly the case
  it should catch.
- **Feature gate:** `--features live` remains the only version selector; nothing here lets a shared
  crate name a version crate.
- **Tests:** `ScheduleBuildSettings { ambiguity_detection: LogLevel::Error }` in the plugin's tests
  (§6). Live gates `#[ignore]`d and run with `-- --ignored --nocapture`, per `CLAUDE.md`.
