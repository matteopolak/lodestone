# 26.3 world source

## What it is

`lodestone_server::Terrain263ChunkSource` serves the columns of one dimension generated by
`lodestone_worldgen::terrain263::Terrain263`: the 26.3 noise fill, surface rules, carvers and real
biomes (multi-noise for the Overworld and the Nether, the End's own source), structures, then the
26.3 placed-feature decoration (`lodestone_worldgen_feature_26_3`). It is the generator the shell
builds for the Normal, Large Biomes and Amplified world types (`lodestone-shell`'s
`preset_chunk_source`), and the integrated server's Nether and End siblings
(`worldgen_data::nether_263_chunk_source`, `end_263_chunk_source`).

## How it works

`Terrain263::with_settings(seed, settings)` compiles the bundled 26.3 tables for one noise settings
document: an Overworld preset (-64..320, sky light), `nether` (0..256, no sky light, noise only up
to 128) or `end` (0..256). A chunk spans the dimension's whole build range; above a Nether or End
noise range the blocks are what fill leaves there (air) and the biome cells come from the biome query
at their own height, as the reference fills every section's biomes. Decoration reads the generator's
own depth (128 in the Nether, which caps a huge fungus) and the dimension's sky light. It exposes two
operations:

- `shaped(cx, cz)` runs fill, surface, carving and the chunk's biome cells, and keeps the result as
  decorator-space blocks (`ChunkData`) in a bounded cache. The world-generation heightmaps are
  taken after carving and stay frozen from then on; the live ones are recomputed from whatever
  blocks a decoration window supplies (`ChunkData::with_states`).
- `decorate_source(source, window)` runs the Decorator over the 3x3 chunks around `source` and
  returns the writes it made, in order. `window` supplies the current blocks of any chunk whose
  content differs from its shaped terrain.

`Terrain263ChunkSource::full_states(cx, cz)` is a target's final column: its shaped terrain, then
the decoration of the nine chunks around it applied in `OVERWORLD_SOURCES` order, each reading the
blocks the earlier ones left in the 5x5 chunks around the target. A column is therefore a pure
function of the seed and its coordinates; nothing carries over between targets. Two adjacent
targets each apply the sources in their own order, so a feature whose outcome depends on blocks an
earlier neighbouring source placed can differ across a chunk border (a tree whose space an earlier
tree took). The 26.2 lifecycle shares resident state between the targets of one request instead;
that is a request-dependent result, this is a deterministic one.

Two block-state spaces meet here. The decorator works in its own 26.3 state table (`State`, a
`u16`); the server stores canonical `StateId`s. `Terrain263` builds both directions by name and
properties once at load (`canonical`, `feature_state`); `unmapped_states` must be zero.

Biomes are the engine's `BiomeId`s, named `minecraft:<path>`; the canonical biome enum carries
`dappled_forest` after the sorted 26.2 names, so every 26.2 identity is unchanged.

## How to change it

- A new decoration feature type goes in `lodestone-worldgen-feature-26-3` (see
  `worldgen-features-26-3.md`); nothing here changes.
- To change what a column's neighbours may see, change `Terrain263ChunkSource::full_states`; the
  window radius is `WINDOW_RADIUS` (two chunks: nine sources, each reading one chunk beyond itself).
- Adding a world preset: `Terrain263::with_settings(seed, "<noise settings name>")` accepts any
  Overworld-shaped bundled settings document (`overworld`, `large_biomes`, `amplified`).
- Generation-time mob packs and structure block-entity data are not produced yet; see the gap list.
- A feature that attaches a block entity calls `Level::attach_block_entity` with a
  `PlacedBlockEntity`; the server adopts it in `Terrain263ChunkSource::surviving_block_entities`.

## Structures

`terrain263::structures` (`Terrain263::with_structures`) runs the legacy structure machinery
(`StructureRegistry`, the jigsaw assembler, templates and processors) over the 26.3 bundled data:

- **Starts.** `structure_starts` finds each structure's start in a chunk from the placement sets
  (spacing, separation, salt, exclusion zones) and the surface heights of the 26.3 terrain. Strongholds
  come from a concentric-ring layout drawn with the legacy LCG random, first biome match taken
  without a further draw.
- **References.** `structure_refs` collects every start within `REFS_RADIUS` chunks of a column
  (cached, `REFS_CAPACITY` entries), so a column knows the pieces that reach it.
- **Beardifier.** `beardifier_for` turns the pieces near a chunk into the terrain adaptation that
  `fill_chunk` applies while the density is evaluated, so villages and ancient cities sit on beard
  and buried structures carve their box.
- **Per-step hook.** `Decorator::decorate_with_structures` asks `place_structures` at the start of
  each decoration step for the writes of the structures generating in that step (strongholds and
  mineshafts at step 4, villages at step 3, and so on, from `STRUCTURE_RUNTIME_ORDER`), before that
  step's features, with the heightmaps kept live.

The embedded structure data is the 26.3 data (`just regen-worldgen-structures` re-extracts it).
26.3 changed two on-disk shapes the parsers accept: block states as a string or `{id, properties}`,
and NBT palette entries as `id`/`properties`.

Verified against a real 26.3 server (`scripts/worldgen-oracle-26-3/StructureOracle263.java`, seed 42,
`tests/overworld_263_structures.rs`): all 118 starts in chunks -60..=60 and the three first stronghold
positions are produced at the right chunk and structure with no extras; 95 of 118 match box, Y and
piece count exactly and the rest match horizontally; all 128 stronghold ring positions match; the
village jigsaw's random draws are identical to the server's over 23,339 trace lines
(`JIGSAW_TRACE=1` with the logging patch under the oracle's `patches/` directory); base
column heights are exact; and the production source serves village blocks, with a control that a
source built without structures does not.

Known differences: a shipwreck, ocean ruin or swamp hut settles its Y when the start is made here
and when the piece is written there; a monument start carries 27 pieces here and one there. Not
verified block for block against the server: template placement and processors, the beardifier's
effect on terrain, and mineshaft and portal terrain writes.

A structure's loot chests and fixed-mob spawners get their data from `structure_loot`
(`chests_for_chunk`, `spawners_for_chunk`), run over the column's completed starts after decoration:
a chest's block is set when the template asks for it, and its entity is kept only while the final
block is a chest. Every self-named structure container's table is bundled (the test
`every_self_named_loot_table_is_bundled` in `structure_loot` keeps it that way); any other
entity block placed without data gets a default, empty entity. A fortress is the exception: its
chest seeds are drawn while its pieces are placed, so `Terrain263::place_structures` returns them
as `CodedLoot` beside its writes, `decorate_source_full` carries them out in `SourceDecoration`,
and the source rolls those inside the target chunk with `chests_from_coded`. The witnesses are
`a_shipwreck_serves_filled_chests` and `fortress_placement_chests_reach_the_chunk_source`. Only the
production constructors (`worldgen_data::overworld_263_chunk_source_of_type`,
`nether_263_chunk_source`, `end_263_chunk_source`) attach structures; a bare
`Terrain263ChunkSource::new` generates none.

## Decoration block entities

A monster room attaches a chest per placed chest (with the loot seed it drew) and a spawner (with
its mob: skeleton, zombie, zombie, spider by the draw), and a tree's beehive decorator attaches a
nest with one `ticks_in_hive` per bee. `Terrain263ChunkSource::full_states_with_block_entities`
returns them as the existing `GeneratedBlockEntity` values, keeping an entry only while the final
block at its position is still its own and one per position, and `generate` adds them to the column.
Test: `tests/overworld_263_block_entities.rs` (seed 42, chunk (-24, -33) holds a room and a hive)
with a unit control that an entity over the wrong block is dropped.

## Configuration

None at runtime. The build range comes from the settings (`Terrain263::min_y`, `height`); the
shaped-chunk cache holds 384 chunks (`SHAPED_CAPACITY`). An End gateway with a known exit (the
return gateway beside the exit portal) is served as an `end_gateway` block entity carrying it.

## Dependencies

`lodestone-worldgen-core` (`engine::release26_3`), `lodestone-worldgen-data-26-3` (bundled tables),
`lodestone-worldgen-feature-26-3` (Decorator), `lodestone_worldgen::frontend26_3` (state-key
resolution) and `lodestone-data` (canonical states and biomes).

## Verification

`scripts/worldgen-oracle-26-3/WorldOracle263.java` runs the real server classes for a target the
way the source does: it fills, surfaces and carves the 5x5 chunks around the target over the real
multi-noise biome source, then runs the real feature placement for the nine chunks around it in the
production source order, and prints one hash per 16-row section of the target plus one for the
whole column. `crates/lodestone-server/tests/overworld_263_oracle.rs` compares what
`Terrain263ChunkSource::column` serves against the committed output
(`tests/fixtures/world-oracle-26-3/overworld-42.txt`) and names the first differing section; its
control runs the same fixture under another seed and requires every target to differ. Given a
leading `nether` or `end`, the oracle switches settings, biome source, build range and sky light;
`tests/nether_end_263_oracle.rs` checks both dimensions the same way (`nether-42.txt`,
`end-42.txt`), with a wrong-seed control (End targets without a pillar are seed-independent, so at
least one must differ there).

Regenerate the fixture (container runtime required, host needs no Java):

```
scripts/worldgen-oracle-26-3/run.sh WorldOracle263 42 0 0 7 -3 -9 12 30 30 | grep -v 'WARN\]' \
  > crates/lodestone-server/tests/fixtures/world-oracle-26-3/overworld-42.txt
```

## Performance

`cargo run --release -p lodestone-server --example bench_overworld_263 -- 42 <radius> [new|old]`
times the 26.3 source against the 26.2 composed source over one square patch (radius 4 is 81
columns, radius 8 is 289). Wall-clock numbers swing with other builds on the machine (load average
reached 70 during measurement), so compare CPU time from `/usr/bin/time -l` on a `new` and an
`old` run:

| patch | 26.3 user CPU | 26.2 user CPU | 26.3 peak RSS | 26.2 peak RSS |
|---|---|---|---|---|
| 81 columns | 3.9 - 4.0 s | 2.7 - 2.9 s | | |
| 289 columns | 11.4 - 12.1 s | 8.5 - 9.0 s | 210 MB | 338 MB |

So the 26.3 path costs about 1.35x the CPU of the old one for a cold batch. On a quiet machine the
single-column latency was p50 22.8 ms against 24.0 ms and cold serial 29 against 32 columns/s
(radius 4); a cold batch through `ChunkSource::columns` finished 81 columns in 0.5 s against 0.3 s.
A column's first request builds its 5x5 chunk window serially, so the very first column of a cold
source is the slow outlier (about 250 ms on a quiet machine).

Where the time went, from sampling: a shaped chunk first cost 118 ms because the surface rules
asked for the biome at every block they inspect and each ask re-sampled six climate noises; one
memo per quart cell (`Terrain263::build_shaped`) brought it to about 10 ms. Decoration is about 9
sources per column at roughly 1.3 ms each; its per-feature change journal sorts instead of hashing
(`Level::drain_changes`). The remaining multiple over 26.2 is that decoration is recomputed per
target: only the first source in a target's order sees pristine terrain, so results cannot be shared
between neighbouring targets without changing the semantics above. `columns` groups a batch so the
union of the windows is built once in parallel (`GROUP`, `WARM_LIMIT` in `terrain263.rs`).

## Diagnosing a mismatch

`run.sh WorldOracle263 42 <cx> <cz> dump` prints every non-air block of the target and of the target
after each source; `LODESTONE_DUMP=cx,cz cargo test -p lodestone-server --test overworld_263_oracle
dump_target -- --ignored --nocapture` prints the served column in the same format. Diff the two
sorted. The first source whose result differs, then the first placed feature (`trace` mode), narrows
it. One real find this way: the red-mushroom footprint check is made with no tree height, so only
the stem column is tested, not the cap rows.

## Gaps

Terrain, biomes, carvers and decoration are covered by the oracle, and structure starts by the
structure oracle. Not yet produced by this source: generation-time mob packs and the End crystals on
the pillars (the decoration builds their bedrock and fire; the crystal entities are the dragon
fight's to spawn).
