# 26.3 Overworld source

## What it is

`lodestone_server::Overworld263ChunkSource` serves Overworld columns generated by
`lodestone_worldgen::terrain263::Terrain263`: the 26.3 noise fill, surface rules, cave and canyon
carvers and real multi-noise biomes, then the 26.3 placed-feature decoration
(`lodestone_worldgen_feature_26_3`). It is the generator the shell builds for the Normal, Large Biomes and Amplified world types
(`lodestone-shell`'s `preset_chunk_source`); the 26.2 composed pipeline (`OverworldGenerator`)
remains for hosting older protocol families and for worlds saved by it.

## How it works

`Terrain263` compiles the bundled 26.3 tables once per seed and exposes two operations:

- `shaped(cx, cz)` runs fill, surface, carving and the chunk's biome cells, and keeps the result as
  decorator-space blocks (`ChunkData`) in a bounded cache. The world-generation heightmaps are
  taken after carving and stay frozen from then on; the live ones are recomputed from whatever
  blocks a decoration window supplies (`ChunkData::with_states`).
- `decorate_source(source, window)` runs the Decorator over the 3x3 chunks around `source` and
  returns the writes it made, in order. `window` supplies the current blocks of any chunk whose
  content differs from its shaped terrain.

`Overworld263ChunkSource::full_states(cx, cz)` is a target's final column: its shaped terrain, then
the decoration of the nine chunks around it applied in `OVERWORLD_SOURCES` order, each reading the
blocks the earlier ones left in the 5x5 chunks around the target. A column is therefore a pure
function of the seed and its coordinates; nothing carries over between targets. Two adjacent
targets each apply the sources in their own order, so a feature whose outcome depends on blocks an
earlier neighbouring source placed can differ across a chunk border (a tree whose space an earlier
tree took). The 26.2 lifecycle shares resident state between the targets of one request instead;
that is a request-dependent result, this is a deterministic one.

Two block-state spaces meet here. The decorator works in its own 26.3 state table (`State`, a
`u16`); the server stores canonical `StateId`s. `Terrain263` builds both directions by name and
properties once at load (`canonical`, `feature_state`); `unmapped_states` must be zero.

Biomes are the engine's `BiomeId`s, named `minecraft:<path>`; the canonical biome enum carries
`dappled_forest` after the sorted 26.2 names, so every 26.2 identity is unchanged.

## How to change it

- A new decoration feature type goes in `lodestone-worldgen-feature-26-3` (see
  `worldgen-features-26-3.md`); nothing here changes.
- To change what a column's neighbours may see, change `Overworld263ChunkSource::full_states`; the
  window radius is `WINDOW_RADIUS` (two chunks: nine sources, each reading one chunk beyond itself).
- Adding a world preset: `Terrain263::with_settings(seed, "<noise settings name>")` accepts any
  Overworld-shaped bundled settings document (`overworld`, `large_biomes`, `amplified`).
- Block entities, generation-time mob packs and structures are not produced yet; see the gap list.

## Configuration

None at runtime. The Overworld shape is `terrain263::MIN_Y = -64`, `HEIGHT = 384`; the shaped-chunk
cache holds 384 chunks (`SHAPED_CAPACITY`).

## Dependencies

`lodestone-worldgen-core` (`engine::release26_3`), `lodestone-worldgen-data-26-3` (bundled tables),
`lodestone-worldgen-feature-26-3` (Decorator), `lodestone_worldgen::frontend26_3` (state-key
resolution) and `lodestone-data` (canonical states and biomes).

## Verification

`scripts/worldgen-oracle-26-3/WorldOracle263.java` runs the real server classes for a target the
way the source does: it fills, surfaces and carves the 5x5 chunks around the target over the real
multi-noise biome source, then runs the real feature placement for the nine chunks around it in the
production source order, and prints one hash per 16-row section of the target plus one for the
whole column. `crates/lodestone-server/tests/overworld_263_oracle.rs` compares what
`Overworld263ChunkSource::column` serves against the committed output
(`tests/fixtures/world-oracle-26-3/overworld-42.txt`) and names the first differing section; its
control runs the same fixture under another seed and requires every target to differ.

Regenerate the fixture (container runtime required, host needs no Java):

```
scripts/worldgen-oracle-26-3/run.sh WorldOracle263 42 0 0 7 -3 -9 12 30 30 | grep -v 'WARN\]' \
  > crates/lodestone-server/tests/fixtures/world-oracle-26-3/overworld-42.txt
```

## Performance

`cargo run --release -p lodestone-server --example bench_overworld_263 -- 42 <radius> [new|old]`
times the 26.3 source against the 26.2 composed source over one square patch (radius 4 is 81
columns, radius 8 is 289). Wall-clock numbers swing with other builds on the machine (load average
reached 70 during measurement), so compare CPU time from `/usr/bin/time -l` on a `new` and an
`old` run:

| patch | 26.3 user CPU | 26.2 user CPU | 26.3 peak RSS | 26.2 peak RSS |
|---|---|---|---|---|
| 81 columns | 3.9 - 4.0 s | 2.7 - 2.9 s | | |
| 289 columns | 11.4 - 12.1 s | 8.5 - 9.0 s | 210 MB | 338 MB |

So the 26.3 path costs about 1.35x the CPU of the old one for a cold batch. On a quiet machine the
single-column latency was p50 22.8 ms against 24.0 ms and cold serial 29 against 32 columns/s
(radius 4); a cold batch through `ChunkSource::columns` finished 81 columns in 0.5 s against 0.3 s.
A column's first request builds its 5x5 chunk window serially, so the very first column of a cold
source is the slow outlier (about 250 ms on a quiet machine).

Where the time went, from sampling: a shaped chunk first cost 118 ms because the surface rules
asked for the biome at every block they inspect and each ask re-sampled six climate noises; one
memo per quart cell (`Terrain263::build_shaped`) brought it to about 10 ms. Decoration is about 9
sources per column at roughly 1.3 ms each; its per-feature change journal sorts instead of hashing
(`Level::drain_changes`). The remaining multiple over 26.2 is that decoration is recomputed per
target: only the first source in a target's order sees pristine terrain, so results cannot be shared
between neighbouring targets without changing the semantics above. `columns` groups a batch so the
union of the windows is built once in parallel (`GROUP`, `WARM_LIMIT` in `overworld263.rs`).

## Diagnosing a mismatch

`run.sh WorldOracle263 42 <cx> <cz> dump` prints every non-air block of the target and of the target
after each source; `LODESTONE_DUMP=cx,cz cargo test -p lodestone-server --test overworld_263_oracle
dump_target -- --ignored --nocapture` prints the served column in the same format. Diff the two
sorted. The first source whose result differs, then the first placed feature (`trace` mode), narrows
it. One real find this way: the red-mushroom footprint check is made with no tree height, so only
the stem column is tested, not the cap rows.

## Gaps

Terrain, biomes, carvers and decoration are covered by the oracle. Not yet produced by this source:
structures and their terrain adaptation, block entities placed by decoration, generation-time mob
packs, and the Nether and End (those keep their own generators).
