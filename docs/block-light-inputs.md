# Block light inputs

## What it is

`lodestone_data::light_props` supplies exact raw dampening and emission for the
32,366 canonical Minecraft 26.2 block states. The values come from a complete
server-registry capture rather than defaults inferred from a block's name or
properties.

## How it works

`LightPropertiesOracle` directly queries the initialized state registry, emitting
one row with the state ID, resource name, raw dampening, emission, and sorted
properties. The complete capture has 1,196 block names and matching census and
completion records. Its SHA-256 is
`6ec5b31daeab2cbdab643ba2f696ebd042aca0683a6e10b92c219ae12e9f8d2b`.

Before generating, `tests/light_props.rs::committed_table_matches_source` requires
the exact release header and digest, dense IDs, unique semantic signatures,
sorted property keys, values in `0..=15`, and a complete trailer. It independently
joins every ID, name, and full property set against the official 26.2
`blocks.json` report and the committed canonical table. A numeric ID alone is
never enough to publish a value.

The runtime representation is 44 distinct `(dampening, emission)` pairs and a
32,366-byte `u8` index column. Lookups through `StateId` use static data and
allocate nothing. The integrated server injects these values into
`lodestone_world::LightProperties`; ordinary light spread applies its own
minimum cost of one while skylight source detection needs raw dampening zero.

The committed fixture contains 40 captured witnesses, including furnace lit and
unlit states, several light levels, cave vines with and without berries, lichen
with and without an attached face, wet and dry slabs, candle counts, and extended
pistons. Hermetic tests check their complete identities and exact pairs plus
the runtime census, range, and lookup boundaries. The full raw capture stays in
private cache; the ignored drift guard checks every generated byte against it.

Scalar accuracy does not establish propagation accuracy. Adjacent states'
opposing faces can jointly block a light edge, and vertical skylight detection
also considers those faces. A solver needs both states and the direction to
resolve that rule; these two scalar columns cannot represent it. Neither a
range check nor an exact scalar capture proves a no-overlighting contract for
the complete solver.

## How to change it

Capture the release with the bounded, serial workflow in
[the oracle documentation](data-light-oracle.md). Preserve the full completion
record and independently check state identity against that release's official
report. Use a fresh capture rather than adding name-based corrections.

For the pinned 26.2 capture, run from the repository root:

```sh
LODESTONE_LIGHT_PROPS_DUMP="$task_capture/light-properties.raw" \
  cargo test -p lodestone-data --test light_props \
  committed_table_matches_source -- --ignored --nocapture
```

Set `LODESTONE_REGEN=1` on the same invocation to publish the generated table
after all capture and identity checks pass. Run the hermetic test target after
regeneration. The existing 26.2 palette is deliberate: introducing another
release requires its semantic states and every dependent state table to move
together, rather than extending only this light table with foreign wire IDs.

When changing the pinned source, update the digest, bounded external witnesses,
and generator census together after independent verification. Keep invalid
capture controls exercised: truncated data, shifted IDs, duplicate semantic
states, another release header, and changed names or properties must fail.

## Configuration

`LODESTONE_LIGHT_PROPS_DUMP` selects the complete private capture.
`LODESTONE_REGEN` enables generated-file publication only after verification.
The official identity report is
`.cache/mc/26.2/generated/reports/blocks.json`; the accepted release is 26.2,
protocol 776. Counts and capture SHA-256 are pinned in the test generator.

## Dependencies

Runtime lookup depends only on the generated table and canonical `StateId`.
Hermetic tests need no JVM or private cache. Ignored regeneration also needs
the full capture, official report, `serde_json`, and host `shasum -a 256`.
Producing a capture requires the official server jar, its libraries, JDK 25,
and Apple `container`, as described in the oracle documentation.
