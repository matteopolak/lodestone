# Ore placement: where its allocations went, and why the ore path was not the biggest one

## What it is

Unit 18 of [`plans/worldgen-rewrite.md`](plans/worldgen-rewrite.md): the
`UNDERGROUND_ORES` placement engine's heap traffic, taken from **8,306
allocations per ore pass to 20** (**207,671 → 503** over a 3×3 sweep, −99.76%)
without moving one RNG draw or one generated byte. It is the sequel to
[`worldgen-ore-lookup-cost.md`](./worldgen-ore-lookup-cost.md) (U15, which
removed the engine's *lookups*) and applies
[`worldgen-vegetation-ids.md`](./worldgen-vegetation-ids.md)'s (U8) `Positions`
shape to the engine U8 did not touch.

It also carries the more important measurement, which is a correction: **the ore
path is not where worldgen's remaining allocations are.** The surface stage is,
by a factor of 18.

## The attribution, and the mis-attribution it corrects

U18 opened with a brief stating that ~2.2M allocations remained on the ore path
and "nobody knows what they are". They are mostly **not on the ore path**.

`tests/ore_alloc_attribution.rs`, 3×3 cold sweep, seed 42, embedded production
data, `--features gen-counters`, real `GlobalAlloc` calls binned by
[`counters::current_stage`]:

| stage | allocations | share |
|---|---|---|
| **surface** | **3,847,972** | **92.46%** |
| ore | 207,671 | 4.99% |
| carve | 101,651 | 2.44% |
| shape | 2,303 | 0.06% |
| biome | 784 | 0.02% |
| materialize / aquifer / other / intern / vegetation | 1,512 | 0.04% |
| **total** | **4,161,893** | |

The reason a figure of ~2.2M got attached to "the ore path" is structural and
worth keeping: **`ore_stage` drives `pre_ore_stage` for its eight neighbours**,
and each of those runs aquifer → shape → surface → materialize → carve. So any
*inclusive* measurement of the ore path — a samply subtree, a wall-clock span, an
allocation count taken around the call — counts the surface stage's allocations
as ore's. `counters`' [`StageGuard`] attributes to the **innermost** stage
precisely so this cannot happen, and that is the only reason the table above can
tell the two apart.

The general lesson is the one `CLAUDE.md` already states about coverage numbers,
one level in: **"allocations on the X path" is ambiguous between inclusive and
self, and for a stage that drives its own dependency closure the two differ by
18×.** Say which one, and bin by the innermost stage if you want the second.

### Inside the ore engine

Two independent instruments, both in `tests/ore_alloc_attribution.rs`: a
**sampled** backtrace aggregation (1 in 64 — symbolising a backtrace costs
milliseconds here, and unsampled ran over eight minutes without finishing) and an
**unsampled** allocation-size histogram.

| site | sampled symbols | unsampled size cross-check |
|---|---|---|
| `Placement::get_positions`'s `Vec<BlockPos>` | **79.96%** | 78.62% of ore allocations are exactly **12 bytes** |
| `VisitedBox::over_spheres`'s `bits` | 10.21% | the 8-byte and small-multiple-of-8 rows |
| `do_place`'s `data` | 9.65% | **2,048 bytes** and **1,056 bytes** |
| interner / `RegionView` overlay growth | 0.18% | — |

The cross-check is not a restatement of the symbol table, because each size is
derivable from the source independently: `size_of::<BlockPos>()` is 12 (three
`i32`s) and **12 is not a multiple of 8**, so a 12-byte allocation cannot be a
`Vec<u64>` or a `Vec<f64>` — the 163,272 twelve-byte allocations are *necessarily*
single-element `vec![pos]`. And `do_place`'s `data` is `size * 4` `f64`s, so
`2048 = 64 * 4 * 8` and `1056 = 33 * 4 * 8` name the `size = 64` blob ores
(andesite/diorite/granite/tuff) and the `size = 33` ones exactly.

## How it works

### `OrePositions`, not `Vec<BlockPos>`

[`Placement::get_positions`] returned a fresh `Vec<BlockPos>` **per modifier per
attempt**, and `place_placed_feature`'s recursion calls it once per modifier per
surviving position — so a feature whose modifiers are
`[Count(n), InSquare, HeightRange, Biome]` allocated `1 + 3n` `Vec`s, times nine
source chunks (`apply_ore_step_3x3_per_source` is vanilla's real
`blockStateWriteRadius(1)` driver: nine full passes per chunk).

It now returns [`OrePositions::{None, One, Repeat}`]. Enumerating every arm shows
the old `Vec` only ever had one of those three shapes, so the enum is
**exhaustive over what the old code could produce**, not a narrowing — the table
is in `OrePositions`' own doc comment. This is exactly U8's
`vegetation::config::Positions`, and the two now differ only in which engine they
serve.

### Per-blob scratch, reused

`do_place` allocated two `Vec`s per blob: `data` (`size * 4` `f64`s — the sphere
table) and `VisitedBox`'s `bits`. Both are now taken from and returned to
`thread_local` `Cell<Vec<_>>` free-lists (`BLOB_DATA`, `VISITED_BITS`).

**Taken-and-returned, not borrowed across the body**, matching U8's precedent: a
`Cell::take` leaves an empty `Vec` behind, so a hypothetical re-entrant call gets
a correct (merely allocating) fresh buffer rather than a `RefCell` panic or a
shared one. `do_place` is not re-entrant today — `try_place_ore` reaches only
`should_skip_air_check` and `is_adjacent_to_air` — and this pattern means that
fact is not load-bearing.

Per-thread, never shared:
[`worldgen-in-place-decoration.md`](./worldgen-in-place-decoration.md) makes "no
shared pool here, ever" a change rule for U6's store, and a per-thread free-list
is what that rule permits.

## How to change it, and the gotchas

**`clear()` before `resize()` in `VisitedBox::over_spheres` is a correctness
requirement, not tidiness.** `Vec::resize` only zeroes the elements it *adds*, so
a buffer returning from a larger blob arrives carrying that blob's set bits in
every word the smaller blob reuses. A stale set bit reads as "already tested",
which makes `do_place` **skip** a `try_place_ore` it must perform — a **dropped
ore**, i.e. a changed world, not a slow one. It is also invisible to any test
that only ever hands `over_spheres` a fresh `Vec`, which is what every
pre-existing test did.
`feature::tests::a_recycled_visited_buffer_starts_clear` is the regression, and
it was **run against the `clear()` removed and observed failing** before the
clean result was believed.

**RNG order is the world, and neither change touches a draw.** Every draw still
happens inside `get_positions`, *before* the value is returned, so the
consumption order is unchanged; the recursion's depth-first shape is untouched
and only what it iterates changed. `Repeat`'s `n` is stored unclamped and the
consumer's `0..n` is empty for `n <= 0`, the same set `vec![pos; n.max(0)]`
produced. The evidence is a counter, not an argument:
`counters::rng_draws[Stage::Ore]` reads **992,537 before and after**,
digit-identical.

**If a modifier that genuinely fans out to *different* positions is ever added,
it needs its own variant.** It must not be smuggled in as a `Repeat`, whose
consumer recurses `n` times on the *same* position — which is what `vec![pos; n]`
meant and is not what a fan-out means. `docs/plans/worldgen-rewrite.md` names
breadth-first "optimisation" of this recursion as instant desync.

**A panic inside `do_place` loses a scratch buffer** to the empty default, which
costs one allocation on the next call and nothing else. That is the intended
degradation; do not "fix" it with a guard object that reintroduces a borrow
across the body.

## No dependency was added, and that was a measured decision

The brief invited `memchr`, `smallvec`/`arrayvec`, `bumpalo` and
`rustc-hash`/`hashbrown`, with the instruction to judge on measurement rather
than reputation. None of them fits what the measurement found:

* **`smallvec`/`arrayvec`** would have removed the same allocations, but the
  measured shape is not "a short variable-length list" — it is *exactly one
  position, or `n` copies of one position*. An enum says that in the type; a
  `SmallVec` keeps a length that the code no longer needs and cannot express that
  `Repeat` is a repetition rather than a fan-out, which is the distinction the
  RNG-order hazard above turns on. Zero dependencies, better information.
* **`bumpalo`** is for many short-lived *heterogeneous* allocations. After
  attribution the ore path has exactly **two** scratch shapes with a per-blob
  high-water mark, which two `Vec`s hold for free; an arena would add a crate and
  a lifetime to reach the same zero.
* **`rustc-hash`/`hashbrown`** — nothing here needed a map at all. U17's
  `hash::fast` already serves the ore overlay, and this unit's finding is the same
  as the one `worldgen-fast-hashing.md` drew from U15: **a cheap hasher is the
  right fix only for a map that has to stay a map.**
* **`memchr`** — `split('[')` does survive on this path (`try_place_ore`'s base
  name, `is_adjacent_to_air`'s six neighbour reads), but it is a **CPU** question
  and not an allocation one: neither `split` allocates, so neither appears
  anywhere in the attribution above. It is left named rather than guessed at; see
  below.

## What was deliberately left

* **The surface stage's 3,847,972 allocations — 92.46% of the pipeline's, and
  18× the whole ore path.** `overworld/fill.rs`'s `surface_stage` builds a `pre`
  closure returning **`String`** (`"minecraft:air".to_string()`,
  `default_block.clone()`, …) and a `biome_at` closure returning
  `(String, bool)` with a `name.clone()`, and `SurfaceSystem::try_apply`
  accounts for a further 21.90% of the stage. This is U3's interning story never
  applied to the surface seam, and `surface_diff`'s
  `HashMap<(i32,i32,i32), String>` is the same type `worldgen-fast-hashing.md`
  lists as still open. It is a larger change than this unit's remaining budget
  and it is the single biggest allocation win left in worldgen. Tracked as
  [#500](https://github.com/matteopolak/lodestone/issues/500).
* **`in_tag`'s string hashing.** `worldgen-ore-lookup-cost.md` names it as "the
  next lookup on this path" at 10.58% inclusive CPU, and it remains true — but it
  is **not an allocation**: `HashMap<String, HashSet<String>>::get(&str)` plus
  `HashSet<String>::contains(&str)` both borrow. It was out of scope for a unit
  whose target was a measured allocation count, and the id-keyed bitset U15
  prescribes (`feature/vegetation/ids.rs`' shape) is still the right fix.
* **The ore-vein system**, still missing and still the live Overworld parity gap
  `worldgen-ore-lookup-cost.md` documents in full.
* **`RegionView`'s residual one allocation per pass.** It belongs to a medium
  this unit does not own (`feature/region_view.rs`), and the gate keeps headroom
  rather than pinning it to 1 so that a neighbouring unit's free-list change is
  not a false alarm about the wrong file.

## Measurements

Release, embedded production server data, seed 42, 3×3 cold sweep, counting
allocator in `tests/ore_alloc_attribution.rs`, `--features gen-counters`:

| | ore-stage allocations | per ore pass | `rng_draws[Ore]` |
|---|---|---|---|
| pre-U18 (`974bd78b`) | 207,671 | 8,306 | 992,537 |
| post-U18 | **503** | **20** | **992,537** |

**Every other stage's allocation count is unchanged to the digit** across the two
runs — surface 3,847,972, carve 101,651, shape 2,303, biome 784, materialize 444,
aquifer 441, other 250, intern 219, vegetation 158. That was not designed as a
control and is the strongest one available: a change that reached outside the ore
engine would have to move one of the other nine numbers, and none moved.

At the pass level (`tests/ore_allocs.rs`, dev profile, `feature_ore_plains_land`
JVM fixture, 50,920 ore writes): a **warm 3×3 pass allocates 1**, against 48
cold.

**The exact expected value is not derived, and this is the honest statement of
that.** The *removal* has an exact floor from the unsampled size histogram —
163,272 twelve-byte allocations are necessarily `vec![pos]` and all of them must
go — and the measured removal, 207,168, clears it. What is not derived from
outside is the residual 503: it is `RegionHeights::unset()` once per pass (25) plus
the interner's and overlay's growth, which the pre-change sampled attribution put
at 384 ± 157 (six samples), and `503 − 25 = 478` sits inside that band. So the
prediction is mechanism-derived with a bracket, not hand-derived exactly. U15's
doc set that as the bar to beat and this unit did not beat it; it did at least
bracket both hypotheses rather than assert a direction.

| the 13 worldgen parity binaries | `tests/*_parity.rs` | the JVM anchors — unchanged |

### The two controls, each observed failing

An allocation gate that has never been seen to fail is the *assertion* species.
Both mechanisms were reverted separately in the working tree and the gate run
against each:

| control | warm allocs/pass | share of the pre-U18 total |
|---|---|---|
| `get_positions`' `Vec` reinstated | 6,701 | 77.9% |
| scratch reuse disabled | 1,901 | 22.1% |
| both (i.e. pre-U18) | ~8,602 | — |

Each control failed with exit 101 and the diagnostic naming the regime. The
**77.9% / 22.1%** split is a genuine cross-check rather than a restatement: it was
measured on a *different scene* (the JVM plains-land fixture) from the sampled
attribution's **79.96% / 19.86%** (embedded production data, 3×3 sweep), by a
*different instrument*, and the two agree to within about two points.

Restoration after each control was by `cp` from a scratchpad backup with an
**md5 check** — never `git checkout`, per `CLAUDE.md`.

## Configuration

None at run time, no feature gate, no new dependency. The counters the figures
above rest on need `--features gen-counters` (default off; every hook compiles to
an empty function without it). `tests/ore_allocs.rs` deliberately needs **no**
feature, because it drives `apply_ore_step_3x3` directly and counts every
allocation the call makes — so the acceptance criterion is enforced under a plain
`cargo test --workspace`, which is where it needs to hold.
`LODESTONE_ALLOC_SIZE_STAGE` points the attribution instrument's size histogram
at a stage other than `ore`.

## Dependencies

`std` only. `feature::region_view::RegionView` for the read/write medium,
`overworld::decorate` for the 3×3 driver, and `lodestone-worldgen-core`'s
`counters` for the RNG-draw and stage-attribution counters every claim above
rests on. `tests/ore_allocs.rs` reads the checked-in JVM fixture
`tests/support/feature_ore_plains_land_jvm.txt`;
`tests/ore_alloc_attribution.rs` uses `lodestone-server`'s embedded production
generator (already a dev-dependency for `benches/generation.rs`).
