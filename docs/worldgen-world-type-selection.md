# World preset generator selection

## What it is

`crates/lodestone-server/src/worldgen_data.rs`'s entry points for building a
chunk source from any of the seven bundled `world_preset/*.json` documents:
`worldgen_data::WorldType` (`Overworld`/`Amplified`/`LargeBiomes`, all three
sharing `OverworldGenerator`) plus three standalone entry points —
`single_biome_generator`/`single_biome_chunk_source`, `flat_generator`/
`flat_chunk_source`, and `debug_generator`/`debug_chunk_source`. Before issue
#519 only the plain overworld was reachable, from a hardcoded `OnceLock`; the
other six presets' `noise_settings`, density functions and layer/grid data
were bundled and byte-identical to the jar but reached by nothing but their
own drift gate. All seven are now generated by real, individually-verified
code. What is **not** landed here is a way for a player to pick one — see
"How to change it".

## How it works

### `Overworld` / `Amplified` / `LargeBiomes` — `WorldType`

`WorldType::settings_asset` maps each variant to its embedded
`noise_settings/<id>` key; `settings_for(world_type)` parses and caches it
(one `OnceLock` per variant). `overworld_generator_of_type(seed, world_type)`
and `overworld_chunk_source_of_type(seed, world_type)` build a
generator/chunk source from that settings document; `overworld_generator`/
`overworld_chunk_source` are unchanged in signature and behavior — they call
the `_of_type` functions with `WorldType::Overworld`.

No new engine code was needed for these two. `OverworldGenerator::new`
already takes an arbitrary `settings: &Value` and builds its density-function
tree and `ClimateSampler` from it per call, and
`EmbeddedResolver::density_function` already resolves any dotted id under
`density_function/`. Both presets' own `world_preset/{amplified,
large_biomes}.json` select `biome_source.preset: "minecraft:overworld"`, so
`EmbeddedResolver::biome_parameters`'s hardcoded `biome_parameters/overworld`
table is the *correct* table for them, not a stand-in.

### `single_biome_surface` — `SingleBiomeResolver`

Also reuses `OverworldGenerator` — no new biome-source type. The generator
already had a fixed-biome *fallback* path: `OverworldGenerator::new` parses
`resolver.biome_parameters()`, and an empty result (the `Resolver` trait's own
default) makes it build `dynamic_biome: None` and answer every column with
the constructor's `biome`/`cold_enough_to_snow` arguments instead of sampling
climate. This **is** vanilla's `FixedBiomeSource` — it existed for
degradation (a resolver too minimal to supply real biome data) and was never
before selected on purpose.

`SingleBiomeResolver` is a newtype over `EmbeddedResolver` (same shape as
`NetherResolver`) that forwards every method except `biome_parameters`/
`biome_temperatures`, which it leaves at the trait default so the fallback
path activates deliberately. `single_biome_generator(seed, biome)` derives
`cold_enough_to_snow` from `EmbeddedResolver`'s *real* temperature table via
`lodestone_worldgen::biome::cold_enough_to_snow` (so an unusually warm/cold
fixed biome still answers correctly) and builds
`OverworldGenerator::new(seed, overworld_settings, &SingleBiomeResolver,
biome, cold_enough_to_snow)`. Surface material, carvers, ore features and
vegetation all already key off whichever biome id the fixed-biome path
reports for a column (`OverworldGenerator`'s `fallback_biome` field), so a
non-default `biome` (e.g. `"minecraft:desert"`) drives the correct surface
material through the same per-biome data lookups the dynamic path uses —
nothing about surface selection is hardcoded to `"minecraft:plains"`.
`world_preset_single_biome_default_biome()` reads `world_preset/
single_biome_surface.json`'s own `biome_source.biome`
(`"minecraft:plains"`) for the un-customized default.

### `flat` / `flat_all_dimensions` — `lodestone_worldgen::flat`

A structurally different, seed-free generator (`lodestone_worldgen::flat::
FlatLevelSource`, issue #519's third landing) — see
[its own module doc](../crates/lodestone-worldgen/src/flat.rs) for why it is
not built out of `OverworldGenerator`. `world_preset_flat_settings(
all_dimensions)` and `flat_level_generator_preset_settings(id)` parse the
bundled documents into `FlatLevelGeneratorSettings`; `flat_generator`/
`flat_chunk_source` build the generator and its `ChunkSource` wrapper
(`FlatChunkSource`, built entirely from `ChunkColumn`'s public API).

### `debug_all_block_states` — `lodestone_worldgen::debug`

Also seed-free and structurally distinct (`lodestone_worldgen::debug::
DebugLevelSource`, a port of `DebugLevelSource.java`): every registered block
state laid out on a grid at world Y 70, with a `minecraft:barrier` floor at Y
60 and a fixed `minecraft:plains` biome everywhere — see that module's own
doc for the exact index formula (`getBlockStateFor`, transcribed verbatim).
Unlike every other generator here, this one needs a full ordered block-state
list as an input rather than a `Resolver`: `lodestone-worldgen` has no block
registry (it stays version-free), so `worldgen_data::all_block_states_ordered`
builds the list once from `lodestone_data::block_states` (ids `0..
STATE_COUNT`, documented as the vanilla global-palette/wire order — the same
order `DebugLevelSource.ALL_BLOCKS` is built from) via the existing
`canonical_state` helper `Resolver::block_freeze_facts` also uses.
`debug_generator`/`debug_chunk_source` build the generator and its
`ChunkSource` wrapper (`DebugChunkSource`, same shape as `FlatChunkSource`).
No customization: vanilla's debug world has no "Customize" screen, so this
takes no parameters.

## Verified, not just wired

Every preset above has a discriminating test that predicts a *specific* value
from each arm and asserts the two differ (CLAUDE.md's *magnitude* species: "is
different" is not sufficient, since a bug can also differ) —
`crates/lodestone-server/tests/world_type_selection.rs` for
`Amplified`/`LargeBiomes`, and `worldgen_data.rs`'s own
`generation_spawn_reaches_a_real_chunk`/`single_biome_and_debug_world_selection`
test modules for `flat`/`single_biome_surface`/`debug_all_block_states`:

* At seed 4242, chunk `(0, 0)`, local `(0, 0)`: `Overworld` yields
  top-non-air `y = 64`; `Amplified` yields `y = 130` at the identical input.
* Over a 120-chunk strip at the same seed, `Overworld`'s biome changes 20
  times across 12 distinct biomes; `LargeBiomes` changes once across 2.
* `flat_chunk_source` produces `world_preset/flat`'s exact
  bedrock/dirt/dirt/grass_block stack at chunk `(0, 0)`, which differs from
  the default overworld's ordinary underground terrain at the same rows.
* `single_biome_chunk_source(4242, "minecraft:desert")` reports biome
  `minecraft:desert` and surface `minecraft:sand` at y=63 at three sampled
  chunks where the default per-column overworld reports three *different*
  biomes (`snowy_plains`, `snowy_plains`, `plains`) and none of them desert.
* `debug_chunk_source()` places `minecraft:barrier` at every `(x, z)` at
  y=60, and at world `(17, 17)` places
  `minecraft:note_block[instrument=trumpet_exposed,note=8,powered=false]` at
  y=70 — a real multi-property state (`GRID_WIDTH`/`GRID_HEIGHT` both `180`
  at the real 32,366-state count), which differs from the default
  overworld's ordinary terrain at the same column.

## How to change it

**Every bundled `world_preset` document now has a generator.** There is no
"needs new engine work" item left in this module — the remaining gap is
entirely the world-creation screen (below).

* **Add a new preset variant to an existing family** (e.g. another
  `flat_level_generator_preset` alternate) — just call
  `flat_level_generator_preset_settings("<id>")`; no code change needed, the
  9 bundled presets are all already parseable.
* **Add a genuinely new generator family** — follow `flat`/`debug`'s shape:
  a standalone type in `lodestone-worldgen` (not built out of
  `OverworldGenerator` unless the new preset really is a `noise_settings`
  variant), a `ChunkSource` wrapper in `worldgen_data.rs` built from
  `ChunkColumn`'s public API (no `chunk.rs` change needed), and a
  discriminating test predicting a specific value from both the new arm and
  the default overworld's own measured output at the same seed/column.
* **The `world_preset/*.json` documents themselves are still only partly
  parsed.** `flat`/`flat_all_dimensions`/`single_biome_surface`'s own
  `generator.settings`/`biome_source.biome` fields are read directly;
  `amplified`/`large_biomes`/`normal` still go through the hand-written
  `WorldType` enum naming the `noise_settings` id rather than resolving it
  from `world_preset/<id>.json`'s own `generator.settings` field, and
  `debug_all_block_states`'s document carries nothing to read (fixed by
  definition). Unifying this would mean `WorldType` (or a broader enum
  covering all seven) resolves a preset id to a document instead of matching
  on a hand-maintained list — a real simplification, but not required for
  correctness today.
* **A per-preset or per-dimension `Resolver::biome_parameters`** (it
  currently takes no argument) is a **separate**, still-open blocker — it
  matters for a Nether/custom biome source (issue #485), not for anything
  landed in this module: `Amplified`/`LargeBiomes` use the ordinary overworld
  biome table by their own preset's choice, and `single_biome_surface`
  deliberately withholds it rather than needing it widened.

### The world-creation screen: three of seven wired, four still to go

**`normal`/`amplified`/`large_biomes` are wired end to end, as of issue
#592's item 1.** `crates/lodestone-shell/src/menu/create_world.rs`'s
`WorldTypePreset::backend_world_type` converts the player's choice to
`WorldType`; `crates/lodestone-shell/src/app/session.rs`'s
`begin_singleplayer` reads it from `WorldCreationConfig` for a `Created`
launch (same rule as the seed — an `Open`ed existing world always takes
`Overworld`, since there is no persisted world-type field to override it
with), threads it through `app/launch.rs`'s `launch_singleplayer`/
`launch_open_to_lan_online` into `NetClient::open_singleplayer`/
`open_to_lan`, and `net.rs`'s `Origin::Integrated` carries it to the
`overworld_chunk_source_of_type` call that used to hardcode `Overworld`
unconditionally. Verified over a real `NetClient` session by
`crates/lodestone-shell/tests/singleplayer_terrain_arrives.rs`'s
`a_singleplayer_world_honours_the_selected_world_type_end_to_end`, reusing
this module's own measured 64/130 top-of-world heights below rather than
re-deriving them.

**The other four remain unreachable from outside this crate**, blocked on
the same re-export gap named below — selecting one of them in the UI
currently falls back to `Overworld` rather than erroring:

| preset | entry point | reachable from `lodestone-shell` today? |
|---|---|---|
| `normal` | `overworld_generator`/`overworld_chunk_source` (unchanged) | yes |
| `amplified` | `overworld_generator_of_type`/`overworld_chunk_source_of_type(seed, WorldType::Amplified)` | yes |
| `large_biomes` | same, `WorldType::LargeBiomes` | yes |
| `single_biome_surface` | `single_biome_generator`/`single_biome_chunk_source(seed, biome)` — `biome` defaults to `world_preset_single_biome_default_biome()` | no |
| `flat` | `flat_generator`/`flat_chunk_source(world_preset_flat_settings(false))`, or `flat_level_generator_preset_settings(id)` for a Customize-screen alternate | no |
| `flat_all_dimensions` | same, `world_preset_flat_settings(true)` | no |
| `debug_all_block_states` | `debug_generator`/`debug_chunk_source()` — no parameters | no |

All seven functions are `pub` in `worldgen_data.rs`, but only
`WorldType`/`overworld_generator_of_type`/`overworld_chunk_source_of_type`
are currently re-exported from the crate root (`lib.rs`); the single-biome/
flat/debug entry points are reached today only from `worldgen_data.rs`'s own
tests. Closing the remaining four needs those re-exported too — a `lib.rs`
change, not a `worldgen_data.rs` one — plus the same `create_world.rs`/
`app/session.rs`/`app/launch.rs`/`net.rs` threading the first three already
have, plus a UI affordance for `single_biome_surface`'s own `biome`
parameter (vanilla's `WorldTab` cycles a preset list rather than exposing
this directly).

## Configuration

No runtime configuration. `WorldType::default()` is `Overworld`, and every
other entry point above takes its preset explicitly (no implicit default
beyond `world_preset_single_biome_default_biome()`'s document-derived
`"minecraft:plains"`).

## Dependencies

* `crates/lodestone-server/assets/worldgen/{noise_settings,world_preset,
  flat_level_generator_preset}/*.json` — bundled by `build.rs`, see
  [`worldgen-dimensions.md`](./worldgen-dimensions.md) for how the embedding
  works.
* `lodestone_worldgen::overworld::OverworldGenerator` — unchanged; reused for
  `Overworld`/`Amplified`/`LargeBiomes`/`single_biome_surface`.
* `lodestone_worldgen::flat` / `lodestone_worldgen::debug` — standalone
  generators for `flat`/`flat_all_dimensions` and `debug_all_block_states`.
* `lodestone_data::block_states` — the ordered global block-state list
  `debug_generator` needs; this is the one entry point in this module that
  depends on `lodestone-data` rather than staying inside the `Resolver` seam,
  because `lodestone-worldgen` itself has no block registry to enumerate.
* [`worldgen-gap-census.md`](./worldgen-gap-census.md) §1 — the fuller
  inventory of which world types are reached.
